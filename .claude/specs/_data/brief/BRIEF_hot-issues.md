# BRIEF — hot-issues

## 0. OVERVIEW
- 목적: 유명 개발·AI 뉴스 출처의 이슈를 매일 자동으로 모아 카드 형태로 제공해, 사용자가 외부 사이트를 개별 방문하지 않고도 개발·AI 동향을 한 곳에서 훑어볼 수 있게 한다.
- 타겟: 기술 블로그 방문자(개발자·채용 담당자 등) — 최신 개발·AI 이슈를 빠르게 훑어보고 싶은 사용자.
- 범위: 외부 출처로부터의 이슈 자동 수집·저장, 카드형 목록 화면(검색·필터·페이지네이션), 카드 클릭 시 이동하는 상세 화면(원문 요약 표시)까지.
- non-goals: 사용자의 이슈 직접 등록·제출 기능은 이번 범위에 포함하지 않는다. 댓글·좋아요 등 상호작용 기능도 이번 범위에 포함하지 않는다. 실시간 알림·구독(이메일·푸시) 기능도 이번 범위에 포함하지 않는다.

## 1. CORE FACTS
- [F-01] 대상 외부 출처는 유명 개발·AI 뉴스 사이트이며, 예시로 Hacker News, GeekNews, Dev.to가 지정되었다.
- [F-02] 수집 주기는 매일이며, 자동으로 실행된다.
- [F-03] 수집된 이슈는 카드 형태로 목록에 노출된다.
- [F-04] 기존 글 목록 화면은 검색어 입력과 카테고리 탭 필터, 페이지네이션(페이지당 20건, 5페이지 단위 이동)을 제공하며, 핫이슈 피드에도 동일한 검색·페이지네이션 방식을 적용한다.
- [F-05] 기존 글 목록의 검색은 제목·설명·태그 텍스트에 대해 공백을 무시한 부분일치로 동작한다.
- [F-06] 기존 글 목록은 검색 결과가 0건일 때 결과 없음 안내 문구를 표시한다.
- [F-07] 카드를 클릭하면 상세 페이지로 이동하며, 상세 페이지는 원문 내용을 요약한 형태로 보여준다.
- [F-08] 현재 콘텐츠는 별도의 데이터베이스 없이 파일 기반 저장소로 관리되고 있다.

## 2. ASSUMPTIONS
- [A-01] 매일 자동 수집은 하루 1회, 지정된 특정 시각에 일괄 실행되는 것으로 가정한다. 근거: 입력에 정확한 수집 시각·횟수가 없어 최소 운영 부담 기준(1일 1회)으로 가정.
- [A-02] 원문 요약은 수집 시점에 1회 생성되어 저장되고, 이후 상세 페이지 조회마다 재생성하지 않는 것으로 가정한다. 근거: 매 조회마다 요약을 새로 만들면 응답 지연·비용이 커짐.
- [A-03] 요약 표시 언어는 한국어로 통일하는 것으로 가정한다. 근거: 블로그의 주 사용자층이 한국어 사용자.
- [A-04] 이슈 중복 판정 기준은 원문 URL 동일 여부로 가정한다. 근거: 동일 이슈가 여러 출처·시점에 재수집될 가능성이 있어 식별 기준이 필요.
- [A-05] 특정 이슈의 원문 수집(접근)에 실패하면 해당 이슈는 목록에 노출하지 않는 것으로 가정한다. 근거: 깨진 콘텐츠 노출보다 미노출이 사용자 경험상 안전.
- [A-06] 카드 목록의 기본 정렬 기준은 수집(발행) 시각 최신순으로 가정한다. 근거: "매일 자동 수집"의 목적이 최신 동향 파악이므로 최신순이 자연스러움.
- [A-07] 카드에는 최소한 제목, 출처명, 수집일, 요약 일부(스니펫)를 표시하는 것으로 가정한다. 근거: 기존 글 카드(PostItem)와 동등한 정보 밀도를 유지하기 위함.
- [A-08] 핫이슈 피드의 검색은 제목·요약·출처명 텍스트를 대상으로 하고, 페이지네이션은 기존 글 목록과 동일하게 페이지당 20건 단위로 나누는 것으로 가정한다. 근거: [F-04] 기존 UX 재사용 요구를 그대로 따름.
- [A-09] 출처별 필터는 기존 카테고리 탭과 동일하게 "전체" + 출처별 탭 형태로 제공하는 것으로 가정한다. 근거: [F-04]의 카테고리 탭 패턴을 출처 축에 재적용.
- [A-10] 수집된 이슈는 별도 삭제 없이 무기한 누적 보관하는 것으로 가정한다. 근거: 입력에 보관 기간 언급이 없어 데이터 유실 방지를 우선.
- [A-11] 상세 페이지와 카드에는 원문 출처명과 원문 링크를 항상 함께 표기하는 것으로 가정한다. 근거: 요약이 원문을 대체하지 않도록 출처를 명확히 밝힐 필요.

## 3. EARS REQUIREMENTS
- [REQ-01] When 자동 수집 주기가 도래하면 → Then 시스템은 지정된 외부 출처들에서 신규 개발·AI 이슈를 수집해 저장한다.
- [REQ-02] When 신규 이슈가 수집되면 → Then 시스템은 해당 이슈의 원문 내용을 요약해 함께 저장한다.
- [REQ-03] Given 동일 원문 URL의 이슈가 이미 저장되어 있음, When 동일 이슈가 재수집되면 → Then 시스템은 중복 저장하지 않고 기존 항목을 유지한다.
- [REQ-04] Given 특정 출처의 수집이 실패함, When 수집 주기가 실행되면 → Then 시스템은 해당 출처를 제외한 나머지 출처의 수집을 계속 진행한다.
- [REQ-05] Given 특정 수집 주기에 신규 이슈가 하나도 없음, When 수집이 완료되면 → Then 시스템은 기존에 저장된 목록을 그대로 유지한다.
- [REQ-06] When 사용자가 핫이슈 피드 목록 화면에 진입하면 → Then 시스템은 저장된 이슈를 카드 목록 형태로, 수집 시각 최신순으로 표시한다.
- [REQ-07] When 사용자가 검색어를 입력하면 → Then 시스템은 제목·요약·출처명 중 하나 이상에 검색어가 포함되는 이슈만 목록에 남긴다.
- [REQ-08] Given 검색 결과가 0건, When 검색이 실행되면 → Then 시스템은 결과 없음 안내 문구를 표시한다.
- [REQ-09] Given 필터링된 목록이 20건을 초과함, When 사용자가 목록 화면을 조회하면 → Then 시스템은 목록을 20건 단위 페이지로 나눠 표시한다.
- [REQ-10] When 사용자가 특정 페이지 번호를 선택하면 → Then 시스템은 해당 페이지에 속하는 20건 이하의 이슈만 표시한다.
- [REQ-11] When 사용자가 출처 탭을 선택하면 → Then 시스템은 선택한 출처에서 수집된 이슈만 목록에 표시한다.
- [REQ-12] When 사용자가 카드를 클릭하면 → Then 시스템은 해당 이슈의 상세 페이지로 이동한다.
- [REQ-13] When 상세 페이지가 열리면 → Then 시스템은 해당 이슈의 요약, 출처명, 수집일, 원문 링크를 표시한다.
- [REQ-14] When 사용자가 상세 페이지에서 원문 링크를 선택하면 → Then 시스템은 원문 페이지로 이동 가능한 경로를 제공한다.

## 4. SCREENS
- [S-01] 핫이슈 피드 목록 — 수집된 이슈를 카드 형태로 나열하고, 검색·출처 필터·페이지네이션을 제공하는 화면.
- [S-02] 핫이슈 상세 — 개별 이슈의 요약·출처명·수집일·원문 링크를 보여주는 화면.

## 5. OPEN QUESTIONS
- [Q-01] 수집 대상 출처 범위를 어떻게 운영할까? A안(추천): Hacker News·GeekNews·Dev.to 등 고정된 소수 출처로 우선 운영하고, 출처 추가는 이후 별도 작업으로 처리한다(운영 부담 최소화). B안: 처음부터 출처를 추가·삭제할 수 있는 관리 기능을 함께 포함한다(운영 자유도는 높지만 범위 확대).
- [Q-02] 핫이슈 피드를 기존 글 목록과 어떤 관계로 노출할까? A안(추천): 기존 글 목록과 완전히 분리된 별도 섹션으로 제공한다(자체 작성 콘텐츠와 외부 수집 콘텐츠를 명확히 구분). B안: 기존 글 목록에 핫이슈 카드를 함께 섞어 통합 노출한다.
- [Q-03] 상세 페이지에서 원문을 어느 범위까지 보여줄까? A안(추천): 요약만 제공하고 원문 전문은 원문 링크로 이동해 확인하도록 유도한다(저작권 부담 최소화). B안: 원문 전문을 그대로 가져와 페이지 내에 전체 표시한다.
- [Q-04] 수집된 이슈 노출에 사람의 검수 개입이 필요한가? A안(추천): 수집 규칙을 통과한 이슈는 사람 개입 없이 전량 자동 노출한다. B안: 노출 전에 운영자가 승인·제외할 수 있는 검수 단계를 추가한다.
- [Q-05] 수집된 이슈를 얼마나 오래 보관할까? A안(추천): 기간 제한 없이 무기한 누적 보관한다. B안: 일정 기간(예: 최근 90일)이 지난 이슈는 자동으로 숨기거나 삭제한다.
