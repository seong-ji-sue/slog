> **TL;DR** — 접근관리 콘솔 안에는 쿠버네티스 오브젝트(Workload, Service, Volume 등)를 웹 화면에서 다루는 배포/운영관리 서브시스템이 있다. 이 글은 그 화면을 "리스트 → 상세 → 배포 계획 → 모니터링" 순서로 나눈 이유를, 백엔드·프론트를 나눠 맡은 동료들과 함께 설계에 참여한 입장에서 정리한다.

1️⃣ `배포 계획 관리` 2️⃣ `리소스별 CRUD` 3️⃣ `Yaml 편집기 공통화`

### ✅ 상황

접근관리 콘솔에는 애플리케이션을 실제로 배포하고 운영하는 화면이 필요했다. 대상은 프로젝트, 클러스터, 서비스, 워크로드, 볼륨(볼륨/볼륨클레임), 배포 계획까지 — 쿠버네티스 오브젝트 대부분을 웹 화면에서 조회·생성·수정·삭제할 수 있어야 하는 규모였다. 백엔드는 동료가, 프론트는 또 다른 동료가 맡았고 나는 그 사이에서 공통 Yaml 편집기 같은 일부 조각을 함께 만들며 전체 설계 논의에 참여했다.

### ✅ 왜 리소스별로 화면을 쪼갰나

가장 먼저 정리된 건 "쿠버네티스 오브젝트 하나당 관리 화면 하나"라는 원칙이었다.

- 프로젝트 관리 — 배포 대상 프로젝트 자체를 등록/관리
- 클러스터 관리 — 어느 클러스터에 배포할지 관리
- 서비스 관리 — 서비스 조회/생성(라벨 추가)/수정/삭제
- 워크로드 관리 — 실제 애플리케이션 워크로드
- 볼륨 관리 — 볼륨과 볼륨 클레임
- 배포 계획 관리 — 배포 실행 전 리소스 조회/추가/삭제 후 실제 배포를 트리거

쿠버네티스 리소스는 원래도 서로 참조 관계가 있는 독립된 개체(프로젝트 안에 클러스터, 클러스터 안에 워크로드/서비스/볼륨)라서, 화면도 그 경계를 그대로 따라가는 게 자연스러웠다. 하나의 거대한 "배포 관리" 화면으로 뭉치는 대신 리소스 단위로 나누면, 백엔드 API 경계와 프론트 화면 경계가 1:1로 맞아떨어져서 담당자를 나누기도 쉬웠다.

### ✅ 화면 흐름 — 리스트 → 상세 → 배포 계획

각 리소스 화면은 공통적으로 같은 흐름을 탔다.

1. **리스트** — 해당 리소스(워크로드/서비스/볼륨 등) 전체 목록 조회, 검색·필터
2. **상세** — 개별 리소스의 스펙 확인, yaml 형태로 편집 가능
3. **배포 계획** — 배포하기 전 단계에서 리소스를 조회·추가·삭제하고 실제로 배포를 실행

배포 계획 관리가 별도 화면으로 분리된 이유는, "배포를 실행하는 행위" 자체가 다른 CRUD와 성격이 달랐기 때문이다. 워크로드나 서비스를 조회·수정하는 건 상태를 들여다보고 스펙을 고치는 일이지만, 배포 계획은 "지금 이 리소스들을 실제로 클러스터에 적용한다"는 실행 액션이 걸려 있는 화면이었다. 그래서 배포 전 확인 단계(리소스 조회/추가/삭제)와 배포 실행을 한 화면에 묶어서, 사용자가 뭘 배포하는지 확실히 보고 나서 실행 버튼을 누르게 만든 게 이 화면의 설계 의도였다.

### 🛠️ 공통 조각 — Yaml 편집기

여러 리소스 화면이 공통으로 필요로 한 게 Yaml 편집/조회 기능이었다. 워크로드든 서비스든 결국 쿠버네티스 리소스는 yaml 스펙으로 표현되기 때문에, "리소스를 폼으로만 편집"하는 게 아니라 "원본 yaml을 직접 보고 고칠 수 있는" 옵션이 필요했다. 요구사항 자체도 처음부터 "배포/운영관리 전체가 쓸 공통 컴포넌트로 만든다"는 전제로 들어왔다.

이 편집기를 리소스 화면마다 따로 만들지 않고 공통 컴포넌트로 뽑아둔 덕분에, 워크로드 상세 화면이든 서비스 상세 화면이든 같은 Yaml Edit/New 컴포넌트를 그대로 갖다 쓸 수 있었다. 처음부터 "이 기능은 리소스 화면 6개가 전부 필요로 한다"는 걸 알고 있었기 때문에, 개별 화면 안에 넣지 않고 공통 영역으로 분리하는 선택이 자연스러웠다.

### ✅ 백엔드 쪽 핵심 개념 (요약)

프론트 흐름이 중심인 글이라 백엔드는 핵심만 짚는다. 백엔드는 프로젝트·클러스터·서비스·워크로드·볼륨 각각에 대해 대응하는 관리 API를 구현했고, 리소스 등록 시 필요한 초기 데이터(init database script) 세팅까지 함께 처리했다. 프론트가 리소스 단위로 화면을 나눈 것과 동일하게, 백엔드도 리소스 단위로 API 경계를 나눠서 프론트-백엔드 담당자 간 인터페이스가 명확했던 게 이 서브시스템이 비교적 매끄럽게 진행된 이유 중 하나였다고 생각한다.

### ✅ 전체 구조 요약

```
Project 관리
  └ Cluster 관리
       ├ Workload 관리 ─┐
       ├ Service 관리   ├ Yaml Edit/New(공통) 사용
       └ Volume 관리   ─┘
       └ 배포 계획 관리 (리소스 확인 → 배포 실행)
```

#### 🎯 결과 & 배운 점

- 쿠버네티스 오브젝트처럼 서로 참조 관계가 있는 도메인은, 화면도 그 참조 경계를 그대로 따라가면 담당자 분담과 API 설계가 함께 깔끔해진다
- "조회/수정"과 "실행(배포)"은 성격이 다른 행위이므로, 같은 리소스를 다루더라도 확인 단계와 실행 단계를 별도 화면으로 분리하는 게 사용자 안전장치가 된다
- 여러 화면이 공통으로 필요로 하는 기능(Yaml 편집기)은 처음부터 공통 컴포넌트로 설계에 넣어두면, 이후 화면이 늘어나도 중복 구현을 피할 수 있다
