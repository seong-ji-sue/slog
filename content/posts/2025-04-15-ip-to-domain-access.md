> **TL;DR** — 배포 스크립트마다 `192.168.x.x` 같은 IP가 그대로 박혀 있었다. 접속 대상을 도메인으로 바꾸면 뭐가 좋아지는지, 왜 이 전환이 필요했는지를 짧게 정리한다.

난이도 : ★★☆☆☆

1️⃣ `IP 하드코딩` 2️⃣ `DNS` 3️⃣ `TLS 도메인 검증`

### ✅ 계기

Jenkinsfile을 열어보면 배포 대상이 이렇게 박혀 있었다.

```groovy
REMOTE_HOST = '192.168.x.x'
registry = '192.168.x.x:5000'
```

standalone 전환 작업(HTTPS 적용)을 하면서 인증서 얘기가 나왔는데, 인증서는 보통 도메인 기준으로 발급된다. IP 기준으로 인증서를 발급하는 것도 기술적으로는 가능하지만 일반적이지 않고, 사설 IP(`192.168.x.x`)는 공인 인증기관에서 아예 발급을 안 해준다. 이 지점에서 "접속 대상 자체를 도메인으로 바꿔야 하는 것 아닌가"라는 질문이 자연스럽게 나왔다.

### ✅ IP 고정 방식의 문제

- 서버가 재배치되거나 IP가 바뀌면 Jenkinsfile·환경변수·설정 파일을 전부 찾아서 고쳐야 함
- 여러 고객사 환경마다 IP 체계가 다른데, 그때마다 배포 스크립트를 개별 수정해야 함
- 인증서를 도메인 기준으로 발급하려면 애초에 접속 경로가 도메인이어야 함

### ✅ 도메인 전환의 방향

- 배포 대상을 IP 대신 도메인(예: `deploy.example.com`)으로 통일
- 실제 IP는 DNS 레코드가 담당하게 하고, IP가 바뀌어도 DNS만 갱신하면 배포 스크립트는 그대로 재사용 가능
- 이렇게 되면 도메인 기준 TLS 인증서 발급·검증도 자연스럽게 연결됨

### 🎯 솔직한 결과

이 부분은 앱 저장소 안에서 직접적인 증거를 더 찾지 못했다 — 실제 도메인 전환 작업은 배포 인프라(Jenkins·nginx·DNS) 쪽 설정이라 애플리케이션 레포의 커밋 이력에는 흔적이 거의 남지 않았다. 그래서 이 글은 "왜 이 전환이 필요하다고 판단했는지"까지만 정리하고, 실제 전환의 세부 구현(DNS 레코드 관리, nginx server_name 설정 등)은 인프라 쪽 자료가 더 확보되면 후속편으로 채워 넣을 계획이다. 삽질의 결과가 아니라 "아직 다 못 판 부분"을 있는 그대로 남겨두는 것도 회고의 일부라고 생각한다.
