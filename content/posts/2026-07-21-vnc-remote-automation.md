### ✅ 요구사항

> 고객사 : PSM for SSH/System에서는 VNC Tool이 되던데, 여기서도 되나요?  
> 선임 : 검증부터 해보자. 되면 만들고, 안 되면 안 되는 이유를 명확히 설명해야지  
> 나 : VNC 프로토콜부터 좀 파보겠습니다

이전 글에서 다룬 SAP 자동화가 "요청받은 걸 어떻게든 만들어내는" 이야기였다면, 이번 VNC는 "되는지 안 되는지부터 확인해야 하는" 이야기였다. 요청 시나리오가 상세하게 오지 않고 "호환 여부 문의" 수준으로만 왔기 때문에, 검증과 개발을 동시에 진행해야 했다.

### ✅ VNC(RFB 프로토콜) 개요부터 정리

- VNC는 RFC 6143(RFB 프로토콜) 기반의 원격 화면 공유 기술이다. Server(화면 제공)와 Client=Viewer(화면 열람·조작) 구조로 나뉜다
- 이번 요청 범위는 명확히 "접속까지"였다. 원격 화면 내부는 픽셀 스트림이라 컨트롤이 존재하지 않는다는 걸 먼저 확인하고, 접속창·인증창까지만 자동화 대상으로 정리했다. 원격 화면 내부 조작까지 자동화하려면 별도로 OpenCV 이미지매칭 방식으로 확장해야 한다는 것도 범위 밖 항목으로 명시했다

### ✅ 자동화 가능 여부 분석 — 컨트롤 있는 창 vs 픽셀 스트림

VNC 뷰어를 실행했을 때 뜨는 접속창과 인증창은 일반 Windows 창이라 창 클래스와 컨트롤 ID로 AutoIt이 직접 제어할 수 있다. 좌표나 이미지 인식이 필요 없는, 상대적으로 다루기 쉬운 대상이었다.

반면 뷰어 창 내부는 원격 화면을 픽셀로 그대로 뿌리는 스트림이라 컨트롤이 전혀 없다. 이 부분까지 자동화하려면 컨트롤 제어가 아니라 이미지매칭 방식으로 접근해야 한다는 게 조사 결과였다. 다행히 이번 요청 범위는 "접속까지"였으므로 컨트롤 제어만으로 구현이 가능했다.

### ✅ 접속 흐름 구현 — 창 클래스로 성공 판정

접속 절차는 다음 순서로 짰다.

```
tvnviewer.exe 실행
  → 접속창 대기 → Remote Host 입력 → Connect 클릭
  → 인증창 대기 → Password 입력 → OK 클릭
  → 뷰어 창 클래스 출현 대기 → 접속 성공
```

여기서 판정 방식에 신경을 좀 썼다. 뷰어 창의 제목은 접속 대상 호스트에 따라 매번 달라지기 때문에, 제목으로 성공 여부를 판정할 수 없었다. 그래서 제목이 아니라 창 클래스(`TvnWindowClass`) 출현 여부로 접속 성공을 판정하도록 했다 — 이전 글에서 다룬 "거짓 성공 판정" 문제를 여기서도 미리 의식하고 짠 부분이다.

비밀번호 입력 필드는 마스킹 처리된 Edit 컨트롤이라 `ControlSetText`가 먹지 않는 경우가 있어서, 실패 시 `ControlFocus` + `Send`로 폴백하는 처리도 넣었다.

### ✅ 연동모드 · 로컬모드 이중 구조

기존 CS 타입 앱들과 동일하게, 이번에도 두 가지 실행 모드를 표준으로 구현했다.

- **연동모드(login.au3)**: 플랫폼을 경유해서 실행되는 모드. 접속 정보를 스크립트에 하드코딩하지 않고, 실행 시점에 플랫폼에 등록된 계정 정보에서 조회한다. 이때 ID 칸을 접속 대상 VNC 서버 호스트명으로, PW 칸을 VNC 접속 비밀번호로 매핑하는 규칙을 정했다 — 원래 계정 체계가 "사람 계정"을 위한 필드인데, 이걸 "접속 대상 서버 식별자"로 용도를 바꿔 쓴 셈이라 운영 등록 시 헷갈리지 않도록 문서에 남겨뒀다
- **로컬모드(login_local.au3)**: 플랫폼 없이 로컬에서 바로 실행 검증할 수 있는 모드. `config.ini`에서 실행 경로·호스트·비밀번호를 직접 읽는다

이 이중 구조 자체는 새로 발명한 게 아니라, 기존 CS 타입 앱(Toad, SQLDeveloper 등)에서 이미 쓰던 표준 구조를 그대로 재사용한 것이다. 새 앱을 만들 때마다 이 뼈대를 다시 고민할 필요가 없었던 게, 표준화가 미리 되어 있었던 덕을 본 지점이었다.

### ✅ 구조 개선 — 별도 파일을 폐지하고 표준 2파일 규칙으로 흡수

처음 구현할 때는 접속 로직(`_ConnectVnc`)을 별도의 전용 파일로 분리해서 짰다. 그런데 이후 팀 컨벤션이 "앱마다 login/login_local + utils 2파일 규칙"으로 정리되면서, 이 전용 파일을 폐지하고 로직을 `utils.au3`로 흡수했다. 로직 자체는 그대로 두고 파일 구조만 표준에 맞춘 리팩토링이었다.

이 커밋 하나만 떼어놓고 보면 사소해 보이지만, 실은 다음 글에서 다룰 "AppScript 11종 공통화" 작업이 실제로 자리잡아가는 과정의 한 조각이었다. 표준이 문서로만 존재하는 게 아니라, 새로 만든 지 얼마 안 된 코드도 표준에 맞춰 다시 정리하는 데까지 이어졌다는 게 의미 있었다.

### ✅ 검증 결과

접속 자동화가 정상 동작하는 걸 확인했다. 접속창에 호스트가 자동으로 입력되고, 인증창에 비밀번호가 자동 입력되고, 뷰어 창이 출현하기까지 사용자 개입 없이 전 과정이 수행됐다.

결론은 "우리 플랫폼 환경에서도 VNC를 통한 앱 실행 지원이 가능하다"였다. 고객 문의에 막연히 "될 것 같다"가 아니라, 실제로 동작하는 걸 확인한 뒤 "된다"고 답할 수 있게 된 것 — 이게 이번 작업의 실질적인 성과였다.

### ✅ 결과 & 배운 점

| 항목 | 이전 | 이후 |
|------|------|------|
| VNC 지원 여부 | 미확인(문의 수준) | 접속 자동화 검증 완료, 지원 가능 확인 |
| 성공 판정 방식 | (신규 개발) | 뷰어 창 클래스 출현 여부로 판정 (제목 의존 배제) |
| 파일 구조 | 접속 로직 별도 파일 분리 | utils.au3로 흡수, 표준 2파일 규칙 준수 |

호환 여부 문의처럼 "예/아니오"로 끝날 것 같은 요청이 실제로는 프로토콜 조사·자동화 가능 범위 판단·표준 구조 설계까지 이어지는 걸 다시 확인했다. 범위를 처음부터 "접속까지"로 명확히 그어둔 게, 나중에 "그럼 원격 화면 안쪽은요?"라는 질문에 흔들리지 않고 답할 수 있게 해준 지점이었다.
