> **TL;DR** — 새 웹 자동화 대상을 붙일 때마다 로그인 폼 XPath를 브라우저 개발자도구로 손으로 찾는 게 반복 작업이라는 걸 인식했다. 그런데 바로 코드부터 짜지 않고, 목표·비목표·수용 기준(AC)을 먼저 문서로 못박은 뒤에 도구를 만들었다. "왜 도구부터 기획했는지"가 이번 글의 핵심이다.

난이도 : ★★★☆☆

1️⃣ `XPath 자동 도출` 2️⃣ `기획(PRD→PLAN→TC) 먼저, 코드는 나중`

### ✅ 요구사항

> 나 : 이번에도 새 웹 자동화 대상 붙이는데, 로그인 폼 XPath를 또 개발자도구 열어서 하나하나 찾고 있다. 이거 벌써 몇 번째지  
> 동료 : 매번 그렇게 하고 있었나? 패턴이 비슷하면 자동화할 수 있을 것 같은데  
> 나 : 문제는 이거 사내망 베스천에서만 붙일 수 있는 대상도 있고, 고객 현장에서 인터넷 없이 돌아가야 하는 경우도 있어서 생각보다 조건이 복잡하다  
> 동료 : 그럼 이번엔 바로 코드 짜지 말고, 뭘 만들 건지부터 정리하고 시작하자

XPath를 찾는 작업 자체는 매번 패턴이 비슷했다. 로그인 폼을 열고, ID 입력란·PW 입력란·로그인 버튼·성공 판정 지점을 찾아서 `config.ini`에 옮겨 적는 일이었다. 반복되는 작업이라는 걸 알고 있었지만, 그동안은 "매번 다른 사이트니까 그때그때 손으로"라고 넘겨왔다.

### ✅ 왜 코드부터 안 짜고 기획서부터 썼나

이 도구는 내가 나 스스로를 위해 만드는 도구였다. 그래서 오히려 "일단 짜보고 고치면 되지"라는 유혹이 컸다. 실제로 처음에는 그냥 스크립트 하나 뚝딱 만들면 될 거라고 생각했다.

그런데 요구사항을 다시 짚어보니 생각보다 조건이 얽혀 있었다.

- **사용 경로가 두 가지다** — 사내 인프라를 경유해서 내부적으로 라이브 실행하는 경로, 그리고 고객 현장 베스천에 파일 몇 개만 올려서 인터넷 연결 없이 독립 실행하는 경로. 이 둘이 서로 다른 소스로 갈라지면 유지보수가 두 배가 된다
- **실패 케이스가 여러 갈래다** — 입력값 누락, URL 접속 불가, DOM 요소 미발견, 인증 실패, 타임아웃. 각각을 다르게 처리해야 하는데 코드부터 짜면 이 갈래를 하나씩 발견할 때마다 땜질하게 될 게 뻔했다
- **범위를 넘어가기 쉬운 작업이다** — 로그인 폼 하나만 지원하면 되는데, 만들다 보면 "이왕이면 다단계 SSO도"라는 욕심이 붙기 쉬웠다

그래서 이번엔 코드를 짜기 전에 PRD(목표·비목표·수용 기준) → PLAN(작업 순서) → TC(검증 항목) 형태로 먼저 문서를 썼다. 핵심은 "비목표"를 먼저 적은 것이다.

- 다단계 SSO/OAuth 로그인 — 지원 안 함(2차 범위)
- 오답 자격증명으로 재시도 — 하지 않음(계정 잠금 위험 방지)
- 이 도구 자체에 대한 별도 API 서버 — 만들지 않음(에이전트/사람이 직접 실행하는 워크플로로 취급)

이 세 줄을 미리 적어두지 않았다면, 만드는 도중에 분명히 "이것도 되면 좋겠다"는 생각에 계속 범위가 늘어났을 거다. 자기 자신을 위한 도구일수록 기획 문서가 스스로에게 거는 제동장치 역할을 했다.

### ✅ 구현 — probe.au3, verdict 마커로 판정하는 진단 스크립트

수동 배포본과 자동 워크플로가 **같은 소스를 공유**하도록 설계했다. 로직이 두 갈래로 갈라지는(drift) 걸 원천 차단하기 위해서다.

```
bastion_settings/probe/
  probe.au3            # 소스 (수동/자동 공유)
  probe.exe             # Aut2Exe /x64 빌드 산출물
  chromedriver.exe       # 기존 자동화 스택 재사용
  RDSAppScriptLib.dll     # 기존 자동화 스택 재사용(x64)
  probe_input.txt         # URL/ID/PW/OUTPUT_DIR 입력 템플릿
  README.md
```

<!-- 이미지 제안: probe_input.txt 입력 → 헤드리스 브라우저 DOM 탐색 → config.ini/flow.json 생성으로 이어지는 probe.au3 실행 흐름도 -->

동작 방식은 이렇다.

1. `probe_input.txt`에 URL·계정·비밀번호·출력 폴더를 채운다 (하나라도 비면 브라우저조차 뜨지 않고 즉시 오류 종료)
2. 헤드리스 브라우저로 대상 페이지에 접속해서, DOM에 JS를 주입해 ID/PW 입력란과 로그인 버튼을 탐지한다
3. 로그인을 시도해보고, 결과에 따라 `config.ini`(XPath 5종) + `flow.json`/`flow.txt`(로그인 절차)를 생성한다

모든 실행 결과는 `probe.log`에 `##RESULT:verdict=...##` 마커로 남는다.

| verdict | 의미 |
|---------|------|
| `SUCCESS` | 로그인 성공 — XPath 5키 + flow 파일 정상 생성 |
| `FAIL:INPUT` | 입력값 누락 — 브라우저조차 안 뜸 |
| `FAIL:NAV` | URL 도달 불가(네트워크/방화벽) |
| `FAIL:DOM` | 로그인 폼(PW 입력란) 미발견 |
| `FAIL:AUTH` | 로그인 시도 후 URL 잔류(자격증명 오류) — **재시도 없음** |
| `FAIL:TIMEOUT` | DOM 탐색 30초 초과 |

`FAIL:AUTH`에서 재시도를 아예 넣지 않은 건 의도적인 선택이다. 도구가 자동으로 몇 번씩 재시도하다가 계정이 잠기는 상황이 훨씬 골치 아프기 때문에, 인증 실패는 사람이 직접 확인하고 다시 실행하도록 막아뒀다.

```ini
; probe 성공 시 출력되는 config.ini 예시 구조
[Login]
ID=...
PW=...
URL=...

[XPath]
IdInput=...
PwInput=...
LoginBtn=...
SuccessCheck=...
ErrorMsg=...
```

DOM 탐색은 `_WD_ExecuteScript`로 JS를 주입하는 방식을 기본 경로로 잡았는데, 이 함수는 기존 스택에서 실제로 검증해본 적이 없는 함수였다. 그래서 실패 시 흔한 id/name/버튼 텍스트 후보를 순차 탐색하는 대체 경로(`_ProbeFallback`)를 하나 더 만들어서, 기본 경로가 안 통하는 페이지에서도 최소한의 탐색은 시도하게 했다. 그리고 PW는 파싱 직후 마스킹해서, 로그 어디에도 원문이 남지 않게 했다.

### ✅ 실측 검증 — 사내 통합 플랫폼 로그인 화면으로 E2E PASS

기획과 구현을 마친 뒤, 실제 사내 통합 플랫폼의 로그인 화면을 대상으로 probe를 돌려봤다. 처음 실행에서 몇 군데 실측 오차가 나와서 `probe.au3`를 수정했고, 도출된 `config.ini`를 기존 범용 로그인 스크립트에 그대로 연결해서 실제 로그인 자동화가 끝까지 통과하는 걸 확인했다.

여기서 확인한 건 "XPath를 뽑아내는 것" 자체가 아니라, 그 XPath로 실제 로그인까지 되는지였다. 프로버가 뽑아낸 값이 형식만 맞고 실제로는 안 먹히면 아무 의미가 없기 때문에, E2E로 실제 로그인 성공까지 봐야 이 도구가 제 역할을 한다고 판단할 수 있었다.

### ✅ 결과 & 배운 점

| 항목 | 이전 | 이후 |
|------|------|------|
| XPath 탐색 방식 | 개발자도구로 사람이 수동 탐색 | probe.exe 실행 한 번으로 자동 도출 |
| 산출물 연동 | 수작업으로 config.ini 작성 | 도출된 config.ini를 기존 스크립트에 바로 연결 |
| 실패 처리 | 정해진 규칙 없음 | verdict 마커 6종으로 원인 구분 |
| 인증 실패 대응 | (수동이라 해당 없음) | 재시도 없이 즉시 중단(계정 잠금 방지) |

이번 작업으로 배운 건, 반복 작업을 자동화하는 도구 자체도 "바로 손대고 싶은 유혹"이 제일 큰 대상이라는 점이다. 결과가 눈에 바로 보이니까 빨리 짜고 싶어진다. 그런데 비목표와 실패 계약을 먼저 정의하고 나니, 오히려 다단계 SSO 같은 곁가지에 흔들리지 않고 로그인 폼 하나에 집중해서 더 빨리 끝낼 수 있었다. 나를 위한 도구일수록 기획을 건너뛰지 말아야 한다는 걸 이번에 체감했다.
