> **TL;DR** — AI(Claude)와 작업하다가 세션이 끊기면 어제 뭘 했는지, 왜 그렇게 결정했는지가 전부 사라진다는 문제를 겪었다. 처음엔 `/start`·`/end`로 작업 이력을 파일에 남기는 단순한 구조(1세대)를 만들었는데, 병렬 작업을 하려니 한계가 바로 드러났다. 그래서 Git의 브랜치·체크아웃 개념을 본떠 작업별로 독립된 기록을 남기고 명령어 하나로 전환하는 2세대 구조로 다시 설계했다.

난이도 : ★★★☆☆

1️⃣ `컨텍스트 휘발성` 2️⃣ `Git 스타일 작업 전환` 3️⃣ `서버 캐싱과의 차이`

### ✅ 문제 — 세션이 끝나면 다 잊어버린다

Claude 같은 LLM과 협업할 때 근본적으로 겪는 문제가 세 가지 있었다. 세션이 종료되면 어제 작업 내용과 프로젝트 환경, 설계 결정 이유를 전부 잊어버리는 **컨텍스트 휘발성**, 매 세션마다 프로젝트 기본 환경과 규칙을 반복 설명하며 시간과 토큰을 낭비하는 문제, 그리고 이슈 해결 과정이나 설계 근거가 기록으로 남지 않아 나중에 유지보수가 어려워지는 **기록의 부재**다.

핵심 아이디어는 단순했다. Claude가 작업을 파일에 실시간으로 기록하게 하고, 다음 세션에서 그 파일을 읽어 컨텍스트를 즉시 복원하는 것.

### ✅ 1세대 — 단일 작업 기록 (`/start`, `/end`)

처음 만든 구조는 작업 이력을 자동으로 문서화하는 정도였다.

```
프로젝트폴더/
├── CLAUDE.md
├── memory/
│   ├── MEMORY.md          # 현재 프로젝트 상태 요약
│   ├── job_history.md     # 세션별 작업 이력 누적
│   └── current_task.md    # 현재 작업 중인 실시간 메모(휘발성)
└── output/
    └── redmine_output.txt # 작업 종료 시 자동 생성되는 보고서
```

써보니 한계가 바로 드러났다. `current_task.md`가 하나뿐이라 병렬 작업을 하려면 이전 기록을 종료(`/end`)해야만 다음 작업을 시작할 수 있었다. 재시작할 때 "내가 어떤 프로젝트의 어떤 작업을 하고 있었는지" 추적할 방법도 없었고, A 작업에서 B 작업으로 전환하면 맥락이 끊기고 다시 A로 돌아올 때 수동으로 복구해야 했다.

### ✅ 2세대 — Git 스타일 멀티태스킹

1세대의 한계를 넘기 위해 전역 상태 관리(HEAD 개념)와 작업 독립성을 도입했다. 핵심 변경은 세 가지다.

1. **멀티태스킹 지원(`tasks/` 폴더)** — 작업별로 독립된 파일을 생성해 기록을 보존
2. **전역 상태 추적(`config.json`)** — 현재 활성화된 프로젝트와 작업을 시스템이 기억
3. **Git 스타일 명령어** — `switch`, `commit` 등으로 컨텍스트를 제어

| 명령어 | 용도 | Git 대비 |
|--------|------|----------|
| `/ctx-project` | 새 프로젝트 생성 및 템플릿 배포 | `git init` |
| `/ctx-task` | 새 작업 생성(`tasks/` 내 파일 생성) | `git branch` |
| `/ctx-sw` | 작업 전환 및 메모리 로드 | `git checkout` |
| `/ctx-commit` | 현재 진행 상황 중간 저장 | `git commit` |
| `/ctx-list` | 전체 프로젝트/작업 목록 확인 | `git branch -a` |
| `/ctx-done` | 작업 완료 처리 | - |

표준 워크플로우는 `/ctx-project 프로젝트명`으로 시작해서, `/ctx-task 작업명`으로 작업을 만들고, 급한 일이 생기면 `/ctx-sw 다른작업명`으로 즉시 전환하고, 다시 `/ctx-sw 원래작업명`을 입력하면 Claude가 이전 작업 내용을 읽어 즉시 재개하는 흐름이다.

### ✅ 서버단 Context Caching과는 다른 층위의 문제

Anthropic이 서버단에서 제공하는 Context Caching 기능과는 목적이 다르다는 것도 짚어둘 필요가 있다. Context Caching은 질문의 앞부분이 이전과 똑같으면 서버가 그 값을 다시 계산하지 않고 캐시된 값을 재사용하는 방식으로, 반복되는 대용량 텍스트의 입력 토큰 비용을 크게 아껴준다. 다만 일정 시간 질문이 없으면 캐시가 삭제되는 휘발성이 있고, Claude가 스스로 캐시 내용을 수정할 수는 없으며, 중간 내용이 조금만 바뀌어도 그 뒷부분의 캐시는 깨진다.

반면 이 컨텍스트 매니저는 로컬 파일 기반으로 작업의 흐름 자체를 직접 제어한다. 작업을 `tasks/`별로 쪼개 필요한 정보만 골라 전달하고, 로컬 디스크에 영구적으로 남으며, Claude가 직접 `MEMORY.md`를 수정하며 자기 기록을 최신화할 수 있고, 작업 전환을 통해 불필요한 정보 자체를 프롬프트에서 빼버린다. 정리하면 Context Caching은 "기술적인 최적화"이고, 이 컨텍스트 매니저는 "업무 프로세스의 최적화"다 — 둘은 대체 관계가 아니라 같이 쓸 때 시너지가 난다. CLAUDE.md·이력 문서처럼 고정된 내용은 캐싱이 맡고, 지금 작업 중인 파일처럼 매번 바뀌는 내용은 이 매니저가 골라 전달하는 식이다.

### ✅ 결과 & 배운 점

| 항목 | 1세대 | 2세대 |
|------|-------|-------|
| 병렬 작업 | 불가 — 이전 작업 종료해야 새 작업 시작 | 작업별 독립 파일로 병행 가능 |
| 세션 재시작 시 추적 | 어떤 작업 중이었는지 알 방법 없음 | `config.json`이 HEAD(현재 프로젝트/작업)를 기억 |
| 작업 전환 | 수동 복구 필요 | `/ctx-sw` 한 명령으로 전환·복원 |
| 서버 캐싱과의 관계 | 고려 안 됨 | 역할 분리 — 고정 규칙은 캐싱, 가변 작업 맥락은 매니저가 관리 |

정직하게 밝히자면, 2세대 구조에서 언급되는 토큰 절약 수치(전환당 약 27%)는 3일간 2개 병렬 작업이라는 시나리오를 가정해 계산한 추정치이고, 실제 운영 환경에서 장기간 측정해 검증한 값은 아니다. 다만 "세션이 끊겨도 작업 맥락이 로컬 파일로 영구히 남고, Claude가 직접 그 기록을 갱신한다"는 구조 자체는 실제로 구축해서 쓴 방식이었고, 이 원칙(계획은 메모리에, 결과는 파일에 표준 형식으로)은 이후 다른 프로젝트의 `.claude/` 설계에도 그대로 이어졌다.
