> **TL;DR** — AI 하나에게 "분석부터 구현, 배포까지 전부 해줘"라고 하면 컨텍스트가 뒤섞이고 전문성이 희석된다. 그래서 역할을 나눈 여러 서브 에이전트를 팀장 격인 Main이 조율하는 구조를 만들었고, AI가 스스로 판단하면 안 되는 지점(도메인 정책, 내부 정보, 반복 실패)에서는 무조건 멈추고 사람에게 묻도록 Human Gate를 못박았다. 새 기능이 필요할 때도 직접 만들기 전에 이미 있는 도구(ECC)부터 찾아 쓰는 원칙을 세웠다.

### ✅ 상황 — 하나의 AI에게 전부 맡기니 생기던 문제

> 동료 : AutoIt 스크립트 만들고 서버에 배포까지 한 번에 해줘
> 나 : (AI에게 그대로 던짐) → 스크립트 생성 + SSH 배포 코드 + 검증을 AI 혼자 처리

이렇게 맡기면 세 가지 문제가 반복됐다. 배경 설명 + 코드 작성 + 서버 접속이 한 대화 안에서 뒤엉키는 컨텍스트 오염, AI가 잘하는 영역과 못하는 영역이 다른데 하나로 뭉뚱그리면 결과가 평균으로 수렴하는 전문성 희석, 그리고 문제가 생겼을 때 어느 단계에서 잘못됐는지 추적이 안 되는 것. 사람 조직도 분업하는 것처럼 AI도 역할을 나눠야겠다고 판단했다.

### ✅ Main-Sub 오케스트레이터 — 팀장은 조율만, 구현은 팀원이

그래서 세운 구조는 단순하다. **Main(팀장 역할의 AI)은 판단과 조율만 하고 직접 구현하지 않는다.** 요청이 들어오면 "이건 SSH 작업이다", "이건 스크립트 작성이다"처럼 성격을 판단해서 해당 역할의 서브 에이전트에게 위임하고, 서브 에이전트는 받은 작업만 독립된 컨텍스트에서 수행한 뒤 결과를 텍스트로 Main에게 반환한다. Main은 그 결과를 종합해서 사람에게 보고한다.

```
[사용자] → [Main] → 위임 → [Sub A]  →  결과 텍스트 반환  → [Main] → [사용자]
                  → 위임 → [Sub B]  →  결과 텍스트 반환  ↗
        ✗ 금지: Sub A가 Sub B에게 직접 말 거는 것
```

여기서 두 가지를 강제로 못박았다.

- **Sub끼리 직접 소통 금지** — Sub A가 Sub B와 바로 대화하면 Main이 전체 상황을 파악할 수 없고, 문제가 생겨도 어디서 잘못됐는지 추적이 불가능해진다. 모든 소통은 Main을 경유한다.
- **Main의 직접 쓰기 차단** — Main이 실수로 직접 파일을 고치는 걸 막기 위해, develop 브랜치에서 Main이 직접 Write/Edit를 시도하면 훅이 즉시 차단하도록 만들었다. 서브 에이전트만 별도 승인 토큰을 발급받은 뒤에 보호 대상 파일을 편집할 수 있다. 사람이 "이번엔 팀장이 직접 해도 되겠지"라고 착각해서 원칙을 어기는 걸 구조적으로 막아둔 셈이다.

### ✅ 정보는 텍스트로만 흐른다 — 파일로 결과를 넘기지 않는다

처음엔 Sub A가 작업 결과를 `result.md` 같은 파일에 저장하고, Main이 그걸 읽어서 경로를 Sub B에게 넘기고, Sub B가 다시 그 파일을 읽는 방식을 떠올렸다. 그런데 이 방식은 Read/Write 호출이 불필요하게 늘어나고, 파일이 남아서 컨텍스트를 오염시키고, "어느 파일이 최신 버전인가"라는 동기화 문제까지 만든다.

그래서 원칙을 바꿨다. **Sub의 결과는 텍스트로 Main의 메모리에 남고, 필요하면 그 텍스트를 그대로 다음 Sub에게 넘긴다.** 추가 Read/Write가 없고 파일 잔여물도 없다. `temp.md`, `draft.md`, `notes-*.md` 같은 임시 파일을 만들면 나중에 지우는 걸 잊고, 다음 세션에서 AI가 그 파일을 읽어 잘못된 맥락을 가져가는 문제가 생긴다는 걸 이미 겪어봤기 때문에, 세션이 끝나면 이런 임시 파일을 자동으로 정리하는 훅도 같이 붙였다. 계획은 메모리에만, 결과는 텍스트로만 — 이 원칙 하나로 파일 오염 문제 자체를 없앴다.

### ✅ Human Gate — AI가 스스로 멈춰야 하는 조건

AI가 잘하는 일과 못하는 일은 명확히 갈린다. 패턴 인식, 코드 생성, 공개 기술 조사, 반복 작업 자동화는 잘한다. 반면 도메인 정책 판단("왜 우리 팀이 이렇게 했는가"), 내부 기밀 정보 추측, 새로운 비즈니스 요구사항 해석, 책임 있는 최종 결정은 AI가 못한다. 이 경계에서 AI가 추측으로 계속 밀고 나가면 사고가 난다.

그래서 다음 조건에서는 AI가 무조건 멈추고 사람에게 묻도록 정했다.

- 같은 오류가 3회 반복됨
- 계획에 모순이 생김
- 도메인·정책 판단이 필요한 상황
- 내부 정보(접속 정보, 좌표, 자격 증명 등)가 필요한데 없음

실제로 자동화 스크립트를 만들다가 겪은 사례가 좋은 예시다. "특정 프로그램 창을 대상으로 스크립트 만들어줘"라는 요청을 받았을 때, 잘못된 방식은 창 제목을 그럴듯하게 추측해서 스크립트부터 만드는 것이다 — 실제 창 제목이 버전이나 환경마다 다르면 스크립트는 바로 실패한다. 올바른 방식은 "정확한 창 제목이 뭔가요? 버전이나 환경마다 다를 수 있습니다"라고 먼저 물어보고, 확인된 값으로 스크립트를 만드는 것이다. 처음엔 AI가 알아서 해주길 바랐는데 자꾸 멈추니 답답하게 느껴질 수 있다. 하지만 AI가 잘못된 방향으로 계속 가는 것보다, 잠깐 멈추고 물어보는 쪽이 결국 시간을 아낀다 — 도메인 사실을 AI에게 추측하게 하는 건 버그를 심는 것과 같다.

### ✅ 바퀴를 다시 만들지 않는다 — 재사용 우선 원칙

에이전트 구조와 Human Gate를 세운 뒤에도, 새 기능이 필요할 때마다 처음부터 직접 만들 필요는 없었다. 우리 개발 환경에는 이미 전역으로 설치된 확장 도구 모음(에이전트 60여 종 + 자동화 스킬 232여 종 + 슬래시 커맨드 75여 종 + 언어별 코딩 룰셋)이 있었기 때문에, 새 기능이 필요할 때는 항상 이 순서를 따르기로 했다.

1. 이미 있는 도구인가? → 있으면 그대로 호출
2. 기존 도구를 옵션 조정으로 쓸 수 있는가? → 필요한 설정으로 호출
3. 정말 없는가? → 그때야 직접 구현

예를 들어 "백엔드 API 리뷰해줘"라는 요청이 들어오면 Main이 스택을 확인하고 해당 언어·프레임워크에 맞는 기존 리뷰 도구를 호출한다. 직접 리뷰 로직을 새로 짜지 않는다. 반대로 우리 프로젝트에만 있는 도메인 특화 영역(AutoIt 스크립트 작성, SSH 배포 등)은 우리 쪽 전용 에이전트·스킬이 맡는다. 이름이 겹칠 걱정도 없앴다 — 프로젝트 전용 자산에는 접두사를 붙여서, 충돌 시엔 우리 프로젝트 정의가 우선 적용되도록 규칙을 정해뒀다.

### ✅ 결과 & 배운 점

| 항목 | 이전 | 이후 |
|------|------|------|
| 작업 위임 방식 | AI 하나가 분석·구현·배포를 전부 처리 | Main이 판단, 역할별 Sub가 실행, 결과는 텍스트로만 반환 |
| Sub 간 소통 | 직접 소통 시 추적 불가 | Main 경유 강제, Sub↔Sub 직접 소통 금지 |
| 애매한 판단 | AI가 추측해서 진행 → 실패 시 원인 파악 어려움 | 조건 충족 시 Human Gate로 즉시 정지, 사용자 확인 후 진행 |
| 새 기능 필요 시 | 매번 직접 구현 검토 | 기존 도구 확인 → 옵션 조정 → 그래도 없으면 직접 구현 순서 고정 |

역할을 나누고, 멈춰야 할 지점을 미리 정해두고, 이미 있는 걸 먼저 찾는 것 — 셋 다 화려한 기술이 아니라 "AI와 어떻게 일할 것인가"에 대한 절차의 문제였다. 코드를 잘 짜는 것보다, AI가 잘못된 방향으로 갈 여지를 구조적으로 줄여두는 쪽이 장기적으로 훨씬 덜 피곤하다는 걸 이번에 체감했다.
