> **TL;DR** — Setting → 서비스 인증서 → KMS → License 순서로 4개 기능을 한 달 반 만에 붙였다. 순서가 우연이 아니었던 게, 뒤쪽 기능일수록 앞쪽에서 만든 공통 컴포넌트(파일 업로드, 다이얼로그 폼)를 그대로 재사용했다.

### ✅ 상황

> 팀장 : 접근관리 콘솔에 Setting 메뉴 밑에 애플리케이션별 인증서 관리를 넣어야 돼. Next.js standalone 전환하면서 Ingress Nginx가 붙었잖아, 그 인증서를 화면에서 첨부·교체할 수 있어야 함
> 나 : 넵, 우선 Setting 하위 페이지 구조부터 잡고 인증서 붙일게요
> ——— (몇 주 뒤)
> 팀장 : KMS 도 인증·시크릿 콘솔 쪽 화면 참고해서 접근관리 콘솔 안에 만들어줘. 근데 컴포넌트 구조가 달라서 그대로 도킹은 안 되고, 다이얼로그 기반으로 새로 짜야 함
> 나 : API랑 기능은 같은데 페이지냐 다이얼로그냐만 다른 거죠? 구조만 바꿔서 만들게요
> ——— (5월 중순)
> 팀장 : 라이선스도 붙여야 돼. 독립 실행형이니까 파일로 등록·삭제·설정하는 형태로

한 달 반 사이 붙인 기능이 네 개였다. Setting(기타 설정 관리), 서비스 인증서 관리, KMS(Key·Secure Random), License. 이 넷이 다 접근관리 콘솔 안에서 "파일 하나를 다루는 CRUD"라는 공통점이 있어서, 순서를 어떻게 잡았는지가 나중에 코드 재사용에 그대로 영향을 줬다.

### ✅ 왜 이 순서였나

- Setting은 접근관리 콘솔 안에서 "기능 외 기타 설정"을 모아두는 최상위 메뉴였다 — 다른 기능들이 들어갈 자리를 먼저 잡아야 했다
- 서비스 인증서는 Next.js standalone + Ingress Nginx 전환이 배경이었다. Nginx가 앞단에 서면서 인증서를 UI에서 관리할 필요가 생겼고, 사용자가 애플리케이션 단위로 인증서 파일을 첨부·교체하는 게 요구사항이었다
- KMS(Key, Secure Random)는 인증·시크릿 콘솔 쪽에 이미 있는 화면이었지만, 접근관리 콘솔은 컴포넌트 구조 자체가 페이지 기반이 아니라 다이얼로그 기반이라 그대로 가져다 쓸 수 없었다. API와 기능은 동일, 화면 골격만 새로 구현하는 작업이었다
- License는 독립 실행형 소프트웨어를 위한 로컬 라이선스 기능이었다. 기존엔 쿠버네티스 환경에서 수동으로 업로드하던 걸, 다이얼로그에서 라이선스 정보 조회·교체·삭제·설정까지 되도록 화면으로 끌어올리는 작업이었다

정리하면 "설정 골격 → 파일 첨부형 관리 기능(인증서) → 구조가 다른 기존 기능의 포팅(KMS) → 새 파일 처리 패턴(라이선스)" 순으로, 뒤로 갈수록 난이도가 조금씩 올라가는 흐름이었다.

### 🛠️ 서비스 인증서 — 파일 전송 포맷부터 잡기

인증서 UI 자체는 하루 만에 뼈대를 잡았다(`feat: 인증서 페이지 UI 구현 (API x)`). 문제는 그다음이었다. API를 연결하면서 파일 전송 포맷과 path 규칙을 서버와 맞추는 데 시간이 더 들었다.

```
2025-04-10  feat: 인증서 페이지 UI 구현 (API x)
2025-04-16  feat: 인증서 api 연결 (조회 확인, 수정 추가는 파일업로드 후 확인예정)
2025-04-17  feat: 인증서 파일 전송 시 데이터 포멧 추가, path 포멧 추가
2025-04-25  fix: 인증서 첨부시 md5 오류 해결(path -> value)
2025-04-25  feat: certificate name 필드 textbox 에서 select box 로 변경
```

특히 `md5 오류` 커밋이 기억에 남는다. 처음엔 인증서 파일 경로(`path`)를 그대로 전송했는데, 서버가 기대하는 건 파일 내용 자체(`value`)였다. 파일이 크지 않으니 경로만 넘기면 서버가 알아서 읽을 거라 생각했던 게 착각이었다 — 클라이언트·서버 어느 쪽이 파일을 실제로 읽어서 들고 있어야 하는지에 대한 합의가 빠져 있었던 거다.

또 하나는 `certificate name` 필드를 텍스트박스에서 셀렉트박스로 바꾼 것. 사용자가 애플리케이션 이름을 직접 타이핑하게 두면 오탈자·중복이 생기기 쉬웠고, 어차피 인증서는 이미 등록된 애플리케이션에 붙는 것이므로 목록에서 고르는 게 맞는 UX였다.

### 🛠️ KMS — 같은 API, 다른 화면 구조

KMS는 "페이지 기반 인증·시크릿 콘솔"을 "다이얼로그 기반 접근관리 콘솔"로 이식하는 작업이었다. API 스펙은 동일했기 때문에 여기서 순수하게 다른 건 컴포넌트 트리뿐이었다.

- 인증·시크릿 콘솔: `/kms/keys` 같은 독립 라우트 → 페이지 전체가 KMS 화면
- 접근관리 콘솔: 다른 메뉴 안에서 다이얼로그를 열면 그 안에 KMS 리스트·상세가 들어가는 구조

<!-- 이미지 제안: 인증·시크릿 콘솔(페이지 기반)과 접근관리 콘솔(다이얼로그 기반)의 KMS 화면 구조 비교 다이어그램 -->

같은 API를 감싸는 dialog wrapper를 새로 짜야 했는데, 이 작업이 뒤에 이어지는 "KMS를 계속 자체 구현할 것인가"라는 더 큰 질문으로 이어졌다. 그 이야기는 다음 글에서 자세히 다룬다.

### 🛠️ License — 다건 파일을 버퍼로 스트림 전송

라이선스는 파일 전송 방식이 인증서와 결이 달랐다. 인증서는 단건이었지만 라이선스는 다건 파일 전송이 요구사항에 있었고, 여기서 결정한 게 "디스크에 저장하지 않고 버퍼에 조금씩 담아 스트림 전송"하는 방식이었다.

```
h2. 요청 기능 시나리오
- 다이얼로그로 라이센스 정보 표시, 교체 삭제 가능, 설정 정보 창 제공
- 다건 파일 전송 시 디스크에 저장하지 않고 조금씩 버퍼에 담아 스트림전송

h2. 고려사항
- 파일 전송 시 대기사항 고려(백프레서)
```

다건 파일을 한 번에 메모리에 올리면 파일 크기·개수에 따라 문제가 생길 수 있어서, 스트림 + 백프레서를 고려사항으로 명시해뒀다. 실제 구현에서는 이 부분이 완전히 정교하게 들어가진 못했지만("설정 필드 데이터 유효성 수정" 등 후속 커밋이 이어졌다), 적어도 "다건 파일은 통째로 들고 있지 않는다"는 원칙만은 처음부터 잡고 시작했다.

### ✅ 진행 순서 요약

1. Setting — 기타 설정 메뉴 골격
2. 서비스 인증서 — 파일 첨부/전송 포맷 정립(path→value, textbox→selectbox)
3. KMS — 동일 API를 다이얼로그 구조로 이식
4. License — 다건 파일 스트림 전송 + 상태 계산 로직

#### 🎯 결과

| 기능 | 이전 | 이후 |
|---|---|---|
| 서비스 인증서 | 인증서 경로(path)를 그대로 전송 → md5 오류, 이름을 텍스트박스로 직접 입력 | 파일 값(value) 전송으로 수정, select box로 애플리케이션 선택 |
| KMS | 인증·시크릿 콘솔에만 페이지 기반으로 존재 | 접근관리 콘솔 다이얼로그 구조로 동일 API 이식 |
| License | 쿠버네티스 환경에서 수동 업로드 | 다이얼로그에서 조회·교체·삭제·설정 가능 |

네 기능 모두 "파일을 다루는 CRUD"라는 공통 축을 갖고 있었고, 순서를 앞에서부터 밟아가면서 파일 업로드·다이얼로그 폼 패턴이 자연스럽게 다듬어졌다. 다만 KMS는 이 뒤로 예상치 못한 방향 전환을 겪는다 — 자체 구현을 계속하다가 결국 다른 콘솔로 연결하는 쪽으로 접었는데, 그 판단 과정은 다음 글에서 다룬다.
