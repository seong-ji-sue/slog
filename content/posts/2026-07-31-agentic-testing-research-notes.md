> **TL;DR** — AI 에이전트가 기존 E2E 테스트를 대체할 수 있는지 궁금해서 Slack 엔지니어링팀(Sergii Gorbachov)이 정리한 200건 이상의 실험 자료를 조사·정리했다. 결론은 "대체가 아니라 보완"이다. 에이전트는 테스트 피라미드의 최상단에서 탐색·디버깅·복잡한 동작 검증을 담당하고, 결정론적 테스트는 여전히 CI의 기반층을 맡는다. 인프라(도구 선택)가 모델 선택보다 신뢰성과 비용에 더 큰 영향을 준다는 점이 개인적으로 가장 인상 깊었다.

### ✅ 왜 이 자료를 찾아봤나

우리 프로젝트에서도 E2E 검증에 AI 에이전트(Playwright MCP 기반)를 쓰고 있는데, "이게 기존 결정론적 테스트를 완전히 대체할 수 있는 물건인가, 아니면 보완재인가"가 궁금했다. Slack 엔지니어링팀이 이 질문에 대해 200건 이상의 실행 실험을 돌려서 정리한 자료가 있어서 조사해봤다.

### ✅ 패러다임 전환 — 여정에서 목표로

| 구분 | 전통적 테스트 | 에이전틱 테스트 |
|------|--------------|----------------|
| 동작 방식 | 클릭 → 입력 → 단언(assert)의 정해진 순서 | UI 상태를 관찰하고 추론해 행동 선택 |
| 검증 대상 | 정해진 UI 경로(여정) | 목표 달성 여부 |
| 예시 | "버튼 A 클릭, 필드 B 입력, 텍스트 C 확인" | "스레드에 답글을 남겨라" |
| 경로 | 항상 동일 | 적응적 — 실행의 약 80%가 다른 경로 |

동일한 목표라도 에이전트는 서로 다른 입력 방식, 탐색 패턴, 단계 조합으로 도달한다. 사람처럼 "여러 유효한 길" 중 하나를 그때그때 찾아내는 셈이다.

### ✅ 실험 설계 — 세 가지 실행 방식

1. **Agent + Playwright MCP** — 사전 정의된 브라우저 도구(Model Context Protocol)로 상호작용하며 실시간 DOM/접근성 트리 스냅샷을 유지
2. **Agent + Playwright CLI** — 셸 명령으로 한 단계씩 처리, 매 단계 상태를 재구성
3. **Generated Playwright Tests** — AI가 테스트 코드를 생성해 결정론적으로 실행

모델은 Claude Sonnet 4.5·Opus 4.6, 테스트 플로는 단순(Thread Reply, 15~20단계)과 중간 복잡도(Search Discovery, 25~30단계)로 나눠 각 구성당 20회씩 반복 실행했다.

### ✅ 신뢰성 — 실패율

| 방식 | 단순 플로 | 복잡 플로 |
|------|-----------|-----------|
| Playwright MCP | 0% | ~12% |
| Playwright CLI | ~12% | ~20% |
| Generated Tests | ~8% | ~48% |

MCP 방식이 가장 안정적이었다 — 특히 복잡한 플로에서 격차가 크게 벌어졌다. CLI 실패는 대부분 추론 오류가 아니라 인증·타이밍·세션 불안정 같은 실행 계층(infrastructure) 문제에서 발생했다는 점이 눈에 띈다. 생성 테스트는 단순 플로엔 무난하지만 복잡도가 오르면 48%까지 급격히 악화됐다.

### ✅ 속도와 비용 — 인프라가 모델보다 중요하다

속도는 Generated Tests(생성 포함 약 3분, 순수 실행은 32~45초)가 가장 빨랐고, MCP는 5~8분, CLI는 9~11분이 걸렸다. 생성 테스트는 한 번 만들어두면 반복 실행의 일회성 생성 비용이 무시할 수준이 되는 반면, 에이전트 방식은 매 실행마다 "관찰 → 추론 → 실행" 사이클의 고정 오버헤드가 붙는다.

비용은 회당 $15~30로 전통 테스트 대비 훨씬 비쌌다. 토큰 소비는 MCP(~3.5~3.8M) < CLI(~6M) < Code Gen(~7M) 순이었고, 턴 수도 MCP가 40~60턴으로 CLI(85턴 이상)보다 적었다. 비용의 주범은 추론 자체가 아니라 컨텍스트 재전송이었다 — 매 턴마다 전체 시스템 프롬프트·대화 이력·브라우저 스냅샷·에러 트레이스가 누적 전송된다. 즉 **실행 방식(인프라)이 모델 선택보다 비용·신뢰성에 더 큰 영향을 미친다**는 게 이 실험의 핵심 발견이다. MCP는 접근성 트리를 응답 스냅샷으로 반환하며 브라우저와 긴밀히 통합돼 세션 내 상태를 효과적으로 유지하는 반면, CLI는 매 단계 추가 계층을 거쳐 상태를 재구성하다 보니 작은 UI 해석 오차가 누적되며 플로가 길수록 신뢰성이 떨어진다.

### ✅ 테스트 피라미드에서의 자리

```
[  에이전틱 테스팅  ]  ← 최상단: 복잡한 UI 동작 탐색, flaky 워크플로 디버깅, 프로덕션 버그 재현
[     E2E      ]
[    통합       ]      ← 결정론적 E2E(기반층): CI에서 빠르고 반복 가능한 회귀 검사
[    단위       ]
```

결정론적 E2E 테스트는 CI에서 빠르고 반복 가능한 회귀 검사, 낮은 운영 비용, 특정 UI 여정을 강제하는 데 적합하다. 에이전틱 테스팅은 복잡한 UI 동작 탐색, 불안정한(flaky) 워크플로 디버깅, 프로덕션 버그 재현처럼 비용이 높은 대신 표적 디버깅·탐색적 테스트에 강점이 있다.

### ✅ 결론 — 대체가 아니라 결합

- 에이전트는 기존 테스트를 대체가 아닌 보완한다
- 인프라/실행 환경이 모델 선택만큼 중요하다(MCP > CLI)
- "목표 기반 검증"은 유연하지만 비용·재현성 트레이드오프를 동반한다(동일한 동작 순서를 그대로 따른 실행은 약 20%에 불과)
- 비용은 추론보다 컨텍스트 재전송이 주범 — 캐싱·압축으로 절감 여지가 크다
- 크로스 워크스페이스·다중 창 플로는 추가 검증이 필요하다는 게 원문의 유보 사항이다

현재의 비용($15~30/회)과 시간(5~11분)을 보면 고빈도 CI 실행보다는 표적 디버깅·탐색적 워크플로에 적합하다는 결론이 실무적으로 가장 와닿았다. 가장 효과적인 전략은 결정론적 테스트로 CI의 안정적 토대를 만들고, 에이전틱 테스팅으로 피라미드 최상단의 탐색·복잡 검증을 담당하는 결합 방식이라는 것.
