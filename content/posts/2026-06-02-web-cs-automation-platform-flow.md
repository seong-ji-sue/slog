> **TL;DR** — WEB 자동화 앱과 CS 자동화 앱을 계속 만들다 보니, "사용자가 아이콘을 클릭한 뒤 실제로 무슨 일이 일어나서 내 AutoIt 스크립트까지 실행되는가"를 문서가 아니라 로그로 직접 추적해봤다. 두 타입은 Bastion 할당·RDP 연결까지는 같은 경로를 타고, 그 이후 WEB은 프록시 릴레이로, CS는 화면 캡처 감사 채널로 갈라진다는 걸 서버별 로그 마커를 대조하며 확인했다.

난이도 : ★★★★☆

1️⃣ `WEB/CS 공통 경로` 2️⃣ `로그 기반 흐름 검증` 3️⃣ `분기 지점 특정`

### ✅ 요구사항

> 선임 : WEB이랑 CS 둘 다 스크립트는 잘 붙였는데, 정작 플랫폼이 내부적으로 어떻게 연결해주는 건지는 제대로 안 봤지?  
> 나 : 문서로는 대충 아는데 로그로 실제 흐름을 확인한 적은 없네요  
> 선임 : 새 앱 붙일 때마다 이상 현상 나오면 결국 이 흐름을 알아야 어디가 문제인지 짚을 수 있어  
> 나 : 각 서버 로그 다 뒤져서 실제 순서대로 맞춰보겠습니다

WEB·CS 앱스크립트를 여러 개 붙이면서 "접속은 되는데 이 단계에서 막힌다"는 이슈를 몇 번 겪었다. 그런데 그때마다 어느 컴포넌트가 문제인지 감으로 짚고 있었다는 걸 깨달았다. 그래서 한 번 제대로, 사용자가 아이콘을 클릭하는 순간부터 AutoIt 스크립트가 실행되기까지 전체 경로를 각 서버의 로그를 따라가며 문서화하기로 했다.

### ✅ 공통 경로 — 클릭부터 RDP 연결까지

WEB이든 CS든, 아이콘 클릭 이후 RDP 세션이 붙기까지는 같은 경로를 탄다.

1. 사용자가 클라이언트에서 앱 아이콘 클릭
2. 클라이언트가 API 서버에 접속 정보 요청
3. API 서버가 로드밸런서(LB)에 Bastion 서버 할당을 요청 — LB는 각 Bastion의 생존 여부를 주기적으로 핑(ping)해서 파악해두고 있다가 배정한다
4. LB가 할당된 Bastion의 정책관리 컴포넌트(policy-mgr)에 일회용 랜덤 비밀번호 변경을 요청 — 매번 새 비밀번호로 세션을 여는 구조다
5. policy-mgr이 변경 완료 후 LB에 응답 → LB가 API 서버에 최종 접속 정보(포트·계정) 전달
6. 클라이언트가 mstsc(원격 데스크톱)를 백그라운드로 실행해 Bastion의 RDS 커넥터와 RDP 세션을 맺는다
7. RDS 커넥터가 policy-mgr에 "이 세션에서 뭘 허용할지"(통제 정책)를 요청
8. policy-mgr이 API 서버와 정책을 교환 — 이 응답에 "이번 세션에서 실행할 앱이 무엇인지", "AutoIt 스크립트 경로가 어디인지"가 함께 담겨 온다
9. policy-mgr이 프로세스 감시 컴포넌트에 비인가 프로그램 차단 정책을 등록

여기까지는 WEB이든 CS든 로그 상에서 완전히 같은 순서로 나타난다. 실제로 policy-mgr 로그에 찍히는 정책 응답 한 줄 안에 이번 세션에서 실행할 앱 이름과 AutoIt 스크립트 경로, 화면 캡처 전송 서버 주소까지 같이 내려오는 걸 확인했는데, 이 한 줄만 봐도 "이 세션이 뭘 하려고 붙었는지"를 재구성할 수 있었다.

### ✅ 분기 지점 — WEB은 프록시 릴레이로, CS는 화면 캡처 감사로

공통 경로가 끝나는 지점부터 WEB과 CS가 갈라진다.

**WEB 전용 경로**
- Bastion의 웹 커넥터가 릴레이 서버에 인증 채널을 연다
- 릴레이 서버가 사용자 웹 트래픽을 허용된 목적지로 프록시 중계한다 — SSL 연결이 수립되면서 실제 접속 도메인(SNI)이 로그에 그대로 남기 때문에, "이 세션이 실제로 어느 사이트에 붙었는지"를 로그만으로 확인할 수 있다
- Bastion에서 Chrome을 띄우고 WEB용 AutoIt 스크립트가 실행된다

**CS 전용 경로**
- Bastion의 CS 커넥터가 화면 캡처 서버(gui-logger)에 SSL로 접속해서, 이 세션의 화면을 실시간으로 감사 서버에 스트리밍하기 시작한다
- 이후 지정된 CS 애플리케이션이 실행되고, CS용 AutoIt 스크립트가 계정 정보를 자동 입력해 로그인을 완료한다
- 로그인 결과(성공 시 0)가 policy-mgr에 전달되는 것으로 이 단계가 끝난다

같은 "앱 실행"이라도 WEB은 트래픽을 프록시로 흘려보내는 구조라 목적지가 로그에 SNI 값으로 남고, CS는 애초에 화면 자체를 캡처해서 감사 서버로 흘려보내는 구조라 접근 통제와 별개로 "무엇을 했는지"까지 기록에 남는다는 차이가 있었다. WEB 자동화 스크립트를 짤 때는 이 프록시 계층이 도메인 단위로 화이트리스트를 걸고 있다는 걸 전제해야 했고, CS 자동화 스크립트를 짤 때는 화면 캡처 연결이 먼저 붙어야 정상 흐름이라는 걸 전제해야 했다.

### ✅ 로그를 계층별로 나눠서 봐야 하는 이유

이번에 로그를 따라가면서 확인한 건, 문제가 생겼을 때 "어디를 봐야 하는가"가 계층마다 다르다는 점이었다.

| 계층 | 확인할 로그 | 확인 가능한 것 |
|------|-------------|----------------|
| API 서버 ↔ LB | LB 로그 | Bastion 가용 상태, 접속 정보 전달 여부 |
| LB ↔ policy-mgr | Bastion의 정책관리 로그 | 비밀번호 변경·정책 응답 성공 여부 |
| 클라이언트 ↔ Bastion | Bastion의 RDS 커넥터 로그 | RDP 세션 수립 여부, 실행 대상 앱·스크립트 경로 |
| WEB 전용 | 릴레이 서버 로그 | 실제 접속 도메인(SNI), 프록시 연결 성공 여부 |
| CS 전용 | Bastion의 CS 커넥터 + 캡처 서버 로그 | 화면 감사 채널 연결 여부, AutoIt 로그인 결과 |

새 앱을 붙이다가 "접속은 되는데 이 앱만 뭔가 이상하다"는 문제가 생기면, 이 표를 기준으로 어느 계층 로그부터 봐야 할지 바로 좁힐 수 있게 됐다. 예전에는 문제가 생기면 이 로그 저 로그 다 열어보면서 감으로 찾았는데, 이제는 "RDP까지는 됐는데 앱이 안 뜬다"면 RDS 커넥터 로그의 정책 응답 구간부터, "화면은 뜨는데 접속 사이트가 이상하다"면 릴레이 서버 로그의 SNI 값부터 보면 된다는 게 명확해졌다.

### ✅ 결과 & 배운 점

| 항목 | 이전 | 이후 |
|------|------|------|
| 플랫폼 내부 흐름 이해 | 문서 수준(대략적인 이해) | 서버별 로그 대조로 실제 흐름 검증 완료 |
| WEB/CS 분기 지점 | 막연히 "다르다"만 인지 | 정책 응답 이후 프록시 릴레이 vs 화면 캡처 감사로 명확히 특정 |
| 장애 대응 방식 | 로그 여러 개를 감으로 확인 | 계층별 로그 매핑표 기준으로 문제 구간 우선 특정 |

앱스크립트 자체를 아무리 잘 짜도, 그 스크립트가 실행되기까지의 플랫폼 내부 경로를 모르면 장애가 났을 때 원인을 좁히는 데 시간이 오래 걸린다는 걸 이번에 체감했다. 특히 "이 앱만 이상하다"는 이슈는 스크립트 버그가 아니라 이 흐름 어딘가의 계층 문제일 때가 많았다 — 로그를 순서대로 따라가며 실제 흐름을 검증해두는 작업이, 다음에 비슷한 이슈가 터졌을 때 원인 좁히는 속도를 결정한다는 걸 배웠다.
