> **TL;DR** — Namespace 생성/삭제 진행 로그를 SSE로 받는데, 처음엔 "이벤트가 순서대로 온다"고 가정하고 짰다가 실제로는 비순차적으로 도착한다는 걸 뒤늦게 알았다. 백엔드를 못 건드리는 상황에서, Frontend와 Backend 사이에 있는 BFF(Node.js)가 이벤트를 순서에 맞게 재정렬해서 내려주는 구조로 바꿔 해결했다.

> 나 : (며칠 뒤) 팀장님, 이벤트가 순서대로 안 옵니다... 상태 A 다음에 B가 와야 하는데 B가 먼저 뜨는 경우가 있어요

이전 편(Namespace 관리 화면)에서 "생성/삭제 요청 접수 후 폼을 닫고 로그창을 연다"는 흐름까지 잡았다. 이 로그창 내부에서 실제로 진행 상태를 어떻게 실시간으로 보여줄지가 이번 주제다.

### ✅ 왜 폴링이 아니라 SSE인가

Namespace 생성/삭제는 여러 단계(리소스 할당 → 초기화 → 권한 설정 → 완료)를 거치는 백엔드 작업이라, 진행 상태를 몇 초 간격으로 다시 물어보는 폴링 방식도 가능은 했다. 하지만 단계가 늘어날수록 폴링 주기와 실제 상태 변화 시점이 어긋나는 문제가 있었고, 서버 입장에서도 불필요한 조회 요청이 계속 쌓이는 구조였다. 그래서 서버가 상태 변화를 이벤트로 흘려주는 SSE(Server-Sent Events)를 붙이기로 했다 — 커넥션 하나만 열어두면 서버가 상태 바뀔 때마다 알아서 밀어주는 구조라 폴링보다 훨씬 자연스러웠다.

### ❌ 처음 가정 — "이벤트는 순서대로 온다"

React 쪽에서 SSE 커넥션을 열고 Node.js(BFF)가 이걸 중계하는 구조 자체는 빠르게 붙었다. 문제는 그다음이었다. 처음엔 "백엔드가 보내는 상태 이벤트는 프로비저닝 단계 순서대로 도착한다"고 가정하고 화면 로직을 짰다 — 이벤트를 받는 순서 그대로 로그에 쌓고, 마지막 이벤트의 상태를 최종 상태로 반영하는 단순한 구조였다.

실제로 연동해보니 이 가정이 깨졌다. 네트워크 계층(로드밸런서, 프록시)을 거치면서 이벤트 도착 순서가 뒤바뀌는 경우가 있었고, 최악의 경우 "삭제 완료" 이벤트가 "삭제 진행중" 이벤트보다 먼저 도착해서 화면이 잠깐 완료로 표시됐다가 다시 진행중으로 되돌아가는 버그가 났다. 백엔드 쪽 이벤트 발행 순서를 프론트가 통제할 수 없는 상황이라, 프론트에서 오는 순서를 그대로 믿는 방식은 쓸 수 없었다.

### ✅ 왜 백엔드에서 바로 안 주고 BFF를 거치는가

여기서 나온 질문이 "그럼 백엔드에서 이벤트를 순서 보장해서 보내주면 안 되나"였는데, 백엔드 쪽 이벤트 발행 구조를 이번 주기에 바꾸는 건 범위 밖이었다. 그래서 백엔드는 그대로 두고, 프론트와 백엔드 사이에 이미 존재하던 BFF(Node.js) 계층에서 이벤트를 재정렬해 내려주는 쪽으로 방향을 잡았다.

BFF를 거치는 구조가 이 문제에서 유리했던 이유는 세 가지다.

- 프론트(React)는 브라우저 환경이라 이벤트를 오래 붙잡아두고 순서를 재구성하는 로직을 넣기엔 상태 관리가 무거워짐 — 탭을 새로고침하면 버퍼가 날아감
- 백엔드는 여러 클라이언트를 상대하는 공용 계층이라 이벤트 단위 순서 보정 책임을 지우면 다른 기능에도 영향이 감
- BFF는 이 화면 하나만을 위한 중계 계층이라, "시퀀스 번호 기준으로 정렬한 다음 순서대로 클라이언트에 흘려보낸다"는 책임을 여기에 둬도 다른 곳에 영향이 없음

즉 "백엔드 이벤트 발행 로직 변경 없이, 프론트 상태 관리도 무겁게 하지 않으면서" 문제를 풀 수 있는 지점이 BFF였다.

### ✅ 구현 — BFF에서 이벤트 재정렬

백엔드가 보내는 각 이벤트에는 시퀀스 번호(또는 타임스탬프)가 있었기 때문에, BFF에서 짧은 버퍼를 두고 순서를 맞춘 다음 클라이언트로 릴레이하는 구조로 바꿨다.

```js
// bff/namespaceLogRelay.js
function createOrderedRelay(clientRes) {
  let nextSeq = 0;
  const buffer = new Map(); // seq -> event

  function flush() {
    while (buffer.has(nextSeq)) {
      const event = buffer.get(nextSeq);
      clientRes.write(`data: ${JSON.stringify(event)}\n\n`);
      buffer.delete(nextSeq);
      nextSeq += 1;
    }
  }

  return function onBackendEvent(event) {
    buffer.set(event.seq, event);
    flush(); // 뒤에 온 seq는 buffer에 쌓아두고, 앞 seq가 채워지면 한꺼번에 흘려보냄
  };
}
```

프론트(React)는 이제 "BFF가 보내주는 순서 = 실제 순서"라고 신뢰할 수 있게 됐고, 화면 쪽 로직은 원래 짰던 단순한 형태(받은 순서대로 로그에 쌓고 마지막 상태를 반영)로 되돌릴 수 있었다.

```jsx
// NamespaceLogDialog.js
useEffect(() => {
  const es = new EventSource(`/api/namespace/${id}/log-stream`);
  es.onmessage = (e) => {
    const event = JSON.parse(e.data);
    setLogs((prev) => [...prev, event]); // BFF가 이미 순서 보장했으므로 그대로 append
  };
  return () => es.close();
}, [id]);
```

### ✅ 결과 & 배운 점

- "백엔드 이벤트는 순서대로 온다"는 가정은 로컬 테스트 환경에서만 성립했다 — 실제 배포 환경(로드밸런서·프록시를 거치는 경로)까지 검증하지 않고 넘어간 게 원인이었다
- 순서 보장 책임을 프론트도 백엔드도 아닌 BFF로 가져온 결정이 핵심이었다. "이 요청 흐름만을 위해 존재하는 중간 계층"이 있으면, 그 계층에 좁은 책임 하나를 추가하는 게 가장 부작용이 적다
- 이후 이 재정렬 로직은 Namespace 로그 리팩토링 때 리스트 API가 중복 호출되던 버그를 잡으면서 한 번 더 정리됐다 (다이얼로그가 열릴 때마다 SSE 연결과 리스트 조회가 각각 따로 트리거되던 문제)
