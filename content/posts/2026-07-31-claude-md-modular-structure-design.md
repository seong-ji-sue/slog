> **TL;DR** — 하나의 거대한 CLAUDE.md에 모든 규칙과 참조 문서를 다 담아뒀더니, AI가 매 요청마다 관련 없는 내용까지 전부 읽어서 예상보다 몇 배 더 많은 토큰을 쓰고 있었다. CLAUDE.md는 가벼운 인덱스(500줄)로만 남기고 상세 규칙·이력·참조 문서는 역할별 폴더로 쪼갠 다음, 필요한 파일만 그때그때 로드하도록 구조를 다시 짰다. 팀원끼리 작업 이력이 공유되지 않던 문제도 이 구조 안에서 같이 해결했다.

### ✅ 문제 — 과금 폭탄과 공유 안 되는 히스토리

여러 모듈로 이뤄진 사내 플랫폼 프로젝트를 Claude Code로 다루면서 두 가지 문제가 동시에 터졌다. 하나는 **과금 폭탄**이었다 — 프로젝트 전체 모듈을 매번 통째로 로드하는 구조라, 실제 예상 대비 3~5배의 토큰을 소비하고 있었다. 다른 하나는 **히스토리 공유 부재**였다 — 팀원 간 작업 내용이 공유되지 않아 같은 질문이 반복되고, 인수인계할 때마다 처음부터 다시 설명해야 했다.

여기에 더해서 레거시 프론트엔드 프레임워크의 레퍼런스 문서 하나가 4,240줄에 달했는데, 이걸 뭔가 참조할 때마다 매번 통째로 읽는 것도 비효율의 큰 축이었다.

### ✅ 해결 1 — CLAUDE.md는 인덱스로, 상세는 역할별 폴더로

핵심 방향은 단순하다. 하나의 CLAUDE.md(수만 줄)에 규칙·이력·참조를 전부 우겨넣는 대신, **역할별로 파일을 쪼개서 필요한 것만 선택적으로 로드**하게 만드는 것이다.

```
CLAUDE.md                       # 500줄 — 가벼운 인덱스 역할만
.claude/
├── rules/          # 파일명 규칙, 코딩 규칙 등
├── skills/         # 명령어 정의
├── modules/        # 모듈 정보(modules.json)
└── reference/      # 레거시 프레임워크 참조 문서
```

CLAUDE.md 자체에는 "답변은 간결체로, 코드 언어는 Java" 같은 기본 규칙만 남기고, 상세 규칙은 `.claude/rules/coding.md`처럼 링크로만 걸어둔다. AI는 일반 작업에서 이 500~600줄짜리 인덱스만 읽고, 정말 필요할 때만 링크를 따라 상세 문서를 읽는다. 문서 크기 기준으로 계산하면 기존 방식(약 20,000줄 전체 로드) 대비 500줄만 읽으면 되니 로드되는 분량 자체가 97% 가까이 줄어드는 구조다 — 다만 이건 문서 크기(줄 수) 기준 구조적 절감률이고, 실제 토큰 사용량을 별도 벤치마크로 재서 검증한 수치는 아니다. 규칙이 바뀔 때도 해당 파일 하나만 고치면 되니 유지보수도 파일 단위로 독립적으로 할 수 있게 됐다.

### ✅ 해결 2 — 팀원 간 작업 이력 공유를 위한 표준 메모리 구조

두 번째 문제(히스토리 공유 부재)는 각 모듈마다 동일한 형식의 메모리 폴더를 두는 방식으로 풀었다.

```
[모듈명]/.claude/memory/
├── features.md        # 완료된 기능 목록(테이블)
├── job_history.md      # 작업 이력 누적 + 실패했던 시도 기록
├── decisions.md        # 설계 결정과 그 이유
├── env_setup.md        # 환경 설정 기록
├── tech_reference.md   # 기술 참조
└── current_task.md     # 진행 중인 작업(있으면 "누군가 지금 작업 중"이라는 신호)
```

이렇게 표준화해두면, 세션이 끊기거나 다른 팀원이 같은 모듈을 열었을 때 `current_task.md`가 있는지만 봐도 "누가 지금 여기 작업 중이구나"를 바로 알 수 있고, `job_history.md`를 보면 이전에 뭘 시도했다가 실패했는지까지 파악할 수 있다. git pull 받고 다시 세션을 열면 다른 팀원이 작업하던 지점부터 이어갈 수 있게 하는 게 목표였다.

### ✅ 해결 3 — 큰 참조 문서는 인덱싱해서 필요한 구간만 읽기

4,240줄짜리 레거시 프레임워크 레퍼런스 문서는 통째로 읽는 대신, 섹션별 위치(오프셋/길이)를 별도 인덱스 파일에 기록해두고 필요한 섹션만 그 위치로 콕 집어 읽는 방식으로 바꿨다. 사용자가 "이 컴포넌트 사용법 알려줘"라고 물으면, AI는 먼저 인덱스에서 관련 섹션의 위치를 찾고, 그 구간(약 200~300줄)만 읽어서 답한다 — 4,240줄을 매번 다 읽던 것과 비교하면 훨씬 적은 분량만 읽는 셈이다.

여기에 더해서 인덱스에 없는 정보를 코드 분석 중에 새로 발견하면, 그 즉시 별도 스테이징 문서에 짧게(제한된 줄 수 안에서) 기록해두고, 주기적으로 정식 참조 문서에 병합하는 흐름도 함께 설계했다. 문서에 없는 지식이 발견될 때마다 그 자리에서 유실되지 않도록 만드는 장치다.

### ✅ 결과 & 배운 점

| 항목 | 이전 | 이후 |
|------|------|------|
| CLAUDE.md 구조 | 단일 문서에 전체 규칙·이력·참조 혼재 | 500줄 인덱스 + 역할별 폴더(rules/skills/reference) 분리 |
| 매 요청 로드량 | 프로젝트 전체 모듈 통째로 로드 | 필요한 파일만 선택적으로 로드 |
| 팀원 간 이력 공유 | 공유 안 됨, 매번 재설명 필요 | 모듈별 표준 memory 폴더(features/job_history/decisions 등)로 공유 |
| 대용량 참조 문서 | 4,240줄 통째로 매번 읽음 | 인덱스로 위치만 찾아 필요한 구간(약 200~300줄)만 읽음 |

숫자로 된 절감률(97%, 95%)은 설계 시점에 문서 크기를 기준으로 계산한 구조적 추정치이지, 실제 운영 중 토큰 사용량을 재서 검증한 값은 아니라는 점은 정직하게 밝혀둔다. 다만 "필요한 것만 골라 읽는 구조"로 바꿨다는 사실 자체는 실제로 적용된 구조 변경이고, 이 방향 자체는 이후 다른 프로젝트의 `.claude/` 구조를 설계할 때도 그대로 가져다 썼다.
