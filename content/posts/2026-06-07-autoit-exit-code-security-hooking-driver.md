> **TL;DR** — 베스천에 AutoIt 스크립트를 자동으로 올리고 빌드하고 실행하는 파이프라인을 짜려는데, SSH 로그인은 되는데 명령 한 줄이 실행되지 않는 문제를 만났다. 원인은 코드가 아니라 사내 보안 접근제어의 커널 후킹 드라이버가 SSH 세션을 가로채 감사 프록시로 우회시키고 있었기 때문이었다. 같은 조사 과정에서 AutoIt 스크립트 자체의 종료 코드 처리에도 버그가 있다는 걸 발견해서 같이 정리했다.

### ✅ 요구사항

> 나 : 맥에서 코드로 베스천에 SSH 붙어서 AutoIt 스크립트 업로드·빌드·실행까지 자동화하려고 합니다  
> 선임 : 좋네, 근데 우리 사내 보안 정책 켜져 있는 상태에서도 되는지 확인해봐  
> 나 : ...로그인은 되는데 명령이 하나도 안 먹네요. 원인부터 파보겠습니다

이전 글([paramiko의 배신](/posts/paramiko-native-ssh-migration))에서 다룬 건 백엔드 서버가 여러 사내 장비에 SSH로 붙을 때 겪은 문제였다. 이번은 결이 다르다 — 이번엔 내 개발 머신(맥) 하나가 베스천 서버 하나에 AutoIt 스크립트를 자동으로 올리고 빌드까지 하려는 상황에서 생긴 문제였고, 원인도 다른 층위에 있었다.

### ✅ 후킹 드라이버란 무엇인가

사내 원격 접속 통제 솔루션은 putty·DBeaver 같은 원격 접속 도구로 서버에 붙을 때, 등록된 대상이면 그 세션을 커널 레벨에서 가로채서(후킹) 감사·통제 시스템을 경유시키는 드라이버를 클라이언트에 심어둔다. 목적은 "누가 어느 서버에 붙어서 뭘 했는지"를 통제 시스템이 중간에서 감시·기록할 수 있게 하는 것이다.

- **드라이버**: OS와 장치가 통신하도록 매개하는, 커널의 일부로 동작하는 프로그램
- **후킹**: 함수 호출·메시지·이벤트를 중간에서 가로채거나 바꾸는 기술
- 이 드라이버가 활성화된 상태에서 원격 접속 도구를 실행하면, 실제 목적지 서버가 아니라 감사 시스템의 프록시를 거쳐 접속된다 — 사람이 화면을 보면서 하는 접속은 이 경로로도 문제가 없지만, 자동화 스크립트가 명령을 반복해서 던지는 무인 접속은 이 프록시가 감사 대상 세션으로만 취급해 명령 실행(exec) 자체를 막아버릴 수 있다

### ✅ 증거 1 — SSH 배너가 토글 하나로 바뀐다

가장 먼저 확인한 건 SSH 접속 시 서버가 보내는 첫 인사말(배너)이었다. 같은 명령인데 사내 보안 접근제어를 켜고 끄는 것만으로 배너가 달라졌다.

- **접근제어 OFF**: 원격 protocol version 2.0, remote software version — 베스천의 진짜 OpenSSH가 응답
- **접근제어 ON**: 원격 protocol version 2.0, remote software version — 통제 시스템의 감사 프록시가 응답

토글 하나로 "붙는 상대"가 통째로 바뀐다는 건, 이게 방화벽이나 포트 문제가 아니라 클라이언트 쪽 후킹이 원인이라는 강한 신호였다.

### ✅ 증거 2 — 켜져 있으면 명령 한 줄도 안 먹는다

다음은 접속 후 `whoami` 한 줄을 원격에서 바로 실행시키는 테스트였다.

- **OFF**: 정상적으로 접속 계정명이 출력됨
- **ON**: 인증까지는 진행되지만 그 직후 연결이 끊기면서 `whoami` 결과를 받지 못함

로그인(인증)은 ON/OFF 둘 다 되는데, 로그인 이후 명령을 실행시키는 통로(exec)는 ON일 때만 막힌다는 게 확인됐다. 사람이 터미널을 열어서 프롬프트까지 보는 건 문제가 없어 보이지만, 그 뒤에 자동으로 명령을 실행시키려는 순간 막힌다는 뜻이다.

### ✅ 증거 3 — 빌드 자체가 OFF에서만 성공한다

마지막으로 실제 자동화가 하려는 작업 그대로 — AutoIt 스크립트를 컴파일러(Aut2Exe)로 빌드하는 명령을 원격으로 던져봤다.

| 항목 | 접근제어 OFF | 접근제어 ON |
|------|--------------|--------------|
| 붙는 상대(배너) | 베스천 진짜 OpenSSH | 감사 프록시 |
| 로그인(인증) | 됨 | 됨 |
| 명령 실행(exec) | 됨 — 자동화 가능 | 거절/끊김 — 자동화 불가 |
| AutoIt 빌드 | 됨(실행 파일 정상 생성) | 불가(명령 자체가 전달 안 됨) |

세 가지 증거가 모두 같은 결론을 가리켰다. 자동화 PC의 SSH가 베스천의 진짜 OpenSSH로 직결되지 못하고, 후킹 드라이버가 중간에서 감사 프록시로 우회시키고 있었다.

### ✅ 결론 — 서버를 후킹 대상에서 빼야 한다

무인 자동화를 하려면, 자동화가 접속할 서버를 사내 접근제어의 후킹 대상 목록에서 제외해야 한다. 그래야 자동화 PC의 SSH가 프록시를 거치지 않고 베스천의 진짜 OpenSSH로 직결돼서 명령 실행·빌드가 정상 동작한다.

단, 여기서 실수하기 쉬운 지점이 하나 있다 — 베스천의 OpenSSH 서비스 자체를 내려버리면 안 된다는 것이다. 후킹 드라이버를 통한 감사 접속도 결국 그 밑에서는 같은 OpenSSH 엔진 위에서 동작하기 때문에, OpenSSH를 내리면 사람이 정상적으로 쓰는 감사 접속 경로까지 같이 죽는다. "이 서버는 후킹 대상에서 뺀다"와 "이 서버의 OpenSSH를 없앤다"는 완전히 다른 조치라는 걸 이번에 명확히 구분해서 정리해뒀다.

### ✅ 조사 도중 발견한 별개의 문제 — AutoIt 종료 코드가 성공 경로에서도 정리 작업을 하고 있었다

이 조사를 하면서 베스천에 배포된 AutoIt 스크립트의 종료 처리 로직도 같이 들여다봤는데, 여기서 또 다른 버그를 하나 찾았다.

WEB 타입 앱스크립트의 배포본을 보면, 로그인 성공/실패와 무관하게 매번 다음 세 가지를 무조건 호출하고 있었다.

```autoit
Local $ExitCode = CheckLoginResult()
SendLoginResult($sConnKey, $ExitCode, $ExitCode)   ; 결과 보고는 여기서 끝

If $ExitCode = 1 Then
    _WD_DeleteSession($WD_SESSION)   ; 실패에서만 세션 파기(브라우저 닫힘)
EndIf

ShutDownChromeDriver()   ; ← 성공/실패 무관하게 무조건 호출 중
ScriptExit()
Exit($ExitCode)
```

`ShutDownChromeDriver()`는 chromedriver.exe 프로세스만 종료시키는 함수인데, 로그인에 성공하면 사용자와 플랫폼이 그 브라우저 세션을 그대로 이어받아 제어해야 한다. 그런데 성공했을 때도 이 함수가 호출되면, 세션은 살아있는데 그 세션을 제어하던 chromedriver만 죽어버려서 플랫폼이 이어받을 제어 다리가 끊길 위험이 있었다.

- **실패 경로(ExitCode=1)**: `_WD_DeleteSession`으로 세션을 파기하고 `ShutDownChromeDriver()`로 남은 프로세스를 정리하는 게 맞다
- **성공 경로(ExitCode=0)**: 세션을 유지해야 하므로 아무것도 정리하면 안 된다 — 스크립트 최상단의 `Exit Main()` 구조 덕분에 `Main()`이 반환되기만 해도 프로세스는 정상 종료(exitCode 0)되고, 로그 파일도 그때 같이 닫힌다

이미 팀 표준 스켈레톤(`skeleton/web/login.au3`)에는 이 문제를 인지하고 "성공 시엔 호출하지 않음"으로 반영이 돼 있었는데, WEB 배포본 하나가 아직 이 패턴을 따라가지 못하고 무조건 호출 로직을 갖고 있었던 것이다. 표준을 세워둬도, 실제 배포본이 그 표준을 따라가고 있는지는 주기적으로 다시 확인해야 한다는 걸 이번에 다시 느꼈다.

### ✅ 결과 & 배운 점

| 항목 | 이전 | 이후 |
|------|------|------|
| SSH 자동화 원인 | 막연히 "포트 충돌"로 의심 | 클라이언트 후킹 드라이버가 명령 실행 통로를 차단하는 것으로 특정 |
| 해결 방향 | 미상 | 자동화 대상 서버를 후킹 정책 대상에서 제외 |
| 종료 코드 로직 | 성공/실패 무관 리소스 정리 무조건 호출 | 실패 경로에서만 정리, 성공 경로는 `Main()` 반환에 위임 |

포트가 열려 있고 로그인도 되는데 명령만 막히는 문제는 방화벽이 아니라 클라이언트 쪽 보안 소프트웨어를 의심해야 한다는 걸 배웠다. 그리고 "성공했을 때 실행되는 코드가 없다"는 것도 하나의 설계 선택이라는 걸 이번에 확인했다 — 아무것도 안 하는 게 맞는 상황에서 굳이 정리 코드를 넣으면, 그 코드가 오히려 다음 단계로 넘겨줘야 할 리소스를 건드리는 조용한 버그가 된다.
