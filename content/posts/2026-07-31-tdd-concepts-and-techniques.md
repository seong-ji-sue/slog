> **TL;DR** — TDD는 "실패하는 테스트를 먼저 쓰고, 통과시키는 최소한의 코드를 쓴 뒤, 정리한다"를 반복하는 방식이다. 테스트가 요구할 때만 코드를 만든다는 뜻에서 Needs-Driven Development라고도 부른다. 이 글은 2023년에 TDD를 익히며 정리했던 개념·원칙·6가지 실전 기법을 다시 정리한 노트다.

### ✅ TDD란 — 테스트가 개발을 주도한다

TDD는 실패하는 테스트를 먼저 작성하고, 그 테스트를 통과시키는 최소한의 코드를 작성한 뒤, 정리(리팩토링)하는 걸 반복하는 개발 방식이다. 핵심은 이름 그대로 테스트가 개발을 주도(Test Drives Development)한다는 것 — 테스트가 "이런 기능이 필요하다"고 먼저 선언하고, 우리는 그 필요를 채우는 코드만 작성한다. 그래서 TDD를 Needs-Driven Development(필요에 의한 개발)라고 부르기도 한다. 미리 상상해서 만드는 게 아니라 테스트가 요구할 때만 코드를 만든다.

TDD가 아닌 것도 짚어둘 필요가 있다. 테스트를 나중에 몰아서 쓰는 것, 커버리지 숫자를 채우려고 모든 메서드에 테스트를 다는 것, 단순 위임(get/set, repository 호출만 하는 메서드)까지 테스트하는 것은 TDD가 아니다.

### ✅ 왜 하는가 — 설계 개선과 살아있는 문서

| 효과 | 설명 |
|------|------|
| 설계 개선 | 테스트하기 어려운 코드는 결합도가 높은 코드다. 테스트를 먼저 짜면 자연스럽게 느슨하게 결합된 설계가 나온다 |
| 리팩토링 안전망 | 테스트가 있으면 "고쳐도 동작이 그대로다"를 즉시 확인할 수 있어 과감하게 개선할 수 있다 |
| 살아있는 문서 | 테스트는 "이 코드는 이렇게 동작해야 한다"는 명세서다. 주석과 달리 거짓말을 하지 않는다(깨지면 빨개지니까) |
| 빠른 피드백 | 작은 단위로 끊임없이 검증하니 문제를 일찍, 작게 잡는다 |

인상 깊었던 비유가 하나 있다. 프로덕션 코드를 잃어버려도 테스트가 있으면 다시 구현할 수 있지만, 테스트를 잃어버리면 프로덕션 코드만 보고 원래 의도했던 모든 명세를 복원하기는 사실상 불가능하다. 그만큼 테스트가 시스템의 진짜 명세라는 것.

### ✅ Red → Green → Refactor 사이클

```
[RED] 실패하는 테스트 작성  →  [GREEN] 통과하는 최소 코드  →  [REFACTOR] 정리
  아직 구현 없음                상수 반환도 OK                테스트는 계속 초록 유지
                          ↑_______________________________|
```

1. **RED** — 아직 구현이 없으니 컴파일조차 안 되거나 빨갛게 실패한다. 이 실패를 반드시 눈으로 확인한다(테스트가 실제로 검증하고 있는지 확인하는 단계)
2. **GREEN** — "예쁘게"가 아니라 "통과하게"가 목표다. 심지어 상수를 반환해도 된다(Fake It 기법). 일단 초록불을 만든다
3. **REFACTOR** — 중복을 제거하고 이름을 다듬고 구조를 개선한다. 테스트가 초록인 상태를 유지하면서 한다

Kent Beck의 진행 순서도 같은 맥락이다 — 1) 일단 동작하게(First, make it work) 2) 그다음 올바르게(Then, make it right) 3) 그다음 작고 빠르게(Then, make it small and fast). 한 번에 두 가지를 동시에 하려 하지 않는 게 핵심이다.

### ✅ 좋은 테스트의 기준 — FIRST

| 글자 | 의미 | 설명 |
|------|------|------|
| **F**ast | 빠르게 | 자주 돌릴 수 있어야 한다. 느리면 안 돌리게 되고, 안 돌리면 의미가 없다 |
| **I**ndependent | 독립적으로 | 테스트끼리 순서·상태에 의존하면 안 된다 |
| **R**epeatable | 반복 가능하게 | 어떤 환경에서 몇 번을 돌려도 항상 같은 결과가 나와야 한다 |
| **S**elf-validating | 스스로 검증되게 | 통과/실패를 사람이 로그 보고 판단하는 게 아니라 assert로 자동 판정 |
| **T**imely | 적시에 | 프로덕션 코드를 만들기 직전에 테스트를 작성한다 |

### ✅ 막혔을 때 쓰는 6가지 실전 기법

Robert C. Martin(엉클 밥)이 정리한, TDD를 막히지 않고 진행하는 기법들이다.

**1) Fake It — 가짜로 통과시키기.** 테스트를 통과시키는 가장 단순한 방법인 상수 반환부터 시작한다.

```java
@Test
void newStack_isEmpty() {
    Stack stack = new Stack();
    assertThat(stack.isEmpty()).isTrue();
}

// 일단 상수로 통과시킨다 — 진짜 구현은 다음 테스트가 요구할 때
public boolean isEmpty() {
    return true;
}
```

핵심 마인드셋은 "예측되면 하지 마라. 반드시 할 필요가 있을 때만 해라"다. 다음 테스트가 이 `return true`를 더 이상 통과시키지 못하게 만들 때, 그때 진짜 로직을 넣는다.

**2) Stairstep Tests — 계단식 테스트.** 최종 기능으로 가기 위한 임시 디딤돌 테스트를 놓는다. "객체를 만들 수 있는가" → "메서드를 호출할 수 있는가" → "진짜 기능이 동작하는가" 순서로 쌓아 올린다. 디딤돌 테스트는 진짜 기능 테스트가 생기면 삭제한다 — 비계를 세웠다가 건물이 올라가면 걷어내는 것과 같다.

**3) Assert First — 단언부터 거꾸로 쓰기.** 테스트를 결과(assert)부터 거꾸로 작성한다. "무엇을 검증하고 싶은가"를 먼저 못박으면 필요한 API가 자연스럽게 드러난다.

```java
@Test
void newMailBox_hasNoMessages() {
    // 1) 단언부터 쓴다 — 이 시점엔 mailbox가 뭔지도 모른다
    assertThat(mailbox.messageCount()).isEqualTo(0);
}
// 2) 컴파일 위해 변수 선언 → 3) 객체 생성 → 4) 필요한 메서드 구현
```

**4) Triangulation — 삼각측량.** 테스트가 구체적일수록 코드는 더 일반화된다. 케이스를 하나 더 추가해서 "상수로는 못 버티게" 만들어 일반화를 강제한다.

```java
// 잔액 100 → 이자 3.0  (구현: return 3.0; ← 아직 상수로 통과)
// 잔액 200 → 이자 6.0  (상수로는 둘 다 통과 불가!)
// → 구현을 일반화: return balance * 0.03;
```

**5) One To Many — 하나에서 여럿으로.** 컬렉션을 다루는 기능은 원소 1개로 먼저 구현하고(필드 하나로 버티기), 그다음 여러 개로 확장한다(배열/리스트로 일반화를 강제).

**6) Refactoring Tests — 테스트도 리팩토링한다.** 세부 절차가 길어지면 의도가 묻히므로, Extract Method로 시나리오만 남긴다.

```java
// Before — 세부 절차가 의도를 가린다
Response response = new FitNesseExpediter(...).process(new Request("?properties&format=json"));
assertThat(response.getContentType()).isEqualTo("application/json");

// After — "무엇을 하는 테스트인지"만 남긴다
givenTestPageExists();
SimpleResponse response = whenPropertiesRequestedAsJson();
thenAllPropertiesAreDefaults(response);
```

### ✅ 테스트 피라미드와 테스트 더블 용어

테스트는 한 번에 얼마나 넓은 범위를 확인하느냐에 따라 세 종류로 나뉜다. 좁게 보는 단위 테스트는 많이, 넓게 보는 E2E는 적게 — 쌓아보면 삼각형(피라미드)이 된다.

```
[   E2E   ]   ← 적게: 느리고 비쌈. 핵심 경로만
[  통합   ]   ← 중간: 모듈 간 연동·DB 검증
[  단위   ]   ← 많이: 빠르고 안정. 로직을 가장 촘촘하게
```

단위 테스트를 많이 만드는 이유는 빠르고(수 ms), 깨지면 어디가 문제인지 바로 짚어주기 때문이다. 반대로 E2E는 느리고 환경 탓에 자주 흔들리고, 깨져도 원인 찾기가 어렵다.

테스트 더블(진짜 객체를 대신하는 가짜) 용어도 헷갈리기 쉬워 정리해둔다.

| 용어 | 무엇 | 예 |
|------|------|-----|
| Dummy | 전달용으로만 쓰이고 실제로는 안 쓰임 | 파라미터 자리만 채우는 빈 객체 |
| Stub | 미리 정해둔 값을 반환 | `when(repo.findById(1)).thenReturn(user)` |
| Spy | 실제처럼 동작하되 호출 기록을 남김 | 호출 횟수·인자 검증 |
| Mock | 호출에 대한 기대를 설정하고 검증 | `verify(mailSender).send(...)` |
| Fake | 동작하는 가벼운 대체 구현 | 인메모리 DB, 가짜 Repository |

실무 감각으로는 값만 필요하면 Stub, 호출 여부·방식 검증이 목적이면 Mock을 쓰고, DB처럼 진짜 동작이 중요한 곳은 가짜보다 Fake(인메모리)나 실제 구현이 안전하다.

### ✅ 정리

| 항목 | 핵심 |
|------|------|
| 사이클 | RED(실패 확인) → GREEN(최소 코드로 통과) → REFACTOR(정리, 초록 유지) |
| 좋은 테스트 | FIRST(Fast·Independent·Repeatable·Self-validating·Timely) |
| 막혔을 때 | Fake It·Stairstep·Assert First·Triangulation·One To Many·Refactoring Tests |
| 테스트 비중 | 단위 多 — 통합 中 — E2E 少 |

경계 조건은 미리 다 설계하려 하지 말고 테스트로 하나씩 끌어내는 게 TDD의 묘미다. 특수 케이스가 쌓이다 보면 결국 하나의 일반 규칙으로 수렴하는 순간이 온다 — 그 순간을 직접 겪어봐야 왜 TDD를 하는지 체감이 된다.
