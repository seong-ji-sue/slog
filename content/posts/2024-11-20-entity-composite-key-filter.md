> **TL;DR** — Entity(계정) 관리 화면 자체는 Namespace 패턴을 그대로 따라가서 비교적 수월했다. 문제는 그 옆에 딸린 "복합키(attributes/metadata) 필터"였는데, 이건 텍스트박스 하나에 `key::value` 형식으로 여러 조건을 입력받는 특수 필터라서, 데이터 형식·유효성 규칙이 요구사항이 바뀔 때마다 거의 1년에 걸쳐 계속 고쳐졌다.

1️⃣ `복합키 필터` 2️⃣ `데이터 형식 변경` 3️⃣ `지속 개선`

### ✅ 요구사항

> 팀장 : Namespace 다음은 Entity(계정)야. 패턴은 비슷하게 가면 될 거야
> 나 : CRUD는 Namespace 때 잡은 모드 기반 다이얼로그 그대로 쓰면 될 것 같아요. 근데 감사로그에서 Entity를 attributes/metadata 값으로 필터링해야 한다는 요구사항은 좀 다른데요
> 팀장 : 아, 그거 복합키 형식으로 받아야 하는데... 일단 이번엔 보류하고 나중에 하자

Entity(계정) CRUD 자체는 이전 편의 Namespace 패턴(모드 기반 다이얼로그 + 상태 기반 제어 명세표)을 그대로 재사용해서 빠르게 붙었다. 이번 글에서 더 비중 있게 다룰 부분은 그 옆에서 계속 형태를 바꿔온 "복합키 필터"다.

### ✅ 복합키 필터가 뭔가

Entity는 `attributes`, `metadata` 같은 키-값(key-value) 형태의 커스텀 속성을 가질 수 있다. 감사로그(Audit Log)에서 "이 attribute 값이 이런 Entity만 보여줘" 같은 조회를 하려면, 일반적인 selectbox나 단일 텍스트박스로는 표현이 안 된다. 그래서 사용자가 `key::value` 형식의 문자열을 직접 입력하면, 이를 파싱해서 여러 조건으로 변환하는 전용 필터 컴포넌트가 필요했다. 처음 요구사항 논의 때는 "이 형식을 어떻게 구현할지 애매하다"는 이유로 한 차례 보류됐을 만큼, 처음부터 형태가 명확하지 않은 기능이었다.

### ✅ 1차 구현 — 텍스트박스 + 유효성

보류됐던 요구사항이 다시 올라왔을 때, 우선 다음 형태로 구현했다.

- 텍스트박스에 `key::value` 형식으로 입력
- 노드(BFF)에서 이 문자열을 파싱해 필터 조건 객체로 변환
- 여러 조건을 동시에 입력할 수 있게 다중 입력 폼 허용
- 입력값이 형식에 안 맞으면(구분자 누락 등) 유효성 오류로 막음

```js
// parseCompositeKeyFilter.js
const SEPARATOR = '::';

function parseCompositeKeyFilter(raw) {
  // "env::prod" -> { key: 'env', value: 'prod' }
  const idx = raw.indexOf(SEPARATOR);
  if (idx === -1) {
    throw new Error('key::value 형식이 아닙니다');
  }
  return {
    key: raw.slice(0, idx).trim(),
    value: raw.slice(idx + SEPARATOR.length).trim(),
  };
}
```

여기까지는 평범했다. 문제는 이 다음부터였다.

### ✅ 왜 계속 리팩토링됐나 — 요구사항이 형태를 바꿀 때마다

이 필터는 이후로도 계속 손이 갔는데, 원인은 매번 달랐다.

1. **필터 요청 데이터 형식 변경** — 처음엔 파싱된 객체를 그대로 요청 바디에 실었는데, 서버 쪽 다른 조회 API와 포맷을 맞추면서 query string 형식으로 바꿔야 했다.
2. **속성 데이터 형식 변경** — attributes/metadata를 `{attributes: 'key::value'}` 형태의 단일 문자열 필드로 다시 정의하면서, 파싱 로직과 유효성 체크를 한 번 더 갈아엎었다.
3. **필터 단건 삭제 버그** — 여러 조건 중 하나만 지울 때, 값이 숫자나 객체인 경우까지 고려하지 않아서 삭제가 안 되는 케이스가 나왔다. 조건 비교 로직을 타입에 안전하게 다시 짰다.
4. **라벨 표기 되돌림** — 필터 UI에 노출하는 라벨을 `key` 그대로 보여주다가 사용자 친화적인 문구로 바꿨는데, 다시 원래 표기로 되돌리는 등 UX 방향 자체가 몇 차례 왔다갔다했다.
5. **연속성 유효성 체크** — 거의 1년 뒤, 여러 조건을 입력할 때 앞 조건이 비어있는 채로 뒤 조건만 채워지는 경우를 막기 위해 "입력해야 하는 텍스트박스에 빨간 테두리 표시" 같은 연속성 검증이 추가됐다.

```js
// compositeKeyRequest.js — 요청 형식 2차 변경 예시
function toRequestFormat(filters) {
  // 변경 전: [{ key, value }] 객체 배열을 그대로 body에 실음
  // 변경 후: 서버 규격에 맞춰 query string으로 직렬화
  const params = new URLSearchParams();
  filters.forEach(({ key, value }) => {
    params.append('attributes', `${key}::${value}`);
  });
  return params.toString();
}
```

### ✅ 되돌아보며 — 왜 처음부터 안정된 형태로 못 짰나

이 필터가 계속 흔들린 근본 이유는, "감사로그를 어떤 기준으로 조회하고 싶은가"라는 요구사항 자체가 화면을 만들면서 같이 구체화됐기 때문이다. 처음엔 단순 key-value 한 쌍만 지원하면 될 줄 알았는데, 실제 사용 패턴을 보니 여러 조건을 조합해야 했고, 서버 쪽 다른 필터(기간, 태그)와 요청 포맷을 통일해야 하는 요구도 나중에 붙었다. 즉 UI 컴포넌트 하나의 문제가 아니라, "이 데이터를 어떤 모양으로 주고받을지"에 대한 계약이 계속 재협상된 것이다.

이후 이 필터는 다른 페이지에 흩어져 있던 필터 컴포넌트들과 함께 공통 필터 구조로 통합되면서(별도 회고 대상), 최소한 "필터 자체의 유효성·직렬화 로직"과 "화면에 어떻게 보여줄지"는 분리해서 관리하는 방향으로 정리됐다.

### ✅ 결과 & 배운 점

- 요구사항이 처음부터 불확실한 기능(형식이 안 잡힌 필터류)은 "일단 보류"도 하나의 선택지다 — 억지로 형태를 만들면 나중에 더 크게 갈아엎게 됨
- 파싱·직렬화 로직을 유효성 체크와 분리해두면, 데이터 형식이 바뀌어도 유효성 규칙까지 전부 다시 짜지 않아도 됨
- 값의 타입(문자열/숫자/객체)을 가정하지 않고 항상 안전하게 비교하는 습관이, 다중 입력 폼처럼 사용자 입력이 다양한 화면에서 특히 중요하다는 걸 여러 번 겪으며 체감했다
