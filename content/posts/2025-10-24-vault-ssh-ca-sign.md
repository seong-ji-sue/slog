> **TL;DR** — SSH 접속용 키를 서버마다 배포하는 대신, 짧은 유효기간의 인증서에 서명해서 나눠주는 SSH CA(Certificate Authority) 방식을 구현했다. ECDSA 키 생성 500 에러를 고치고, OS·OpenSSL 버전에 따라 지원하는 알고리즘과 접속 명령어가 다르다는 걸 직접 조사해서 정리했다.

### ✅ 요구사항

> 선임 : SSH Key 관리 콘솔에 CA Sign 기능 있잖아 — 거기서 Key Algorithm을 ECDSA로 선택하면 500 에러남  
> 나 : 재현되나요?  
> 선임 : 됨. 근데 이거 고치기 전에, 애초에 왜 SSH Key를 그냥 배포하지 않고 CA로 서명하는 방식을 쓰는지부터 한 번 짚고 가자  
> 나 : 넵, 개념부터 정리하고 에러 원인 보겠습니다

이 시리즈의 다른 글들이 "DB 자격증명", "권한 모델", "감사 로그"처럼 각자 독립된 기능이었다면, 이 기능은 시리즈 제목 그대로 "SSH Key 관리"의 핵심이었다. 그래서 이번 글은 유독 오래, 그리고 깊게 팠다.

### ✅ SSH Key를 그냥 배포하지 않고 CA로 서명하는 이유

**기존 방식 — 공개키를 서버마다 개별 등록**

- 접속 대상 장비마다 사용자의 공개키를 서버에 등록해야 한다. 장비가 수백 대면 배포·회수 작업 자체가 운영 부담이다
- 키가 유출되면 만료 시점이 없다. 서버에서 직접 그 키를 찾아 삭제해야만 무효화된다
- 담당자가 바뀌거나 퇴사하면, 등록된 서버를 일일이 찾아다니며 키를 지워야 한다

**SSH CA(Certificate Authority) 서명 방식**

- 서버는 "이 CA가 서명한 인증서라면 신뢰한다"는 CA 공개키 하나만 등록해두면 된다(OpenSSH의 `TrustedUserCAKeys` 설정)
- 접속할 때마다 사용자의 공개키에 CA가 서명해서 단기 인증서를 발급한다. 인증서에는 유효기간과 허용 계정(principal)이 함께 박힌다
- 유효기간이 지나면 인증서는 자동으로 무효화된다 — 키를 찾아서 회수하는 운영 작업 자체가 사라진다
- 서버 개별 등록이 아니라 CA 등록 한 번으로 전체 서버를 커버한다. 신규 서버가 추가돼도 CA 공개키만 심으면 끝난다

정리하면, 기존 방식은 "한 번 배포하면 회수 전까지 계속 유효한" 구조였고, CA 서명 방식은 "누구에게 얼마나 오래 접속 권한을 줄 것인가를 매 요청마다 판단해서 짧게 내주는" 구조다. 영구 자산을 나눠주는 것과, 그때그때 필요한 만큼만 짧게 발급하는 것의 차이 — 앞서 다룬 DB 동적 자격증명과 사실 같은 철학이다.

### ✅ ECDSA 생성 오류 — 알고리즘마다 숨어있던 버그

- **현상**: Key Algorithm을 ECDSA로 선택해서 CA Sign을 생성하면 내부 라이브러리에서 500 에러가 발생
- **원인 분석**: ECDSA 알고리즘으로 키를 생성하는 로직이 로컬 파일 경로를 이용해서 처리하도록 짜여 있었는데, 이 경로에 권한 문제가 있어서 파일 생성 자체가 실패하고 있었다
- **해결**: ECDSA 키 생성 시 로컬 파일 경로를 사용하지 않고, 메모리 상에서 바로 처리하도록 로직을 수정

```ts
type KeyAlgorithm = "rsa" | "ecdsa" | "ed25519";

function generateCaKeyPair(algorithm: KeyAlgorithm): KeyPair {
  // ECDSA는 로컬 파일 경로 의존 로직 제거 — 인메모리 생성으로 통일
  if (algorithm === "ecdsa") {
    return generateInMemoryKeyPair(algorithm);
  }
  return generateInMemoryKeyPair(algorithm);
}
```

수정 자체는 간단했지만, 배운 점은 따로 있었다. 알고리즘별로 내부 라이브러리가 처리하는 방식이 미묘하게 달라서, RSA 하나만 테스트하고 "CA Sign 기능은 됐다"고 넘어갔으면 ECDSA에서 이런 식으로 숨어있던 버그를 놓쳤을 거라는 점이다. 지원한다고 명시한 알고리즘이 있다면, 그 알고리즘 각각으로 실제 생성까지 확인해야 한다.

### ✅ OS·OpenSSL 버전별 알고리즘·접속 명령어 호환성 조사

인증서로 SSH 접속을 시도했을 때, 접속 대상 장비의 OS(OpenSSL/OpenSSH 버전)에 따라 지원하는 키 알고리즘과 접속 옵션이 달라서 "접속이 안 되는" 문제가 생길 수 있다는 게 출시 전에 이미 예상됐다. 그래서 기능을 내보내기 전에 별도로 두 가지를 조사했다.

1. **OS 버전별 지원 Key Algorithm 조사** — OpenSSL 버전에 따라 RSA/ECDSA/Ed25519 중 어떤 조합이 실제로 동작하는지 직접 테스트
2. **OS 버전별 CA Sign 접속 명령어 조사** — 인증서를 포함해 SSH로 접속할 때 필요한 옵션이 OpenSSH 버전별로 어떻게 달라지는지 확인

조사는 실제 여러 버전의 장비에 인증서 기반 접속을 시도해보면서 진행했고, 결과는 표로 정리해 지원 가능한 조합과 그렇지 않은 조합을 구분했다. 지원되지 않는 조합에 대해서는 화면에서 사전에 안내하거나 별도 가이드로 대응하기로 했다.

이 조사가 없었다면 "왜 어떤 서버는 접속이 되고 어떤 서버는 안 되는지"를 매번 현장에서 하나하나 디버깅해야 했을 것이다. 기능을 내보내기 전에 지원 범위를 명확히 그어두는 것이, 실제로는 출시 이후 장애 대응 시간을 줄이는 가장 확실한 방법이라는 걸 이번에 체감했다.

### ✅ CA Sign 이력 보강 — Host Address·계정명 컬럼

연동 장비에 CA Sign으로 실제 접속을 해보니, 로그에 어떤 장비(호스트 주소)로 접속했는지가 안 남아서 이력을 구분하기 어렵다는 피드백이 들어왔다.

- 로그 테이블에 `host_address` 컬럼 추가
- 서명(sign) 시점에 접속 대상의 호스트 주소를 함께 적재하도록 서비스 로직 수정
- 허용 계정 목록(principals)이 배열로 저장돼 있었는데, 조회 API에서는 문자열로 합쳐서 내려주도록 응답 형식을 통일

```ts
interface SshCaSignLog {
  keyId: string;
  serialNumber: string;
  hostAddress: string;
  principals: string; // 배열을 콤마로 join한 문자열로 응답 통일
  issuedAt: string;
  expiresAt: string;
}
```

같은 시기에 CA Sign 권한 관련 버그도 같이 정리했다. 권한이 없는 사용자가 CA Sign 버튼을 눌러도 아무 반응이 없던 걸, 권한이 없다는 알림창이 뜨도록 수정했다. "눌러도 반응이 없는 것"과 "권한이 없다고 명확히 알려주는 것"은 사용자 입장에서 완전히 다른 경험이다 — 기능 버그는 아니었지만, 신뢰도에 영향을 주는 수정이었다.

### ✅ 전체 진행 순서 요약

1. SSH CA 개념 정리 — 왜 개별 키 배포 대신 CA 서명 방식을 쓰는지
2. ECDSA 키 생성 500 에러 원인 분석 및 수정 (로컬 파일 경로 의존 제거)
3. OS/OpenSSL 버전별 지원 Key Algorithm 조사
4. OS 버전별 CA Sign 접속 명령어 옵션 조사
5. CA Sign 이력에 Host Address·계정명 컬럼 추가
6. CA Sign 권한 없음 알림창 처리

### ✅ 결과 & 배운 점

| 항목 | 이전 | 이후 |
|------|------|------|
| 키 배포 방식 | 서버마다 공개키 개별 등록 | CA 공개키 1회 등록 + 단기 인증서 발급 |
| 유효기간 | 없음(수동 회수 필요) | 인증서 만료 시 자동 무효화 |
| ECDSA 생성 | 500 에러 | 인메모리 처리로 정상 발급 |
| 호환성 파악 | 접속 시도 후 사후 대응 | 사전 조사 기반 지원 범위 명시 |

SSH Key 관리라고 하면 보통 "키를 안전하게 저장하는 것"만 떠올렸는데, 이 기능을 구현하면서 진짜 어려운 부분은 저장이 아니라 "그 접속 권한을 얼마나 짧게, 얼마나 정확한 범위로 내주느냐"라는 걸 깨달았다. 인증서의 유효기간과 principal을 얼마나 촘촘하게 설계하느냐가 결국 이 기능 전체의 보안 수준을 결정한다.
