> **TL;DR** — POC 때마다 손으로 반복하던 베스천(Bastion) 서버 세팅을 연결→방화벽→초기설정→배포 4단계 STEP 스킬로 쪼개서 자동화했다. 방화벽 통신 점검과 Windows 초기설정을 각각 별도 PowerShell 스크립트로 분리하고, `[OK]/[SKIP]/[WARN]/[FAIL]` 결과 코드로 진행 상태를 판별하도록 만들었다. SSH를 native CLI로 통일하면서 점프호스트(ProxyCommand) 경유 접속으로 전환했고, "베스천은 빌드·실행 전용, 소스의 SSoT는 로컬"이라는 원칙도 이 과정에서 명문화했다. 그리고 별도로 겪었던 RDS 라이선스(CAL) 카운팅 문제 — Workgroup 환경이라 발급 자체가 안 되던 문제 — 의 원인도 이번에 함께 정리했다.

난이도 : ★★★★☆

1️⃣ `STEP 파이프라인 스킬화` 2️⃣ `RDS 라이선스(CAL) 카운팅 트러블슈팅` 3️⃣ `ProxyCommand 점프호스트`

### ✅ 요구사항

> 담당 이사님 : 저번 글에서 말한 그 "매번 반복되는 베스천 세팅", 이제 좀 자동화해보자  
> 나 : 세팅 과정을 단계별로 쪼개볼게요. 한 번에 다 자동화하려고 하면 나중에 하나만 고쳐도 전체를 다시 돌려야 하니까요  
> 담당 이사님 : 좋다, 대신 어디까지 자동화되고 어디부터 수동인지는 솔직하게 정리해줘

앞선 글([해외 POC 대응기](/posts/overseas-poc-infra-license-security))에서 "POC마다 반복되는 베스천 세팅 자체가 가장 시간을 많이 잡아먹었다"고 짚었었다. 이번 글은 그 세팅 과정을 실제로 어떻게 자동화했는지, 스킬 신설부터 API/UI 통합, 인프라 전환, 그리고 자동화 스크립트가 다루는 범위와 그렇지 않은 라이선스 이슈를 어떻게 구분해 정리했는지까지 시간순으로 다룬다.

### ✅ 손으로 하던 베스천 세팅 — 뭘 자동화 대상으로 삼았나

자동화 이전에는 베스천 서버 구축 가이드(사내 접근제어 솔루션 베스천 구성 가이드 문서)를 보면서 아래 과정을 매번 손으로 반복했다.

1. **방화벽 포트 오픈** — AWS 보안 그룹에서 사용자 PC → 베스천(3389), 베스천 → 사내 통합 플랫폼 서버(웹·API·DB 등 다수 포트) 인바운드를 수동으로 등록
2. **DB 권한 부여** — 사내 통합 플랫폼 서버의 MariaDB 쉘에 접속해서 베스천 서버의 사설 IP에 대한 DB 접근 권한을 수동으로 부여
3. **서버 관리자 기능 설치** — Server Manager에서 `Add roles and features` 마법사를 열어 Remote Desktop Services → Remote Desktop Session Host 역할을 체크하고, AWS 패스워드 변경 플러그인 호환을 위한 .NET Framework 3.5 기능도 같이 설치
4. **기본 환경 세팅** — UAC 알림을 `Never notify`로, NLA(네트워크 수준 인증) 체크를 해제, 솔루션 구동용 로컬 그룹 생성, 로컬 보안 정책에서 패스워드 복잡도 요구사항 해제, GPO에서 PowerShell 실행 정책·모듈 로깅 활성화, OS Hardening용 로그온 스크립트 등록까지 `gpedit.msc`를 열어 하나씩 클릭
5. **RDS Agent 설치** — 설치 파일을 실행해 서버 URL 정보를 입력하고 서비스가 기동되는지 확인
6. **연결 테스트** — 전용 연결 테스트 툴로 베스천 ↔ 사내 통합 플랫폼 서버 간 통신(WEB/API/DB)이 전부 성공으로 뜨는지 확인

이 6단계가 그대로 자동화 스크립트의 PRE-CHECK/CHECK A/STEP1~7 구조로 옮겨간 대상이다. GUI 클릭 몇 번이 필요한 3~4번 항목은 레지스트리·보안정책 값을 직접 건드리는 방식으로, 반복적인 확인 작업(1·2·6번)은 점검 스크립트로 대체했다.

### ✅ 첫 스킬 — 연결→방화벽→초기설정→배포를 한 덩어리로

가장 먼저 만든 건 `bastion-setup`이라는 단일 스킬이었다. 이름 그대로 베스천 서버에 대한 작업을 "연결 확인 → 방화벽 오픈 → 초기설정 → 배포"라는 하나의 흐름으로 묶어서, 실행 한 번으로 세팅이 끝까지 가도록 만드는 게 목표였다.

처음엔 이 구성이 맞다고 생각했다. 세팅을 처음부터 끝까지 한 번에 밀어붙이는 게 사람이 손으로 하던 것과 가장 비슷한 흐름이었기 때문이다. 하지만 곧 다른 필요가 생겼다 — "방화벽만 다시 확인하고 싶다", "초기설정만 재실행하고 싶다"는 요청이 반복됐다. 하나로 묶인 스킬은 이런 부분 재실행에 취약했다. 전체를 다시 돌리거나, 스킬 코드를 열어서 원하는 구간만 손으로 잘라내야 했다.

### ✅ 스킬 분리 — 관심사별로 나눠야 재사용이 된다

그래서 `bastion-firewall`과 `bastion-init-setup`을 별도 스킬로 분리했다. 방화벽 점검·오픈 로직과 서버 초기설정 로직을 각자 독립적으로 실행 가능하게 만든 것이다.

- 방화벽만 확인하고 싶을 때는 `bastion-firewall`만 호출한다
- 서버가 이미 살아있는 상태에서 초기설정만 다시 하고 싶을 때는 `bastion-init-setup`만 호출한다
- 전체 파이프라인이 필요할 때는 두 스킬을 순서대로 조합해서 부른다

한 덩어리였을 때는 "전체를 다시 돌리거나 아무것도 안 하거나"의 양자택일이었는데, 분리하고 나니 필요한 구간만 골라서 재실행할 수 있게 됐다. STEP 단위로 쪼개는 게 처음엔 번거로워 보였지만, 실제로는 이후 운영에서 훨씬 자주 도움이 됐다.

### ✅ 방화벽 점검 스크립트 — 오픈 요청 전에 통신 가능 여부부터 확인

`bastion-firewall` 스킬의 핵심은 PowerShell 스크립트 하나다. 목적은 명확했다 — 고객사 측에 방화벽 오픈을 요청하기 전에, 베스천 → 사내 통합 플랫폼 방향으로 필수 포트가 실제로 통신 가능한지부터 스크립트로 먼저 확인하는 것.

동작 순서는 이렇다.

1. 설정 파일에서 대상 서버 IP를 로드한다 — 실제 값 예시:

```
# 대상 서버 IP 설정 파일 (개념 예시, 실제 IP는 마스킹)
TargetServerIp=<사내 통합 플랫폼 서버 IP>
BastionIp=<이 베스천 서버 IP>
```

2. 베스천 → 사내 통합 플랫폼 방향으로 아래 포트들의 TCP 연결 상태를 포트당 3초 타임아웃으로 체크한다.

| 포트 | 서비스 | 용도 |
|------|--------|------|
| 8443 | 사내 통합 플랫폼 WEB Server | 웹 서비스 |
| 12000 | 사내 통합 플랫폼 AUTH Server | 로그인 / 인증 |
| 11200 | 사내 통합 플랫폼 API Server | REST API |
| 11070 | asa-relay-listener | 엔진 통신 릴레이 |
| 11500 | hi-ndc | Client ↔ 서버 통신 |
| 11310 | app-relay-lb | CS 타입 앱 데이터 릴레이 LB |
| 11700 | app-relay-lb | WEB 타입 앱 릴레이 |
| 7777 | psm-gui-logger | RDP 화면 녹화 / 라이브 릴레이 |
| 3306 | MariaDB | 데이터베이스 |
| 1205 ~ 1210 | app-web-relay | WEB 앱 릴레이 채널 |

3. 포트별 결과를 `[OK]` / `[FAIL]`로 화면에 출력한다. 열리지 않은 포트로 임의의 값(존재하지 않는 포트)을 하나 넣어서 "FAIL이 진짜로 FAIL로 뜨는지" 자체 검증까지 스크립트 안에 넣어뒀다.

실행은 아래 명령 한 줄이다.

```powershell
PowerShell -ExecutionPolicy Bypass -File "$env:USERPROFILE\Desktop\autoit-file\bastion-firewall-check.ps1"
```

방화벽 오픈 요청을 보내기 전에 이 스크립트부터 돌리면, "요청은 했는데 실제로는 막혀 있더라"는 뒤늦은 확인을 방지할 수 있다.

### ✅ 초기설정 스크립트 — PRE-CHECK부터 STEP7까지, 이미 된 건 SKIP

`bastion-init-setup` 스킬은 신규 베스천 서버의 Windows 환경을 자동으로 구성한다. 이미 설정된 항목은 자동으로 SKIP 처리되도록 만들어서, 신규 서버든 기존 서버에 재실행하든 같은 스크립트를 쓸 수 있게 했다.

| 단계 | 항목 | 내용 |
|------|------|------|
| PRE-CHECK | Workgroup 확인 | 도메인 가입 상태면 즉시 종료 + 안내 출력 |
| CHECK A | RDS Agent 설치 확인 | 미설치 상태면 즉시 종료 + 설치 안내 출력 |
| STEP 1 | UAC 비활성화 | `EnableLUA=0` 레지스트리 설정 |
| STEP 2 | 전용 로컬 그룹 생성 | 솔루션 구동용 로컬 그룹 생성 |
| STEP 3 | 패스워드 복잡도 해제 | 로컬 보안 정책 변경 |
| STEP 4 | GPO PowerShell 설정 | 실행 정책 / 모듈 로깅 / 트랜스크립션 |
| STEP 5 | GPO 로그온 스크립트 등록 | OS Hardening용 로그온 스크립트 자동 등록 |
| STEP 6 | Windows 기능 설치 | Remote Desktop Services + Remote Desktop Session Host 설치 |
| STEP 7 | 웹 배포 | AppScript 폴더에 웹 배포 압축 파일 해제 |

실행 명령어와 결과 코드 체계는 이렇다.

```powershell
PowerShell -ExecutionPolicy Bypass -File "$env:USERPROFILE\Desktop\autoit-file\bastion-init-setup.ps1"
```

| 코드 | 의미 |
|------|------|
| `[OK]` | 정상 수행 완료 |
| `[SKIP]` | 이미 설정됨 — 변경 없음 |
| `[WARN]` | 비치명적 경고(예: 배포 파일 없음) — 계속 수행 |
| `[FAIL]` | 오류 발생 — 스크립트 즉시 종료 |

스크립트 실행이 끝나면 STEP별 결과가 요약으로 출력되고, 마지막에 "다음에 할 일(Next Steps)"이 따로 안내된다 — **MariaDB 권한 부여**(사내 통합 플랫폼 서버 MariaDB에 접속해서 이 베스천 IP의 접근 권한을 부여하는 작업)와 **서버 재부팅**(설정 적용을 위해 필요) 두 가지다. 이 두 항목만큼은 스크립트가 서버 바깥(DB 서버)이나 재부팅 이후 상태를 다뤄야 해서 자동화 범위 밖에 남겨뒀다.

### ✅ IP 입력 방식으로 재작성 — 서버가 매번 바뀐다는 전제

초기 버전은 대상 서버 정보가 스킬 내부나 설정 파일에 고정돼 있는 구조에 가까웠다. 그런데 POC 환경은 매번 다른 서버(다른 IP, 다른 리전)를 대상으로 한다는 게 문제였다. 그래서 스킬을 실행할 때 대상 서버의 IP를 사용자 입력으로 받는 방식으로 다시 작성했다.

실행할 때마다 "이번 세팅 대상이 어디인가"를 명시적으로 입력받는 구조로 바뀌면서, 새 POC가 잡힐 때마다 스킬 파일 자체를 건드릴 필요가 없어졌다. 스킬은 고정된 로직만 갖고, 대상은 매 실행마다 파라미터로 주입받는다는 원칙이 이때 자리 잡았다.

### ✅ SSH native 단일화 + 스크립트를 스킬 레이어로 이전

같은 시기에 백엔드 SSH 연결 방식도 [paramiko에서 native SSH CLI로 전환](/posts/paramiko-native-ssh-migration)하는 작업이 진행되고 있었다. 베스천 자동화도 이 흐름 위에 올라탔다 — 베스천 스크립트와 스펙 산출물을 `.claude` 디렉토리(스킬·운영 자산 레이어)로 옮기면서, 접속 방식도 native SSH로 통일했다.

베스천 접속처럼 보안 접근제어 장비를 통과해야 하는 구간일수록 native SSH CLI가 필요했다는 게, 이 두 작업이 같은 시기에 맞물려 진행된 이유였다. 라이브러리 선택 하나가 플랫폼 전체 접속 경로에 영향을 준다는 걸 이 지점에서 다시 확인한 셈이다.

### ✅ API화 + UI 통합 — CLI 스킬을 서버뷰 버튼으로

스킬을 CLI로 직접 실행하는 단계까지는 개발자만 쓸 수 있는 도구였다. 이후 방화벽·베스천 설정 확인 로직을 백엔드 API로 포팅하고, 서버뷰의 작업 메뉴에 통합했다.

- 방화벽·베스천 점검 로직을 API 엔드포인트로 노출
- 서버뷰의 `[작업 ▾]` 드롭다운에 방화벽·베스천 체크 항목을 추가
- 이후 UI 연동을 마무리해서, 개발자가 아니어도 서버뷰에서 버튼 하나로 점검 결과를 확인할 수 있게 만듦

CLI 스킬로 검증까지 끝낸 로직이었기 때문에, API/UI 통합 자체는 상대적으로 매끄럽게 진행됐다. 스킬 단계에서 로직을 충분히 검증해두면, 그 위에 인터페이스를 얹는 작업은 오래 걸리지 않는다는 걸 다시 확인했다.

### ✅ "베스천은 빌드·실행 전용" — 로컬 SSoT 원칙

이 시점에 원칙 하나를 명문화했다 — **베스천 서버는 빌드·실행 전용이고, 소스의 단일 진실 공급원(SSoT)은 로컬(개발 레포)이다.**

앞서 [AppScript 공통화 리팩토링](/posts/appscript-commonization-refactor)에서 "버전 관리는 로컬만 담당하고, 배포 대상 서버는 최신 실행본만 갖는다"는 원칙을 세운 적이 있었다. 이번엔 그 원칙을 베스천이라는 인프라 레이어까지 그대로 확장한 것이다. 베스천에 접속해서 직접 코드를 고치거나 버전을 관리하는 일이 없도록 못을 박아두면, "베스천에만 있는 변경사항"이 생겨서 로컬과 어긋나는 사고를 원천 차단할 수 있다.

같은 맥락에서 DB 권한 부여 스크립트(`run_db_grant`)에도 온프레미스 폴백을 추가했다. 대상 서버로 직결 SSH가 실패하면, 베스천 호스트를 경유해서 재시도하도록 만든 것이다. 베스천이 단순 세팅 대상이 아니라 실제 운영 시 점프호스트 역할까지 겸하게 된 시점이었다.

### ✅ ProxyCommand 점프호스트 전환 — 점검 로직도 경유하게

방화벽·베스천 점검 로직 자체도 이후 ProxyCommand를 경유하도록 통일했다. 고객사 네트워크 구조상 베스천을 거쳐야만 내부망의 대상 서버에 도달할 수 있는 경우가 있었기 때문이다.

```
# ~/.ssh/config 개념 예시 — 점프호스트 경유 접속
Host target-server
    ProxyCommand ssh -W %h:%p bastion-user@bastion-host
    User target-user
```

점검 스크립트가 대상 서버에 직접 붙는 걸 전제로 짜여 있으면, 이런 네트워크 구조에서는 아예 점검 자체가 불가능하다. 점프호스트 경유를 기본값으로 바꾸면서, 베스천을 거쳐야 하는 환경과 직결이 가능한 환경 양쪽 모두를 하나의 로직으로 커버할 수 있게 됐다.

### ✅ STEP6(RDS/RDSH 설치)와 RDS 라이선스(CAL) 카운팅 문제는 서로 다른 이슈였다

초기설정 스크립트의 STEP6(Windows 기능 설치 — Remote Desktop Services + Remote Desktop Session Host)는 그 자체로는 이미 정상적으로 자동화돼 있었다. 이미 설치된 서버에서는 `[SKIP]`으로, 신규 서버에서는 `[OK]`로 결과가 떨어졌고, 완료 후 수동으로 남겨둔 항목도 앞서 정리한 것처럼 MariaDB 권한 부여·서버 재부팅 두 가지뿐이었다.

진짜 골치 아팠던 건 스크립트 바깥, 운영 중이던 다른 베스천 서버에서 터진 **RDS 라이선스(CAL) 카운팅 문제**였다. STEP6가 설치하는 Remote Desktop Session Host 역할은 원격 접속 라이선스(CAL)가 있어야 정상 동작하는데, 이 라이선스 자체가 카운팅되지 않는 별도 사고가 있었다.

**현상**: 해외 POC 시연을 위해 구축해 둔 AWS 베스천 서버(Windows Server 2019 Datacenter, 업무 자동화(RPA) 플랫폼 설치용)에서, PowerShell로 유예 기간을 조회하니 75일밖에 남지 않은 상태였다.

```powershell
# 라이선스 유예 기간 확인
(Invoke-WmiMethod -PATH (gwmi -namespace root\cimv2\terminalservices -class win32_terminalservicesetting).__PATH -name GetGracePeriodDays)
```

**1차 조치 — 정식 라이선스 구매·등록**: RDS User CAL 10 Copy(사용자 단위 라이선스)를 구매하고, 받은 제품 키를 `licmgr.exe`(RD Licensing Manager)에서 `License Pack (Retail Purchase)` 방식으로 등록했다. 이어서 `gpedit.msc`에서 `컴퓨터 구성 > 관리 템플릿 > Windows 구성 요소 > 원격 데스크톱 서비스 > 원격 데스크톱 세션 호스트 > 라이선싱` 경로로 들어가 "지정된 원격 데스크톱 라이선스 서버 사용"을 활성화하고 라이선스 서버 주소로 로컬(자기 자신) 루프백 주소를 지정했으며, "원격 데스크톱 라이선싱 모드"를 `Per User`로 설정했다.

**그런데도 해결되지 않았다**: 정식 라이선스를 등록했는데도 실제 사용자 접속 시 라이선스 발급 건수(Issued)가 계속 0으로 고정됐고, 접속자에게 "60분 후 세션 종료" 경고가 반복해서 떴다.

**원인 분석**: 이 서버는 Workgroup(독립형) 환경인데, 설치된 라이선스는 Per User 방식이었다. Windows 구조상 Per User 라이선스는 발급 시점에 사용자 정보를 기록할 장부(Active Directory)를 참조해서 고유 ID를 대조해야 하는데, Workgroup 환경에는 이 장부(AD) 자체가 존재하지 않는다. 그래서 라이선스 서버가 정식 CAL을 보유하고 있음에도 "누구에게 발급해야 할지 몰라" 발급을 거부하고 임시 유예 모드로 계속 빠진 것이었다.

**해결 — Device CAL로 전환**: 사내 통합 플랫폼 클라이언트가 User CAL 등록 시 필요한 도메인 연동 기능을 제공하지 않아서, 최종적으로는 Device CAL로 우회 적용했다. 진단은 자체 작성한 `RDS_Complete_Diagnostic.ps1`로, 수정 적용은 `RDS_Ultimate_Fix.ps1`로 진행했다. 이 과정에서 세션 종료 시마다 임시 라이선스 오브젝트가 계속 새로 생성되는 부작용도 있었는데, 이 오브젝트는 Windows가 소유권을 SYSTEM으로 보호하고 있어서 권한(Permissions) 창에서 소유자를 Administrators로 바꾸고 Full Control을 부여한 뒤에야 삭제할 수 있었다.

정리하면, STEP6 자체는 스크립트가 이미 잘 자동화해둔 영역이었고, 진짜 사람이 판단해야 했던 부분은 그 위에 얹히는 "왜 이 환경에서는 라이선스가 카운팅되지 않는가"라는 OS·라이선스 아키텍처 진단이었다. 자동화 스크립트의 STEP 하나하나와, 그 스크립트가 절대 대신 판단해줄 수 없는 인프라 레벨 문제는 완전히 다른 층위라는 걸 이번에 명확히 구분하게 됐다.

### ✅ 결과 & 배운 점

| 항목 | 이전 | 이후 |
|------|------|------|
| 세팅 방식 | 매 POC마다 수동으로 처음부터 구성 | 연결→방화벽→초기설정→배포 STEP 스킬 자동화 |
| 스킬 구조 | 단일 스킬(전체 흐름 한 덩어리) | firewall/init-setup 분리 — 부분 재실행 가능 |
| 대상 서버 지정 | 고정/설정파일 의존 | 실행 시점 IP 입력 |
| 접속 방식 | 대상 서버 직결 전제 | native SSH + ProxyCommand 점프호스트 |
| 소스 관리 주체 | 불명확 | 로컬 SSoT 원칙 — 베스천은 빌드·실행 전용 |
| STEP6(Windows 기능: RDS/RDSH) | 서버 관리자에서 수동으로 역할 추가 | 스크립트 STEP6에 편입 — 이미 설치돼 있으면 자동 SKIP |
| RDS 라이선스(CAL) 카운팅 | 발급 건수 0 고정, 60분 후 세션 종료 반복 | Workgroup 환경(AD 부재) 원인 규명 후 Device CAL로 우회 |

베스천 세팅을 스킬로 쪼개는 작업은 처음엔 "그냥 스크립트 하나 자동화하는 일"처럼 보였다. 하지만 실제로 진행해보니 스킬 분리, 접속 계층 전환, 소스 관리 원칙 수립까지 이어지는 인프라 레벨의 의사결정이 계속 뒤따라왔다. 그리고 그 과정에서 배운 가장 중요한 교훈은, 스크립트가 자동화한 STEP과 스크립트가 대신 판단해줄 수 없는 인프라 아키텍처 문제(이번엔 라이선스 카운팅)를 정확히 구분하는 게, 모든 걸 자동화하려는 것보다 더 실무적인 태도라는 것이었다.
