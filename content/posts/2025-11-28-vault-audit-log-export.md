### ✅ 요구사항

> 선임 : 로그 화면에 칼럼이 너무 많아서 뭐가 바뀐 건지 한눈에 안 보임. 상세보기에서 변경 전/후를 diff 형태로 보여줘야 될 것 같음  
> 나 : 서비스마다(IAM, Vault, KMS, Fabric) 로그 구조가 다 다른데 공통으로 뽑아낼 수 있을까요?  
> 선임 : 이미 한 서비스 쪽에서 먼저 해놓은 게 있으니까 그거 기준 잡고 나머지로 확장하면 됨  
> 나 : 넵, BFF에서 prev/next 필드부터 추가하고 상세보기에 diff 컬럼 넣어볼게요

비슷한 시기에 별도로 들어온 요청도 있었다.

> 선임 : 리스트 화면에 있는 데이터, 파일로 내보낼 수 있게 해달라는 요청이 옴. 우선 Excel이랑 PDF부터  
> 나 : 넵, 내보내기 버튼 누르면 메뉴 뜨는 형태로 붙여볼게요

이 요청은 나중에 CSV·HTML까지 늘어나면서 생각보다 오래 끌고 간 작업이 됐다.

### ✅ 왜 변경 전/후 데이터를 구조화했는가

감사 로그의 본질은 "무엇이 언제 어떻게 바뀌었는가"를 증명하는 것이다. 단순히 "수정함"이라는 이벤트 한 줄만 남기면 감사 대응이 안 된다.

- 기존 방식: 로그를 칼럼별로 나열만 함 → 필드가 20개 넘는 리소스(정책류)는 사람이 눈으로 뭐가 바뀌었는지 찾기 어려움
- 해결 방향: 각 리소스의 변경 전(prev)/후(next) 스냅샷을 함께 저장하고, 상세보기에서 필드 단위로 diff를 보여줌
- 예외 기준도 같이 잡아야 했음
  - 암호화된 필드(패스워드류)는 diff 대상에서 제외
  - API로 별도 조회해야만 값을 알 수 있는 필드(정책의 action 데이터 등)도 이번 범위에서 제외
  - 값이 없는 경우와 실제로 빈 값으로 바뀐 경우를 구분해야 diff가 왜곡되지 않음

### 🛠️ 구현 — BFF에서 전/후 데이터 컨버팅

서비스마다 로직을 새로 짜지 않고, 먼저 구현된 서비스의 컨버팅 함수를 기준으로 나머지 서비스에 순서대로 확장하는 방식을 택했다.

```ts
interface AuditLogEntry<T> {
  action: string;
  actor: string;
  prev: Partial<T> | null;
  next: Partial<T> | null;
}

function buildAuditLog<T extends Record<string, unknown>>(
  action: string,
  actor: string,
  prevData: T | null,
  nextData: T | null,
): AuditLogEntry<T> {
  return { action, actor, prev: prevData, next: nextData };
}
```

필드별로 "값이 배열인지, 객체인지, 단순 문자열인지"를 판단해서 공통 diff 렌더링 함수로 분리했다. 리소스마다 로그 페이지를 제각각 만들면 필드 타입이 하나 추가될 때마다 모든 페이지를 손봐야 하기 때문에, 이 판단 로직만큼은 공통 함수 하나로 몰아야 유지보수가 됐다.

### ✅ 왜 Export를 4종이나 만들었는가

- **Excel** — 가장 먼저 요청이 온 포맷. 대부분 실무자가 다운받아서 정렬·필터로 재가공하는 용도
- **PDF** — 그대로 보고서로 출력하거나 첨부해야 하는 경우 필요. 다만 PDF는 페이지 폭이 고정이라 칼럼이 많은 테이블에서 너비가 잘리는 문제를 실제로 겪었다
- **CSV** — PDF의 폭 제한 문제를 근본적으로 우회하는 포맷. 구분자로만 이뤄진 텍스트라서 칼럼이 아무리 많아도 잘리지 않고, Excel과 시트 생성 로직을 공유할 수 있어서 재사용도 쉬웠다
- **HTML** — 다운로드가 아니라 "그 자리에서 넓게 펼쳐보기" 용도. 새 탭에 테이블을 그대로 렌더링해서, 파일을 내려받지 않고 확인만 하면 되는 상황을 위한 뷰였다

포맷을 하나씩 추가할 때마다 "이미 있는 포맷으로 안 되나?"를 먼저 따져봤는데, 결국 각자 존재 이유가 명확해서 넷 다 남기게 됐다.

### 🛠️ 구현 — 포맷별 처리 포인트

Excel/CSV는 같은 라이브러리로 시트를 만들기 때문에, 체크박스·액션 컬럼을 제외하고 화면에 보이는 포맷 그대로 변환하는 함수를 공통으로 뺐다.

```ts
type ColumnType = "text" | "icon-status" | "array";

function formatCellForExport(value: unknown, columnType: ColumnType): string {
  if (columnType === "icon-status") {
    return extractTextFromIconCell(value); // 아이콘은 빼고 텍스트만 추출
  }
  if (columnType === "array" && Array.isArray(value)) {
    return value.join(", ");
  }
  return String(value ?? "");
}
```

PDF는 테이블 스타일(칼럼 너비, 폰트 크기)을 따로 조정해야 했고, 데이터가 없을 때는 아예 출력하지 않도록 예외 처리를 추가했다. 다국어가 적용된 화면이라 내보낸 파일도 그 시점의 언어 그대로 나가야 했는데, 라벨 변환 함수를 하나로 통일해서 포맷이 늘어나도 새로 손댈 곳이 없게 만들었다.

### ✅ Operation 로그 — 별도 관점의 로그

전/후 데이터 diff와는 별개로, 각 서비스가 요청·응답 자체를 남기는 Operation 로그도 급하게 추가됐다. API 명세가 먼저 나온 서비스 하나만 실제 API로 연결하고, 나머지는 화면 골격과 필터만 임시 데이터로 먼저 완성한 뒤 API가 나오는 대로 순차적으로 붙이는 방식을 택했다. 전체가 다 준비될 때까지 기다리기보다, 준비된 만큼 먼저 검증 가능한 상태로 만드는 게 이 단계에선 더 맞는 판단이었다.

### ✅ 전체 진행 순서 요약

1. 리스트 Excel/PDF 내보내기 구현 (아이콘 텍스트 변환, 다국어 적용)
2. CSV 내보내기 추가 (Excel과 시트 생성 로직 공유)
3. HTML View 추가 (다운로드 없이 새 탭 렌더링)
4. 로그 상세보기에 변경 전/후 데이터(diff) 구조화 — 참고 서비스 기준으로 순차 확장
5. 서비스별 Operation 로그 페이지 추가 (API 준비된 것부터 우선 연결)

### ✅ 결과 & 배운 점

| 포맷 | 용도 | 한계 |
|------|------|------|
| Excel | 재가공(정렬·필터) | 스타일 정보까지 포함돼 용량이 큼 |
| PDF | 보고서 출력·첨부 | 페이지 폭 고정 — 칼럼 많으면 잘림 |
| CSV | 재가공 + 넓은 테이블 | 스타일 정보 없음(순수 텍스트) |
| HTML | 다운로드 없는 열람 | 파일로 남지 않음 |

이 작업을 하면서 배운 건 "내보내기 기능은 결국 몇 개를 만드느냐가 아니라, 각 포맷이 실제로 대체 불가능한 이유를 갖고 있는가"라는 점이다. 넷 다 겹치는 것 같아도 막상 하나를 빼면 꼭 그 포맷이 필요한 상황이 남아 있었다.
