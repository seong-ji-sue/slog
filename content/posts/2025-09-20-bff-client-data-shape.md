> **TL;DR** — 클라이언트가 여러 백엔드 API를 원본 그대로 쓰면, 백엔드 응답 형태가 바뀔 때마다 프론트 전체가 흔들린다. 접근관리 콘솔은 BFF(server-common) 레이어에서 백엔드 원본 응답(`{code, name}`)을 클라이언트 전용 뷰모델(`{value, label}`)로 변환해서, 두 쪽의 데이터 형태를 의도적으로 갈라놨다.

난이도 : ★★★☆☆

1️⃣ `BFF 데이터 변환` 2️⃣ `{code,name} → {value,label}` 3️⃣ `API Router 분리`

### ✅ 상황

> 동료 : BFF랑 Client가 서로 다른 데이터 형태를 필요로 하는데, 지금은 백엔드가 주는 형태를 그대로 화면까지 흘려보내고 있어. 이러면 나중에 백엔드가 필드 하나만 바꿔도 프론트 컴포넌트들이 줄줄이 깨질 거야
> 나 : 그럼 BFF 단에서 한번 변환해서 넘기는 게 맞겠네요. 어떤 형태로 통일할까요?
> 동료 : 클라이언트는 `{value, label}` 형태 셀렉트박스 옵션으로 바로 꽂아 쓸 수 있는 형태가 필요해. BFF가 관리하는 code를 value로, 화면에 보이는 이름을 label로 매핑하자

이 작업은 동료가 주도한 것이었고 나는 옆에서 구조를 함께 이해하며 참여했다. 접근관리 콘솔(packages/server-common)이 프론트(client)와 백엔드 API 사이에서 데이터를 한 번 변환해주는 BFF 레이어 역할을 하고 있었는데, 그 변환 규칙 자체가 명시적으로 정리되지 않고 있던 걸 이번에 데이터 형태 분리 작업으로 정리했다.

### ✅ BFF가 왜 필요한가

클라이언트가 백엔드 API를 직접 호출하는 구조라면, 백엔드 응답 스키마가 곧 화면의 데이터 스키마가 된다. 이게 편해 보이지만 실제로는 두 가지 문제를 만든다.

1. **백엔드 응답이 바뀌면 프론트 전체가 흔들린다** — 백엔드가 필드명을 바꾸거나 구조를 바꾸면, 그 데이터를 쓰는 모든 컴포넌트를 찾아가 고쳐야 한다
2. **클라이언트가 원하는 형태와 백엔드가 주는 형태가 항상 같지 않다** — 백엔드는 도메인 모델(예: `code`, `name`)을 주지만, 화면(셀렉트박스, 테이블)은 UI 컴포넌트가 바로 쓸 수 있는 형태(`value`, `label`)를 원한다

BFF(Backend for Frontend)는 이 사이에서 "백엔드 응답을 화면이 바로 쓸 수 있는 형태로 한 번 가공해서 내려주는" 계층이다. 접근관리 콘솔의 `packages/server-common`이 이 역할을 맡고 있었고, 실제 서버 디렉터리 구조도 그 경계를 그대로 보여준다.

```
packages/server-common/src/
├── api/            # 라우팅 계층 — 도메인별 엔드포인트 (application, iam, license, dashboard ...)
├── controllers/    # 실제 데이터 조회·변환 로직
├── middleware/
├── db/
└── utils/
```

`api/`는 도메인별로 나뉜 라우터 계층이고(`application`, `iam`, `license`, `dashboard`, `database` 등), `controllers/`가 실제 백엔드 API를 호출하고 응답을 가공하는 로직을 담고 있다. 클라이언트는 이 구조를 몰라도 되고, 그저 `server-common`이 내려주는 형태만 신뢰하면 된다.

### ✅ 왜 데이터 형태를 분리했나 — `{code, name}` vs `{value, label}`

이번 작업의 핵심은 이거였다.

```
1. BFF서버에서 서버에 보내주는 {code, name} 형태의 데이터를
   Client에서 필요로 하는 {value, label} 형태로 변경
2. code는 BFF가 관리, BFF의 name은 Client의 value와 동일,
   Client의 label는 화면에 보여지는 필드명을 뜻함
```

정리하면 이렇다.

| 계층 | 필드 | 의미 |
|------|------|------|
| 백엔드 원본 | `code` | 시스템 내부에서 쓰는 식별 코드 |
| 백엔드 원본 | `name` | 그 코드에 대응하는 값 |
| BFF 변환 후 | `value` | 셀렉트박스가 선택값으로 쓰는 값(백엔드의 `name`과 동일) |
| BFF 변환 후 | `label` | 화면에 실제로 보여지는 문구 |

```js
// server-common/controllers 어딘가
function toClientOption(backendItem) {
  return {
    value: backendItem.name,   // 백엔드의 name == 클라이언트의 value
    label: backendItem.label ?? backendItem.name,
  };
}
```

백엔드 입장에서 `code`는 시스템이 관리하는 식별자일 뿐이고, 클라이언트 입장에서는 `code`가 뭘 의미하는지 알 필요가 없다. 클라이언트가 필요한 건 오직 "선택했을 때 서버에 뭘 보낼지(`value`)"와 "화면에 뭘 보여줄지(`label`)" 두 가지뿐이다. 이 둘을 분리하지 않고 백엔드 원본 형태(`code`, `name`)를 그대로 화면 컴포넌트에 넘기면, 셀렉트박스마다 "이 화면에서는 `name`을 보여주고 저 화면에서는 `code`를 보여준다"는 식의 임기응변이 생기고, 그게 곧 일관성 없는 화면과 중복 로직으로 이어진다.

### 🛠️ 후속 작업 — API Router 단 Refactoring

데이터 형태를 분리한 뒤에는 라우팅 계층 정리가 이어졌다.

```
h2. 요구사항 정의
server-common에 작성되어 있던 API Router단의 로직을
각각의 서비스 내부로 이동
```

`server-common`이 여러 도메인(application, iam, license, kms 등)의 라우팅 로직을 한곳에 모아 갖고 있었는데, 도메인이 늘어날수록 이 공통 라우터 파일이 비대해지는 문제가 있었다. 그래서 라우팅 로직을 각 도메인 서비스 내부로 옮기고, `server-common`은 정말 여러 도메인이 공통으로 쓰는 것(데이터 변환 규칙, 미들웨어, DB 유틸)만 남기는 방향으로 정리했다. BFF 레이어 자체도 "공통"과 "도메인 개별"의 경계를 계속 다듬어가야 하는 대상이라는 걸 보여준 사례였다.

### ✅ 정리 — 클라이언트 전용 뷰모델 vs 백엔드 원본 응답

이 작업을 관통하는 원칙은 하나다.

> 백엔드가 주는 데이터(도메인 모델)와 화면이 필요로 하는 데이터(뷰모델)는 애초에 목적이 다르므로, 같은 모양일 필요가 없다.

- 백엔드 원본 응답 — 시스템 내부 식별자와 정합성이 중심(`code`, `name`)
- 클라이언트 전용 뷰모델 — UI 컴포넌트가 바로 소비할 수 있는 형태가 중심(`value`, `label`)

이 둘을 BFF 레이어에서 명시적으로 분리해두면, 백엔드가 내부 구현을 바꿔도 그 변화가 BFF의 변환 함수 한 곳만 고치면 흡수되고, 클라이언트 컴포넌트는 전혀 영향을 받지 않는다. 반대로 이 분리가 없으면 백엔드 응답 구조 변경이 곧바로 화면 깨짐으로 이어진다 — 접근관리 콘솔이 이번에 정리한 게 바로 그 완충 지대였다.

#### 🎯 결과 & 배운 점

- BFF는 단순히 "API를 한 번 더 감싸는 계층"이 아니라, 백엔드 도메인 모델과 화면 뷰모델 사이의 번역기 역할을 한다
- `{code, name}` → `{value, label}` 같은 필드 매핑 규칙을 명시적으로 문서화해두면, 이후 합류하는 개발자가 "이 필드가 어디서 왔는지" 헤매지 않는다
- 공통 계층(`server-common`)도 시간이 지나면 비대해지므로, "정말 공통인가"를 주기적으로 다시 물어보고 도메인별로 재분배하는 리팩토링이 필요하다
