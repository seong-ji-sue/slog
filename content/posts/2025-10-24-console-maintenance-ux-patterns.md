> **TL;DR** — 접근관리 콘솔 유지보수 티켓을 몇 달치 쭉 훑어보니 겉모습은 다 다른 버그였는데 원인은 세 갈래로 수렴했다 — 공통 컴포넌트 부재, 각 화면이 필터/유효성 로직을 따로 들고 있는 상태관리 방식, 그리고 반응형을 나중에 붙인 스타일 구조.

### ✅ 상황

> 팀장 : 이번 스프린트도 유지보수 티켓 좀 많다. Audit 필터 이상한 거, 유효성 걸리는 거, 테이블 스타일 깨지는 거...
> 나 : 하나씩 보면 다 별개 버그인데, 계속 보다 보니 몇 개 패턴으로 묶이는 것 같아요
> 팀장 : 그럼 이번엔 그거부터 정리해보자

몇 달치 유지보수 티켓을 개별로 처리하다 보면 "또 이 종류 버그네"라는 느낌이 쌓인다. 이 글은 그 느낌을 개별 버그 나열이 아니라 원인 패턴 3가지로 정리한 기록이다.

### ❌ 패턴 1 — Audit/이력 필터가 매번 따로 논다

Audit(이력 조회) 관련 티켓만 추려도 결이 비슷한 게 여럿이었다.

- Audit 공통 Filter의 EventType 코드가 파스칼 표기인데 실제 이력 데이터는 대문자라 안 맞음
- Image Repository 이력 조회 시 `REGISTERED` 이벤트 타입이 필터 옵션에 없어서 조회 자체가 불가능
- Namespace 목록 조회에 Status 필터가 새로 추가됐는데 화면 반영이 누락
- 복합키 필터(Application Name + Version + Profile + Label)의 단계별 조합 유효성이 빠짐
- 복합키 필터 라벨 텍스트가 길어지면 다이얼로그 박스 밖으로 삐져나감

각 이력 화면(Application, IAM, Image Repository 등)이 "필터 옵션 목록"과 "실제 데이터 코드"를 따로 관리하고 있었다. 백엔드에서 이벤트 타입을 하나 추가하면, 프론트는 그 화면의 필터 컴포넌트를 일일이 찾아가서 옵션을 추가해야 했다. 즉 필터 정의가 화면 개수만큼 흩어져 있었고, 하나가 바뀌면 나머지가 따로 놀 수밖에 없는 구조였다.

**공통 원인**: 이력 화면마다 필터 스펙을 각자 하드코딩하고 있어서, 백엔드 이벤트 타입 변경이 프론트 전체에 자동으로 전파되지 않음.

### ❌ 패턴 2 — 유효성 검사가 화면마다 다른 기준으로 걸림

- Application Information에서 Properties 수정 시 애플리케이션명 필드에 불필요한 유효성이 걸려 수정 자체가 막힘
- Service Certificate 생성 시 name이 선택형(Select) 필드인데 정규식 유효성이 걸려서 저장이 안 됨
- Namespace Entity 이름에 한글 입력이 막혀 있었음(허용 문자셋 누락)
- "unknown-group" 상태인 Workload는 description이 필수가 아닌데 수정 시 필수값 검증에 걸림
- 인증·시크릿 콘솔 연동 프로퍼티(eddy-fabric, eddy-kms 등) 수정 시 Description 미입력이면 무조건 실패

패턴이 뚜렷하다. 유효성 규칙이 "이 필드가 어떤 데이터를 담을 수 있는가"라는 원본 스펙과 무관하게, 화면을 만들 당시의 가정(예: 텍스트 입력이니까 특수문자 금지, description은 항상 필수)이 그대로 굳어 있었다. 필드 자체의 성격(선택형인지, 조건부 필수인지)이 바뀌었는데 유효성 로직은 처음 만들 때 기준에서 갱신되지 않은 것.

**공통 원인**: 유효성 규칙이 필드/화면 단위로 개별 하드코딩돼 있어서, 데이터 성격이 바뀌어도 유효성이 따라가지 못함.

### ❌ 패턴 3 — 반응형·스타일이 나중에 덧붙여진 티가 남

- 테이블 셀 내용이 길면 툴팁이 테이블 영역에 잘려서 보임
- 브라우저 크기를 줄이면 Dialog 컨텐츠가 밖으로 벗어나고, 내부 테이블은 아예 안 보임
- 테이블 칼럼 너비가 화면마다 제각각 고정돼 있고 헤더 정렬 기준도 다름
- 브라우저를 작게/크게 하면 콤보박스가 위/아래로 뜨는 위치가 바뀌는 현상
- Dialog 안에 테이블 데이터가 많아지면 렌더링 항목이 늘어나 브라우저가 과부하 걸림

테이블·다이얼로그가 처음엔 "고정 크기 화면"을 가정하고 만들어졌고, 반응형 대응은 그 위에 나중에 얹은 흔적이 여러 화면에서 개별적으로 보였다. 화면마다 툴팁 처리, 컬럼 너비, 콤보박스 위치 계산을 각자 구현했기 때문에, 어떤 화면은 반응형이 되고 어떤 화면은 안 되는 상태로 갈라져 있었다.

**공통 원인**: 테이블/다이얼로그의 반응형 처리 로직이 공통 컴포넌트가 아니라 화면별 구현으로 흩어져 있었음.

### ✅ 그 외 — 세션/인증 쪽 반복 패턴

- 새 탭을 열었을 때 기존 세션 공유가 안 되던 "중복 로그인" 이슈가 여러 차례 티켓으로 반복됨(탭별 중복 로그인 허용 → 중복 로그인 기능 재확인)
- 로그인 실패 후 새로고침 시 실패 알림창이 값 없이도 다시 뜨는 현상
- 1시간 후 자동 로그아웃되며 토큰 자동 갱신이 되지 않는 문제

이쪽은 세션·토큰 상태를 컴포넌트 로컬 상태나 개별 API 콜 시점에 맞춰 판단하고 있어서, "지금 로그인 상태가 유효한가"를 화면마다 다르게 해석하는 게 원인이었다. 전역에서 하나의 세션 상태를 신뢰할 수 있는 지점이 명확하지 않았던 것.

### ✅ 세 패턴을 관통하는 것

세 가지 패턴 모두 근본적으로 같은 이야기를 하고 있었다.

> "화면 단위로 각자 구현한 로직(필터 스펙, 유효성 규칙, 반응형 스타일, 세션 판단)이 공통 기준 없이 흩어져 있으면, 그중 하나가 바뀔 때마다 나머지가 따라가지 못하고 버그로 드러난다."

버그를 개별로 고칠 때는 "이 화면의 이 필드 문제"로 보이지만, 몇 달치를 모아 보면 "공통화되지 않은 로직이 화면 수만큼 복제돼 있다"는 구조적 문제였다. 이 시기 이후로 Dialog 레이아웃 props 공통화, 테이블 기본 cell·헤더 분리, API 호출 상태를 다루는 공통 훅 작업이 이어지는데, 그 이야기는 다음 글에서 다룬다.

### ✅ 패턴별 근본 원인 정리

| 패턴 | 겉으로 드러난 증상 | 공통 원인 |
|------|---------------------|-----------|
| Audit/이력 필터 | 필터 옵션 누락, 코드 표기 불일치 | 필터 스펙을 화면마다 하드코딩 — 백엔드 변경이 전파 안 됨 |
| 유효성 검사 | 화면마다 다른 기준으로 저장 실패 | 유효성 규칙이 필드/화면 단위로 개별 하드코딩 |
| 반응형·스타일 | 툴팁 잘림, Dialog 레이아웃 깨짐 | 반응형 처리가 공통 컴포넌트가 아닌 화면별 구현으로 흩어짐 |

#### 🎯 결과 & 배운 점

- 버그를 고칠 때 "이 버그 하나"로 끝내지 않고 "같은 원인을 가진 다른 화면이 더 있는가"를 먼저 확인하는 습관이 붙었다
- 반복되는 버그 유형은 회고 시점에 패턴으로 묶어봐야 다음 리팩토링 우선순위가 보인다
- 화면이 늘어날수록 "공통 로직을 어디에 둘 것인가"를 먼저 정하지 않으면, 그 사이 공백은 QA 티켓으로 채워진다
