> **TL;DR** — [판정엔진 도입기](/posts/sap-gui-login-verdict-engine)에서 다룬 "6/6 성공"이 거짓이었던 사고를, 판정엔진 코드 하나 고치는 걸로 끝내지 않았다. 같은 사고가 다른 사람·다른 세션에서 반복되지 않도록, "무엇을 근거로 성공이라 말할 수 있는가"를 Evidence Grade A/B/C 체계로 정리해서 Claude Code 스킬(SOP)로 박제했다. 이번 글은 그 스킬의 실제 내용과, 왜 코드 수정만으로는 부족했는지를 다룬다.

난이도 : ★★★★☆

1️⃣ `Evidence Grade` 2️⃣ `SOP as Skill` 3️⃣ `회귀 방지`

### ✅ 코드는 고쳤는데, 왜 스킬까지 만들었나

앞선 글에서 판정엔진(PASS/FAIL/SUSPECT/INCONCLUSIVE)을 도입해서 "성공 여부 판정" 로직 자체의 버그는 고쳤다. 그런데 코드를 고치는 것과, **다음에 이 코드를 쓰는 쪽(나 자신을 포함해서, 혹은 다른 세션의 AI 에이전트)이 판정 결과를 올바르게 "보고"하는 것**은 별개의 문제였다.

판정엔진이 아무리 정확하게 `PASS`/`SUSPECT`/`FAIL`을 뱉어도, 그걸 받아서 사람에게 전달하는 쪽이 "일단 로그에 성공 마커가 있으니 성공이라고 하자"고 판단해버리면 사고는 똑같이 재발한다. 실제로 사고의 3계층 원인 중 마지막 계층("결과를 받아본 나도 로그 마커만 보고 독립 증거 없이 성공을 단정")은 코드 문제가 아니라 **판단 절차의 문제**였다. 절차의 문제는 코드로 막을 수 없고, 절차(SOP)로 막아야 한다는 게 이번 결론이었다.

### ✅ Evidence Grade — "무엇을 근거로 성공이라 부를 수 있는가"

그래서 만든 게 `appscript-verdict`라는 Claude Code 스킬이다. 핵심은 성공 주장의 근거를 3등급으로 나눠서, 등급에 따라 쓸 수 있는 말을 다르게 강제한 것이다.

| 등급 | 정의 | 예시 |
|------|------|------|
| **A — 독립 직접 증거** | 스크립트 자기 보고와 무관하게, 대상 시스템 자체에서 확인되는 증거 | 로그인 후 대상 DB/앱에 실제 쿼리 성공, 화면 캡처로 확인된 로그인 상태, 대상 시스템의 세션 기록 |
| **B — 스크립트 마커** | `verdict.py`가 로그를 판정해서 나온 결과 — exit code 일치, 모순 없음, 부정 증거 없음 | `##SUCCESS##` + exitCode=0, verdict=PASS |
| **C — 정황 증거** | 실제 로그인/대상 시스템 결과를 확인해주지 않는 간접 신호 | 작업관리자에 프로세스가 떠 있음, SSH 명령이 에러 없이 리턴됨 |

그리고 등급별로 **말할 수 있는 것과 없는 것**을 못박았다.

- **C 단독으로는 성공을 절대 보고할 수 없다.** "미검증 — 정황 증거뿐"이라고만 말해야 한다
- **B 단독이면 "스크립트 마커 기준 성공, 그 이상은 미검증"이라고 명시해야 한다.** 조건 없는 "성공"으로 격상시키면 안 된다 — 무엇이 검증 안 됐는지("대상 DB 세션은 독립적으로 확인 안 함" 등)를 구체적으로 밝혀야 한다
- **A, 또는 A+B가 함께 있을 때만 조건 없는 성공으로 보고할 수 있다**
- `verdict.py`가 `SUSPECT`/`FAIL`/`INCONCLUSIVE`를 뱉으면, 로그가 아무리 "성공처럼 보여도" 절대 성공으로 보고하면 안 된다

지난 사고의 원인이었던 "로그에 `success`라는 단어가 있으면 성공"이라는 판단은, 이 체계에서는 아예 성립하지 않는다 — 그건 C등급도 못 되는, 등급 미달의 근거다.

### ✅ 스킬로 만든 이유 — "언제 이걸 써야 하는가"까지 못박기

이 내용을 문서 한 장으로 남겨두는 것과, Claude Code 스킬로 만들어서 특정 트리거에 자동으로 호출되게 하는 것은 실무에서 차이가 크다. 스킬 정의에는 "언제 반드시 이 SOP를 거쳐야 하는가"도 함께 명시했다.

- 앱스크립트 실행 API(`/api/servers/{id}/run/{folder}`) 호출 직후
- AppScript 실행 결과에 대해 "성공"/"실패"/"N건 중 M건 통과" 같은 문장을 쓰기 직전
- 다른 세션·다른 에이전트가 작성한 실행 결과 보고서를 검토하고 그걸 근거로 뭔가를 하기 전

문서로만 있으면 "이거 언제 봐야 하더라"를 매번 사람이 기억해야 하지만, 스킬로 등록해두면 저 트리거 상황에서 놓치지 않고 호출된다는 전제가 생긴다. 그리고 스킬 안에 "여러 앱 결과를 절대 'N/M passed' 한 줄로 뭉뚱그리지 말고, 앱마다 판정+증거등급을 각각 명시하라"는 규칙도 넣었다 — 뭉뚱그린 요약 자체가 지난 사고의 표면적 증상이었기 때문이다.

### ✅ 정직하게 밝히는 것 — 아직 다 안 끝났다

이 스킬이 잘 자리 잡았는지는 코드 리뷰만으로는 알 수 없어서, 실제 테스트 스위트 상태를 확인해봤다.

- 루트 레벨 테스트: 마지막 실행 기준 실패 0건
- 백엔드 테스트 스위트(406개): 마지막 실행 기준 **1건(`test_sse_start_event`) 여전히 실패 상태로 남아있음**

전부 그린이라고 말하고 싶었지만, 그건 이 글에서 스스로 세운 원칙("B등급 근거만으로 조건 없는 성공을 주장하지 말라")을 어기는 일이 된다. 406개 중 405개가 통과했다는 건 실제 근거지만, 남은 1건이 무엇 때문에 실패하는지는 이번 조사에서 확인하지 못했다 — 그러니 이 스킬 체계 자체가 "완결됐다"고 말하는 대신, "핵심 판정 로직은 검증됐고, 주변 테스트 1건은 아직 미해결"이라고 정확히 선을 긋는 게 맞다.

### ✅ 결과 & 배운 점

| 항목 | 이전 | 이후 |
|------|------|------|
| 성공 판정 기준 | 로그에 특정 단어가 있으면 성공 | Evidence Grade A/B/C — 등급별로 쓸 수 있는 말이 다름 |
| 재발 방지 방식 | 판정엔진 코드 수정 | 코드 수정 + 판단 절차 자체를 스킬(SOP)로 박제 |
| 보고 방식 | 여러 앱 결과를 "N/M passed"로 뭉뚱그림 | 앱마다 판정 + 증거등급을 개별 명시 |
| 테스트 상태 | 확인 안 함 | 루트 0건 실패 확인, 백엔드 1건 미해결로 정직하게 남김 |

같은 실수가 코드 밖(판단·보고 절차)에서도 반복될 수 있다는 걸 이번에 배웠다. 버그를 고치는 것과, "이 사람(혹은 에이전트)이 다음에도 같은 실수를 하지 않게 만드는 것"은 다른 층위의 작업이다. 후자는 코드 리뷰가 아니라 SOP와 그 SOP를 강제하는 장치(스킬의 트리거 조건)로 풀어야 한다는 게, 이 사고 전체를 관통하는 결론이었다.
