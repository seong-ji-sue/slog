> **TL;DR** — 여러 개의 독립 배포 콘솔(키 관리, 인증, 시크릿 볼트 등)을 한 저장소에서 관리해야 해서, `apps/*`(배포 단위)와 `packages/*`(공유 코드)로 나눴다. 공유 코드도 다시 클라이언트 전용·서버 전용·공통 3단으로 쪼갰다.

### ✅ 요구사항

> 사수 : 우리가 관리해야 하는 콘솔이 하나가 아니라 여러 개야 — 키 관리, 인증, 시크릿 볼트 같은 것들. 근데 로그인 로직이나 API 호출 방식, 공통 컴포넌트는 다 똑같이 가져가야 하거든  
> 나 : 그럼 앱마다 레포를 따로 파는 것보다, 하나의 저장소로 묶고 공통 로직은 별도 패키지로 분리해서 각 앱이 가져다 쓰는 구조가 맞을 것 같아요  
> 사수 : 그래, 그 구조로 한번 잡아봐

프로젝트 초기 단계였고, 아직 앱이 하나둘 늘어나기 전이었지만 "이후에 앱이 여러 개로 늘어날 것"이 이미 정해진 전제였다. 그래서 처음부터 여러 앱을 전제로 한 저장소 구조를 잡아야 했다.

### ✅ 왜 모노레포인가

여러 앱이 로그인/인증 흐름, API 클라이언트, 폼 검증, 테이블 컬럼 정의 같은 걸 그대로 공유해야 하는 상황이었다. 이럴 때 레포를 따로 두면 생기는 문제가 있다.

- 공통 로직(인증, API 호출, 폼 검증)을 앱마다 복붙하거나 별도 배포된 패키지로 버전 관리해야 함
- 각 레포가 서로 다른 버전의 공통 패키지를 참조하게 되면, 버그가 나도 어느 버전에서 고쳐졌는지 추적이 어려움
- 공통 로직 하나 고칠 때마다 앱 개수만큼 배포·동기화를 반복해야 함

하나의 저장소 + workspaces 구조면 공통 패키지를 수정한 즉시 심볼릭 링크로 연결된 모든 앱에서 바로 반영된다. 별도 배포 없이도.

### ❌ 기존에 없던 것 (레포를 따로 뒀다면)

- 앱마다 독립된 레포 → 공통 코드 동기화 수단이 없음
- 로그인/인증 로직을 앱마다 손으로 맞춰야 함
- 공통 컴포넌트(테이블, 폼)를 앱별로 미묘하게 다르게 구현하게 될 위험

### ✅ 최종 구조

```
apps/
  iam/        # IAM 콘솔
  vault/      # 시크릿 볼트 콘솔
  kms/        # 키 관리 콘솔
  client/     # 통합 클라이언트 앱
packages/
  common/          # 클라이언트·서버 공용
  client-common/   # 브라우저 전용 공용
  server-common/   # Node.js 전용 공용
```

- `apps/` — 독립적으로 실행·배포되는 단위
- `packages/` — 여러 앱이 import해서 쓰는 라이브러리

### 🛠️ 공유 코드를 왜 3단으로 쪼갰나

공유 코드를 하나의 `common` 패키지로 몰아넣지 않고 세 단으로 나눈 이유는 실행 환경이 다르기 때문이다.

- **`common`**: 클라이언트·서버 어디서든 쓰이는 것 — 에러 코드, 라벨/문구, 옵션 상수, API 요청/응답 타입 등 "런타임 환경에 의존하지 않는 순수 로직"
- **`client-common`**: 브라우저 전용 — 커스텀 훅, 폼 검증 규칙, 테이블 컬럼/셀 정의, axios 인터셉터, 전역 스타일
- **`server-common`**: Node.js 전용 — controller, middleware, DB 접근, redis, 인증 유틸

이유는 단순하다. `common`에 client·server 전용 코드가 섞이면, 서버 코드에서 브라우저 전용 API를 import하다가 빌드가 깨지거나, 반대로 클라이언트 번들에 서버 전용 로직(DB 접근 코드 등)이 끼어들어가 번들 크기가 쓸데없이 커지는 문제가 생긴다. 실행 환경 경계를 패키지 경계로 그대로 옮긴 셈이다.

### 🛠️ Yarn Workspaces + Lerna 조합

```json
// package.json
{
  "private": true,
  "workspaces": ["packages/*", "apps/*"],
  "scripts": {
    "start": "lerna run start"
  }
}
```

- `workspaces`가 심볼릭 링크로 패키지 간 의존을 연결해줘서, 로컬에서 공유 패키지를 수정하면 별도 배포 없이 바로 앱에서 최신 코드를 참조한다
- Lerna는 이 프로젝트에서 버전 관리(npm 배포용)보다는 "여러 패키지에 걸쳐 스크립트를 한번에 실행"하는 러너로 사용했다 — `lerna run start`처럼 각 앱의 스크립트를 한 명령으로 묶어 실행

```ts
// packages/client-common/package.json 발췌
{
  "name": "@console/client-common",
  "exports": {
    "./hooks": "./src/hooks/index.ts",
    "./validation": "./src/validation/index.ts",
    "./column": "./src/column/index.tsx"
  }
}
```

`exports` 필드로 하위 경로별 진입점을 명시해두면, 앱에서 `@console/client-common/hooks`처럼 필요한 것만 골라 import할 수 있어서 전체 패키지를 통째로 불러오는 것보다 트리쉐이킹에 유리하다.

### ✅ 결과 & 배운 점

- 이후 진행한 클라우드 Secret Engine 관리 페이지, IAM Entity/Role 구조를 만들 때 공통 폼 검증·테이블 컬럼 정의를 그대로 재사용할 수 있었음
- 처음엔 3단 분리가 과한가 싶었는데, 앱이 여러 개로 늘어나면서 "이 코드가 클라이언트 전용인지 서버 전용인지 공용인지"가 명확히 갈렸고 유지보수가 오히려 편해짐
- 모노레포 자체보다, 공유 코드를 실행 환경 기준으로 쪼갠 게 이후 확장에 더 크게 기여함
