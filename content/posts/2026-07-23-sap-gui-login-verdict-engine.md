> **TL;DR** — 동남아 고객사 POC를 위해 SAP GUI 자동 로그인 스크립트를 세 번 갈아엎었다. 그런데 진짜 무서운 사고는 로그인 자체가 아니라 다른 데서 터졌다 — CS 앱 6종을 검증하고 "6/6 성공"이라고 보고했는데, 실제로는 절반이 실패였다. 원인을 3개 계층으로 쪼개 분석하고, "성공 여부 판정" 자체를 스크립트와 하네스에서 떼어내 별도 판정엔진(PASS/FAIL/SUSPECT/INCONCLUSIVE)으로 구조화했다.

난이도 : ★★★★★

1️⃣ `SAP GUI Scripting` 2️⃣ `이미지매칭 폴백` 3️⃣ `거짓 성공 판정 차단`

### ✅ 요구사항

> 선임 : 동남아 고객사 POC에 SAP 앱 자동 로그인 시연을 넣기로 했어. 근데 우리가 그 고객사 SAP 서버엔 접근을 못 해  
> 나 : 그럼 뭘로 테스트하나요?  
> 선임 : 우리 쪽에 SAP 테스트 서버부터 세우고, 거기서 먼저 검증해야지  
> 나 : 넵, 환경 구축부터 하고 SAP GUI Scripting 조사하겠습니다

업무 자동화(RPA) 플랫폼에 새 앱스크립트를 하나 추가하는 일이었는데, 끝나고 보니 이 글 시리즈에서 다룬 다른 앱들("VNC", "해상도·DPI 대응")과는 무게가 완전히 달랐다. SAP 자체의 로그인 방식이 세 번 바뀐 것도 있지만, 그 과정에서 우리 자동화 전체를 관통하는 구조적 결함 하나를 발견하고 고쳤기 때문이다.

### ✅ SAP 테스트 환경부터 직접 구축

- 고객사 SAP 서버에는 접근할 수 없어서, 자체 SAP ABAP Platform Trial(A4H, HANA) 단일 구성 테스트 서버를 VM에 직접 세우고 라이선스 등록까지 했다
- SAP GUI for Windows 7.70 클라이언트도 별도로 설치
- 자동화 스크립트를 짜기 전에 "테스트할 수 있는 환경을 만드는 것"부터가 이미 하루치 일이었다는 걸 이번에 체감했다 — 자동화 난이도를 가늠할 때 실제 스크립트 분량보다 이 사전 준비 비용을 과소평가하기 쉽다

### ✅ SAP GUI Scripting 제약 발견 → 처음부터 폴백을 설계에 넣음

SAP GUI Scripting(COM 인터페이스)으로 로그인 필드를 제어하려면 서버 파라미터(`sapgui/user_scripting=TRUE`)가 켜져 있어야 한다. 이건 우리 쪽에서 통제할 수 없는 전제조건이다 — 고객사 Basis팀의 협조가 있어야 켜지는 서버측 설정이기 때문이다.

그래서 설계 단계에서부터 "협조가 안 되면 어떻게 할 것인가"를 같이 넣었다. 답은 OpenCV 이미지매칭(특징점 방식) 폴백이었다. v2.0에서는 로그인 흐름을 3단계 폴백 체인으로 짰다 — COM Scripting → 이미지매칭 → 키보드 입력. config의 `LoginMethod`(auto/scripting/image) 값으로 어떤 경로를 강제할지도 제어할 수 있게 했다.

### ✅ v1.0 — x64 COM 경로와 ConnString 접속

- x64 환경에서 흔히 쓰는 `SapROTWr`가 32bit 전용이라 그대로는 붙지 않았다. `ObjGet("SAPGUI")`를 우선 시도하고 실패하면 `SapROTWr`로 폴백하는 방식으로 우회했다
- `OpenConnectionByConnectionString`을 채택해서, SAP Logon 엔트리를 미리 등록해둘 필요 없이 config의 Host/SystemNr/Router 값만으로 접속하도록 했다
- 클라이언트 스크립팅 사용에 필요한 레지스트리 3키를 자동으로 설정하는 함수(`EnsureSapClientScripting`)를 넣어서, 배포 대상 장비마다 수동 설정을 반복하지 않게 했다

이 버전으로 POC-ready 상태를 만들었지만, 여기서 끝나지 않았다.

### ✅ v3.0 — sapshcut 직접 로그인으로 전면 전환

v1.0/v2.0은 COM 인터페이스로 SAP Logon Pad를 조작하는 방식이었는데, 이후 `sapshcut.exe`라는 SAP 자체 커맨드라인 로그인 도구로 완전히 갈아엎었다.

- `-conn` 파라미터가 SAP 공식 문서상 미지원이라는 걸 확인하고, `-sysname` + `-guiparm` 조합으로 전환 — 사전에 등록된 SAP 서버 목록(landscape)에 의존하지 않고 접속 가능
- SAP GUI Security 팝업(스크립팅 관련 보안 경고창)을 `{LEFT}` + `{ENTER}`로 자동 Allow 처리
- v2.0의 COM/이미지매칭/키보드 3단 폴백 코드, 전용 라이브러리 파일, OpenCV UDF까지 전부 들어내고 슬림하게 리라이트

폴백을 통째로 걷어내는 게 맞는 판단인지 스스로도 의심했다. 그런데 sapshcut 방식은 서버 스크립팅 설정 자체에 의존하지 않는 완전히 다른 경로라서, v2.0에서 폴백이 필요했던 이유(서버 스크립팅이 꺼져 있을 가능성) 자체가 사라졌다. 존재 이유가 없어진 코드를 남겨두는 것도 부채라고 판단해서 정리했다.

### ✅ 멀티 로그온 다이얼로그 — 또 하나의 숨은 분기

검증 중에 "License Information for Multiple Logons" 다이얼로그가 예고 없이 튀어나왔다. 기본 선택은 "세션 종료"인데, 자동화 스크립트가 이걸 그대로 두면 방금 만든 로그인 세션이 끊겨버린다.

기존에 쓰던 `WinWaitAdvanced`는 특정 제목의 창 하나를 블로킹으로 기다리는 구조라, "뜰 수도 있고 안 뜰 수도 있는" 조건부 다이얼로그에는 맞지 않았다. 그래서 폴링 루프 안에서 여러 창 제목을 번갈아 확인할 수 있는 헬퍼를 새로 만들었다.

```autoit
; 단발성 가시 창 탐색 - 대기 없이 현재 떠 있는 창만 확인 (부분일치, 대소문자
; 무시). 찾으면 창 핸들, 없으면 0 반환. 폴링 루프 안에서 여러 제목을 번갈아
; 확인할 때 사용 (WinWaitAdvanced는 단일 제목 블로킹 대기 전용)
Func WinFindVisible($sTitle)
    Local $aList = WinList(StringFormat("[REGEXPTITLE:(?i)(.*%s.*)]", $sTitle))
    For $i = 1 To $aList[0][0]
        If BitAND(WinGetState($aList[$i][1]), 2) Then Return $aList[$i][1]
    Next
    Return 0
EndFunc
```

이 창이 뜨면 `{UP}{ENTER}`로 "Continue with this logon"을 선택하도록 처리했다.

### ✅ 진짜 사고 — "6/6 성공"의 절반이 거짓이었다

여기까지는 SAP 하나에 국한된 이야기였다. 그런데 CS 타입 앱 6종을 배포·실행 검증하고 "6/6 전부 로그인 성공"이라고 보고했는데, 사용자가 화면 캡처로 반증했다 — 실제로는 최소 3건이 실패였다.

원인을 파고들어 보니 한 계층의 문제가 아니라 3개 계층에 걸쳐 있었다.

1. **AutoIt 스크립트 자체가 거짓 `##SUCCESS##`를 기록**했다. Toad는 접속에 실패해도 창 타이틀에 계정 ID가 그대로 남는 UI 특성이 있는데, 타이틀 매치만으로 성공을 확정하던 로직이 이걸 성공으로 오판했다. SAP는 보안 팝업을 영문 고정 문자열로 찾다가 한글 환경에서 못 찾고, 그냥 다음 단계로 넘어가며 실패를 조용히 삼켰다
2. **판정 로직이 PowerShell 문자열 매치에 박혀 있었다.** `'success'` 부분문자열 매치 + exitCode 교차검증 없음 + mtime 기준 최신 로그 1개만 채택 — 실행 모드(로컬/연동)가 다른 예전 성공 로그를 잘못 채택할 수 있는 구조였다
3. **결과를 받아본 나도 로그 마커만 보고 독립 증거 없이 성공을 단정**했다. 마커가 있으니 성공이라고 믿었지, 다른 증거로 교차검증하지 않았다

이 셋 중 하나만 고쳐서는 재발을 막을 수 없다고 판단했다. 스크립트를 아무리 정교하게 고쳐도 언젠가 또 다른 앱에서 같은 패턴의 오탐이 나올 거고, 사람이 매번 로그를 의심하며 읽는 것도 지속 가능한 방법이 아니었다.

### ✅ 판정엔진 도입 — PASS / FAIL / SUSPECT / INCONCLUSIVE

그래서 "성공 여부를 판정하는 로직" 자체를 스크립트와 하네스에서 떼어내 별도 순수 함수 모듈로 뽑아냈다. 로그 텍스트를 입력받아 네 가지 중 하나로 판정한다.

- **마지막 실행 블록만 판정 대상으로 한정** — 과거 실행의 마커를 잘못 채택하던 문제를 원천 차단
- **`##SUCCESS##` / `##FAIL##` 마커는 정확 매치만 인정** — 부분 문자열 매치로 인한 오탐을 구조적으로 막음
- **SUCCESS 마커가 있어도 부정 증거가 검출되면 SUSPECT로 강등**

```python
# 부정 증거 패턴 — ##SUCCESS## 마커가 있어도 이 패턴이 블록에서 발견되면
# SUSPECT 로 강등한다.
NEGATIVE_EVIDENCE_PATTERNS: list[tuple[re.Pattern, str]] = [
    (re.compile(r"ORA-\d{4,5}"), "Oracle 에러코드 — 실제 오탐 사고와 동일 패턴"),
    (re.compile(r"logon denied", re.IGNORECASE), "logon denied"),
    (re.compile(r"팝업\s*없음"), "팝업 없음 — 보안 팝업 로케일 불일치 사고와 동일 패턴"),
    (re.compile(r"실패"), "실패 문구"),
    # ... 이하 access denied / authentication failed / 타임아웃 등
]

# 정상 흐름에서 양성(benign)으로 나올 수 있는 문구는 부정 증거로 취급하지 않는다.
# OpenCV 이미지매칭 폴링 루프는 아직 화면에 나타나지 않은 템플릿에 대해
# 매 프레임 "이 이미지는 존재하지 않습니다"를 정상적으로 남기기 때문이다.
BENIGN_EXCEPTION_PATTERNS: list[re.Pattern] = [
    re.compile(r"이\s*이미지는\s*존재하지\s*않습니다"),
]
```

이 benign exception 목록이 없었다면, 이미지매칭 방식으로 도는 앱들은 정상 실행 중에도 SUSPECT로 오판됐을 것이다. 판정 로직을 만들 때는 "실패로 봐야 할 것"만큼이나 "실패처럼 보이지만 실패가 아닌 것"을 구분하는 게 중요하다는 걸 여기서 배웠다.

응답에는 `verdict` / `reasons` / `evidence_lines` / `warnings`를 함께 실어서, 판정 근거를 사람이 다시 읽을 수 있게 했다. 비밀번호 토큰은 evidence에서 마스킹 처리했다.

이 판정엔진 도입과 함께, CS_Toad와 CS_SAP 각각에서 실제로 오탐을 만들던 지점도 같이 고쳤다.

- **CS_Toad**: 접속 실패해도 타이틀에 계정 ID가 남는 문제라, 타이틀 매치 이후 곧바로 성공 확정하지 않고 몇 초간 정착 대기하며 에러 팝업을 폴링하는 함수를 별도로 넣었다. Oracle 에러 코드가 검출되면 그때 실패로 확정한다
- **CS_SAP**: 보안 팝업 대기를 영문 고정 문자열이 아니라 로케일 무관 정규식으로 바꿔서, 한글 환경에서도 팝업을 놓치지 않게 했다. 팝업이 일정 시간 후에도 닫히지 않으면 이제는 실패로 판정한다

### ✅ 결과 & 배운 점

| 항목 | 이전 | 이후 |
|------|------|------|
| SAP 로그인 방식 | COM Scripting + 3단 폴백 | sapshcut 직접 로그인 (필요 시 이미지매칭 폴백 별도 유지) |
| 성공 판정 방식 | PowerShell 부분문자열 매치 | 순수 함수 판정엔진(PASS/FAIL/SUSPECT/INCONCLUSIVE) |
| 판정 대상 로그 | mtime 최신 1개 | 실행 시작 이후 갱신된 전체 후보 |
| 오탐 사례 대응 | 타이틀 매치 = 성공 확정 | 에러 팝업 폴링 + 정확 매치 + 부정 증거 검출 |

"성공"이라는 단어를 스크립트가 스스로 판단하게 두면 안 된다는 걸 이번에 제대로 배웠다. 자동화는 결과를 만들어내는 것 못지않게, 그 결과가 진짜인지 증명하는 책임까지 같이 짊어져야 한다. 로그에 성공 마커가 찍혀 있다는 것과, 실제로 성공했다는 것은 다른 이야기다 — 이 둘 사이의 간격을 메우는 게 이번 작업의 진짜 핵심이었다.
