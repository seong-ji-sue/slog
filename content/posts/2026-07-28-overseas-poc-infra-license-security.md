### ✅ 상황 — 해외 POC마다 반복되는 인프라 삽질

> 담당 이사님 : 이번엔 동남아 고객사 POC 지원 건이야. Bastion 세팅부터 스크립트까지 다 준비해야 됨
> 나 : 이번이 몇 번째죠?
> 담당 이사님 : 벌써 세 번째인데, 매번 인프라 문제로 시간을 다 씀
> 나 : ...일단 원인부터 하나씩 정리해볼게요

업무 자동화(RPA) 플랫폼을 해외 고객사에 소개할 때는 실제 환경에 Bastion(베스천) 서버와 사내 통합 플랫폼을 설치하고, 그 위에서 고객사가 쓰는 애플리케이션(웹사이트, SQL Developer, Toad 등)의 로그인·조작을 자동화하는 스크립트를 붙여서 시연한다. 동남아 금융 고객사의 15개 웹 애플리케이션 자동화 지원, 동남아 고객사의 SQL Developer·Toad 자동화 POC, 그리고 그 이후 이어진 몇 차례의 추가 POC까지 — 짧은 기간에 여러 건이 겹치면서 매번 새로운 환경 이슈가 튀어나왔다.

처음엔 이게 "이번 POC만의 특수한 문제"라고 생각했는데, 몇 건을 반복하고 나니 패턴이 보였다. 자동화 스크립트 자체는 이미 검증된 것들이었고, 발목을 잡는 건 항상 그 아래 인프라 레이어 — 방화벽, 라이선스, 보안 정책이었다.

### ✅ 왜 사소해 보이는 이슈들이 실전 배포를 막는가

동남아 금융 고객사 건에서는 Bastion 서버의 라이선스 문제로 접근 자체가 막혀서 개발을 진행하지 못한 적도 있었다. 방화벽이 도메인으로 열려 있지 않거나, 접속할 웹사이트의 로그인 IP가 막혀 있는 식의 이슈도 반복됐다.

스크립트 로직은 이미 몇 번이나 검증된 코드다. 그런데 정작 POC 현장에서 막히는 건 항상 "그 서버에 진짜로 접속이 되는가", "그 계정으로 그 프로그램을 실행할 권한이 있는가" 같은, 코드 바깥의 문제였다. 자동화 로직 자체보다 그 로직이 돌아갈 수 있는 환경을 만드는 데 더 많은 시간이 들어간다는 걸 이번에 확실히 체감했다. 그래서 이번 글은 스크립트 로직이 아니라, 그 아래 인프라·라이선스·보안 정책 이슈들을 어떻게 하나씩 걷어냈는지에 집중한다.

### ✅ Bastion 세팅 시간 — 가장 오래 걸리던 작업을 자동화로 넘기다

POC 때마다 가장 오래 걸리는 작업은 사실 자동화 스크립트 개발이 아니라 "Bastion 서버 세팅" 자체였다. 물리 서버나 VM에 Windows를 올리고, 방화벽을 열고, 사내 통합 플랫폼(Bastion + 메인 서버)을 설치하고, 연동까지 확인하는 과정을 매번 처음부터 반복하고 있었다.

이 문제는 이후 AWS EC2 환경에 자동 세팅 파이프라인을 구축하면서 해결했다 — 연결→방화벽→초기설정→배포를 STEP 단위 스킬로 쪼갠 자동화 과정, 그리고 그 과정에서 세운 원칙들은 별도 글에서 자세히 다뤘다: [베스천 자동 세팅 스킬화](/posts/bastion-automation-skillify).

이 파이프라인을 만들고 나서부터는, 신규 POC가 잡히면 바로 배포 가능한 환경을 준비해두고 스크립트 개발에만 집중할 수 있게 됐다. 매번 몇 시간씩 걸리던 "환경부터 만들기" 작업이, 이후로는 반복 가능한 절차로 정리됐다.

### ✅ UAC 알림창 — 원인은 게시자 미확인, 해결은 그룹 정책

AWS EC2로 구성한 환경에서 자동화 스크립트가 애플리케이션을 실행할 때마다, 전에는 없던 "이 앱이 디바이스를 변경할 수 있도록 허용하시겠습니까?"라는 사용자 계정 컨트롤(UAC) 알림창이 뜨기 시작했다. 스크립트는 이 팝업 앞에서 그대로 멈춰버렸다.

- **원인**: 실행 대상 프로그램이 게시자 미확인(Unknown Publisher) 상태이거나 관리자 권한을 요구하는 동작을 포함하고 있어서, Windows 보안 정책상 사용자 승인 단계가 강제로 끼어드는 것이었다
- **해결**: 로컬 그룹 정책 편집기(`컴퓨터 구성 > Windows 설정 > 보안 설정 > 로컬 정책 > 보안 옵션` 경로)에서 `사용자 계정 컨트롤: 기본 관리자 승인 모드에서 모든 관리자 실행` 옵션을 비활성화. 관리자 그룹 계정이 별도 승인 절차 없이 프로그램을 실행할 수 있도록 환경 자체를 조정했다

물리 서버에서는 한 번도 겪지 않았던 문제가 클라우드 환경으로 옮기자마자 나타났다는 게 포인트다. 같은 자동화 스크립트라도 실행되는 인프라가 바뀌면 그 위에 깔린 OS 보안 기본값도 달라질 수 있다는 걸 새로 배웠다.

### ✅ SQL Developer의 C드라이브 접근 — 레지스트리로는 못 막는 이유

RDP로 Bastion에 접속해서 SQL Developer를 실행했을 때, 파일 탐색기(Save As 등)를 통해 서버의 로컬 C드라이브에 접근할 수 있다는 게 확인됐다. 관리자 계정을 제외한 일반 사용자 세션에서는 이 접근을 원천 차단해야 했다.

- **선행 이슈**: 관리자를 제외하는 그룹 정책(Non-Administrators 대상 GPO)을 걸어뒀는데도 일반 사용자에게 제한이 걸리지 않는 현상이 먼저 있었다. 추적해보니 RDP 접속용으로 만든 일반 계정들이 생성 시점에 윈도우 로컬 Administrators 그룹에 기본으로 포함돼 있었다 — 윈도우 OS 입장에서는 이 계정들이 이미 "관리자"였기 때문에, "관리자가 아닌 사용자"를 대상으로 건 제한 정책 자체가 조용히 무시되고 있었다. 계정을 Administrators 그룹에서 빼는 것부터 다시 잡아야 했다
- **1차 시도 실패 원인**: 기존에 적용해두었던 레지스트리 기반 하드닝 정책(`NoDrives`, `NoViewOnDrive`)은 C++ 기반 애플리케이션에는 먹혔지만, SQL Developer 같은 Java 기반 앱은 `JFileChooser`를 통해 NTFS에 직접 접근하기 때문에 Windows 레지스트리 정책 자체를 무시했다
- **해결**: 레지스트리가 아니라 NTFS 권한 레벨에서 물리적으로 차단하는 방향으로 전환. 로그온 시 실행되는 하드닝 스크립트에 다음 한 줄을 추가했다

```powershell
# C 드라이브 루트 접근 물리적 차단 — 일반 사용자 그룹만 대상
icacls "C:\" /deny "일반사용자그룹:(CI)(NP)RD" | Out-Null
```

- `RD`(목록 보기 권한)만 거부해서 사용자가 마우스로 폴더를 탐색하는 것만 막고, 앱이 절대 경로로 직접 접근하는 것(`AppData` 등)은 그대로 허용했다
- `CI`(하위 폴더 상속) + `NP`(1단계만 적용)의 조합으로 C드라이브 루트만 차단하고 앱 실행에 필요한 하위 경로는 건드리지 않았다 — `CI`만 쓰면 앱이 무한 로딩에 빠졌다
- 관리자 계정은 이 정책에서 예외 처리해서, 긴급 대응이나 유지보수 시 탐색기 접근이 막히지 않도록 했다

기존 정책과 새 정책은 서로 충돌하지 않고 상호 보완적으로 작동했다. 애플리케이션의 구현 언어(C++ vs Java)에 따라 같은 종류의 보안 정책이라도 통하는 레이어가 다르다는 걸 이번에 직접 확인했다.

### ✅ RDS Per User 라이선스 — Workgroup 환경의 함정

Bastion 서버가 도메인(AD)이 아니라 Workgroup 환경으로 구성된 상태에서 Per User CAL(라이선스)을 도입하려니, 사용자를 식별할 방법이 없어서 라이선스 할당(Issued) 자체가 실패하는 문제가 있었다. 그 결과 임시 유예 모드(Grace Period)가 강제로 작동하면서, 접속 60분 후 세션이 종료된다는 팝업이 계속 떴다 — 시연 도중에 세션이 끊기면 곤란한 문제였다.

- **원인**: Windows 정책상 Workgroup은 기본적으로 Per Device 모드만 지원한다. Per User 라이선스를 할당하려면 사용자 고유 ID(ObjectGUID)를 저장할 공간이 필요한데, 도메인이 없는 Workgroup 환경에는 그 저장소 자체가 물리적으로 존재하지 않았다
- **검토한 대안**: 라이선스를 Per Device로 다시 구매하는 방법도 있었지만, 이미 구매해둔 Per User 라이선스 자산을 그대로 활용하는 쪽으로 협의가 정리됐다
- **해결**: 단일 서버 안에 독립형 AD LDS(Active Directory Lightweight Directory Services) 인스턴스를 구축해서 RDS 전용 스키마를 확장하고, 라이선스 서버가 이 로컬 AD LDS를 조회하도록 경로를 리다이렉션했다. 사내 통합 플랫폼이 생성하는 로컬 계정이 실시간으로 AD LDS에 동기화되도록 별도 동기화 서비스도 붙였다
- **보안 고려**: AD LDS는 루프백(로컬호스트) 주소로만 열어서 외부 LDAP 접근 자체를 차단했고, 동기화 스크립트도 필요한 속성만 수정할 수 있도록 최소 권한으로 실행했다

"도메인 없이도 정식 라이선스 토큰을 발행할 수 있는가"라는, 처음엔 막연했던 질문이 AD LDS라는 구체적인 해법으로 이어졌다. Workgroup 환경이라는 제약 조건 하나가 라이선스 정책 전체를 다시 설계하게 만든 케이스였다.

### ✅ 그 외 POC마다 새로 튀어나온 예외들

이 외에도 POC를 반복할 때마다 조금씩 다른 예외 상황이 생겼다.

- 캡차(보안 문자)가 있는 로그인 화면은 자동화 범위에서 제외하고, 그 구간만 사용자가 수동으로 입력한 뒤 신호를 보내 세션을 유지하도록 정책을 정리
- 2차 인증(MFA)이 붙은 화면도 마찬가지로 자동화 범위 밖으로 두고, 발생 시 사용자가 직접 처리하도록 안내
- 어떤 POC 현장에서는 사내 통합 플랫폼 API가 참조하는 DB 접속 정보(설정 파일에 저장된 값)와 실제 DB 비밀번호가 어긋나 있어서 연결 자체가 거부되는 문제도 있었다 — 로그를 계층별로(연동 정책 매니저 → DB) 따라가며 어느 구간에서 인증이 끊기는지 확인해야 했다

이런 이슈들은 하나하나는 사소해 보이지만, 현장에서는 POC 전체 일정을 지연시키는 원인이 됐다. 그래서 POC를 반복하면서 얻은 원칙은 하나였다 — **다음 POC 전에 인프라·라이선스·보안 정책을 미리 정상 세팅 완료해두고 들어간다.** 현장에서 새로 발견해서 그 자리에서 고치는 방식은 대응 시간이 너무 길다.

### ✅ 결과 & 배운 점

| 이슈 | 원인 | 해결 |
|------|------|------|
| Bastion 세팅 시간 | 매 POC마다 수동으로 처음부터 구성 | AWS EC2 자동 세팅 절차로 전환 |
| UAC 알림창 | 게시자 미확인 앱 + 관리자 승인 모드 강제 | 로컬 그룹 정책으로 승인 모드 비활성화 |
| SQL Developer C드라이브 접근 | Java 앱이 레지스트리 정책을 무시(NTFS 직접 접근) | icacls 기반 NTFS 권한 물리적 차단 |
| RDS Per User 라이선스 | Workgroup 환경엔 사용자 식별 저장소 부재 | AD LDS 구축 + 실시간 계정 동기화 |

자동화 스크립트를 잘 만드는 것과, 그 스크립트가 실제로 돌아갈 수 있는 환경을 준비하는 것은 완전히 다른 종류의 일이라는 걸 이 프로젝트를 통해 배웠다. 특히 해외 POC처럼 매번 다른 인프라 조건(클라우드냐 물리 서버냐, 도메인이냐 Workgroup이냐)에서 시연해야 하는 상황에서는, 인프라·라이선스·보안 정책을 미리 검증해두는 것 자체가 프로젝트 진행 속도를 결정하는 핵심 변수였다.
