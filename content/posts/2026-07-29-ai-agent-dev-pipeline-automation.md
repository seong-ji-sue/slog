> **TL;DR** — 신규 앱 자동화 스크립트를 개발할 때마다 매번 똑같이 반복하던 "실행파일 찾기 → UI 분석 → 제어 방식 결정 → 스크립트 작성 → 배포·검증 → 등록"이라는 과정 자체를 AI 에이전트가 따라갈 수 있는 스킬로 만들었다. 특정 인프라 전담 점검 에이전트를 붙이고, 스크립트 코드도 AI가 파싱할 수 있는 로그 마커로 표준화했다. 업무 자동화를 만드는 그 업무 자체를 자동화한 메타적인 작업이었다.

### ✅ 상황 — 신규 앱 자동화는 매번 같은 순서로 막혔다

> 나 : 이번 신규 앱은 또 처음부터 분석해야겠네
> 동료 : 저번에 하던 방식대로 하면 되지 않아?
> 나 : 방식은 같은데, 매번 사람이 판단해야 하는 지점이 똑같이 반복돼

새로운 애플리케이션을 자동화 대상으로 추가할 때마다 순서는 항상 비슷했다. 실행 파일을 찾고, 화면 UI를 뜯어보고, 이 앱이 표준 Win32 컨트롤로 제어가 되는지 좌표 클릭이 필요한지 판단하고, 스크립트를 짜고, Bastion에 배포해서 검증하고, 마지막에 제품 DB에 앱 등록정보를 남기는 것까지. 논리적으로는 같은 흐름인데, 매번 새 앱을 마주할 때마다 이 판단 과정을 처음부터 사람이 다시 밟고 있었다.

반복되는 판단 흐름이라면 그 흐름 자체를 파이프라인으로 만들 수 있겠다는 생각이 들었다. 다만 이번엔 파이프라인을 코드로 짜는 게 아니라, AI 에이전트가 그 판단 순서를 그대로 따라갈 수 있도록 스킬(문서화된 절차)로 만드는 방식을 택했다.

### ✅ 신규 앱 개발 파이프라인을 스킬로 — appscript-dev-pipeline

기존에 데스크톱 클라이언트형 앱 하나를 자동화하면서 겪었던 판단 과정을 그대로 일반화해서 스킬 문서로 옮겼다. 실제로 자동화했던 앱은 Win32 자식 컨트롤이 하나도 없는 Qt 기반 UI였는데, 이 사례가 오히려 "표준 케이스가 아닐 때 어떻게 판단해야 하는가"를 정리하기 좋은 재료였다.

스킬은 단계를 명확히 나눴다.

- **Phase 0 — 타입 결정**: 대상이 웹 기반(브라우저 자동화)인지 데스크톱 실행파일 기반인지부터 사람에게 명시적으로 확인받는다. 모호하면 절대 추측하지 않고 사용자에게 되묻는다
- **Phase A — 신규 앱 분석**
  - A-1 실행파일 탐색: 바탕화면 바로가기, Program Files 하위 폴더, 앱 자체 실행 로그를 뒤져서 로그인 진입점 exe와 메인 실행파일을 찾는다
  - A-2 실시간 UI 프로브: Bastion에 배치해둔 포터블 AutoIt으로 창 목록, 자식 컨트롤 클래스, 스크린샷을 수집한다 — 스케줄 작업을 최고 권한으로 등록해 실제 사용자 세션에서 실행되도록 만들어야 데스크톱 접근이 가능했다
  - A-3 제어 방식 결정 트리: 자식 컨트롤이 있으면 표준 Win32 제어, 없고 Qt류 클래스면 좌표 기반 클릭, 그마저도 불안정하면 이미지 매칭(OpenCV)까지 — 3단계로 나눠 판단 기준을 문서화했다
  - A-4 실패 시그니처: 일부러 틀린 계정으로 로그인해서 에러 팝업의 제목·클래스·크기를 기록한다. 로그인창과 에러창의 제목이 같을 수 있어서, 클래스만이 유일하게 신뢰할 수 있는 구분자라는 걸 명시했다
  - A-5 성공 시그니처: "로그인창이 사라졌는가 + 메인창이 떴는가 + 그 메인창의 프로세스가 실제로 살아있는가" 세 가지를 모두 만족할 때만 성공으로 판정하도록 못박았다 — 제목만 보고 성공이라고 판단하는 방식은 명시적으로 금지
- **Phase B 이후 — 스크립트 작성부터 배포·검증·등록까지**: 앞선 분석 결과를 넘겨받아 실제 스크립트를 작성하고, Bastion에 배포해서 빌드·실행까지 검증한 다음, 제품 DB에 남겨야 하는 앱 등록정보(앱 타입 코드, 배포 경로 등)까지 실측해서 매핑해뒀다

이 스킬을 만들고 나서 얻은 건 "다음 신규 앱은 더 빨리 끝난다"는 것보다, **판단 기준 자체가 문서로 고정됐다는 것**이었다. 예전엔 "이 앱은 어떻게 제어할까"를 매번 감으로 판단했다면, 이제는 결정 트리를 따라가면 같은 결론에 도달한다.

### ✅ 특정 인프라 전담 점검 에이전트 — 반복 점검도 위임

신규 앱 개발 파이프라인과 별개로, 특정 인프라(SAP·Oracle 계열 서버) 하나를 전담해서 점검·복구하는 에이전트도 따로 만들었다.

- **점검 전용 스킬**: HANA/ABAP 계열 서비스, Oracle 인스턴스, 호스트 상태를 읽기 전용으로 점검해서 OK/FAIL 리포트만 뽑는다. 이 단계에서는 어떤 것도 건드리지 않는다
- **복구 담당 에이전트**: 점검 결과 이상이 확인되면 진단 후 필요한 서비스 재기동, 메모리 관련 설정 점검, 관련 프로세스 기동까지 처리한다. 단, Oracle 인스턴스 자체는 명시적으로 불가침 대상으로 못박아뒀다 — 잘못 건드리면 복구보다 장애가 커질 수 있는 영역이라 판단했다

점검과 복구를 분리한 이유는 단순하다. "읽기만 하는 것"과 "고치는 것"은 위험도가 다르기 때문에, 점검은 자유롭게 자주 돌리되 복구는 점검 결과가 실제로 FAIL일 때만 실행되도록 경계를 그었다.

### ✅ 스크립트 자체도 표준화 — AI가 읽을 수 있는 로그 마커

파이프라인과 에이전트를 만드는 것과 별개로, 실제로 쌓여있던 자동화 스크립트들도 정리가 필요했다. WEB 타입과 CS(데스크톱) 타입 스크립트마다 공통으로 쓰는 로직(재시도, 로그 기록 등)이 파일마다 따로 구현돼 있었다. 이걸 타입별 공통 유틸 파일로 뽑아내고, 로컬 테스트용 스크립트와 실제 배포용 스크립트를 별도 파일로 분리했다.

여기서 같이 넣은 게 AI가 파싱하기 쉬운 로그 마커였다.

```autoit
; AI가 파싱 가능한 로그 마커 상수
Global Const $LOG_STEP    = "##STEP:"
Global Const $LOG_SUCCESS = "##SUCCESS##"
Global Const $LOG_FAIL    = "##FAIL##"
Global Const $LOG_RESULT  = "##RESULT:exitCode="
```

스크립트 실행 로그를 사람이 읽을 때는 자연어 문장이 더 편하지만, 그 로그를 AI 에이전트가 파싱해서 "이 실행이 성공했는지, 몇 번째 단계에서 실패했는지"를 판단하게 하려면 고정된 마커가 훨씬 안정적이다. 로그 문구가 조금씩 다르더라도 `##SUCCESS##` / `##FAIL##` 마커만 찾으면 되니까, 이후 실행 결과 판정 엔진을 붙일 때도 이 마커를 기준으로 삼을 수 있었다.

이 작업의 핵심은 "코드를 리팩토링했다"가 아니라, **앞으로 이 로그를 읽을 주체가 사람만이 아니라 AI 에이전트일 수도 있다는 걸 전제로 코드를 설계했다**는 점이다.

### ✅ 성과과제 티켓은 비어있었다 — 진짜 기록은 커밋에 있었다

이 전체 작업의 명분이 된 레드마인 티켓 하나가 있었다. 제목은 "AI 성과과제 App Script 목록 취합 및 개발 자동화"였는데, 실제로 조회해보니 본문(description)은 빈 문자열이었고 custom_fields(설계 내역·구현 내역)도 아예 null이었다.

솔직히 말하면 이 티켓만 봐서는 무슨 작업을 했는지 전혀 알 수 없었다. 이 티켓은 "AI로 성과를 내는 과제를 진행한다"는 이니셔티브의 명분 역할만 했을 뿐, 실제로 무엇을 어떻게 했는지에 대한 기록은 전혀 남아있지 않았다.

진짜 작업 내용은 티켓이 아니라 커밋 히스토리에 있었다. 스킬 파일이 언제 어떤 구조로 추가됐는지, 에이전트가 언제 어떤 권한 경계로 설계됐는지, 스크립트 리팩토링이 어떤 순서로 진행됐는지 — 이 모든 게 레드마인이 아니라 git log에 그대로 남아있었다. 업무 관리 시스템에 기록을 남기는 습관과, 실제로 손을 움직인 기록이 코드 저장소에 쌓이는 것은 별개의 문제라는 걸 이번에 다시 확인했다. 성과를 증명해야 할 때 참고할 자료는 결국 커밋 로그였다.

### ✅ 결과 & 배운 점

| 항목 | 이전 | 이후 |
|------|------|------|
| 신규 앱 개발 순서 | 매번 사람이 처음부터 판단 | 결정 트리 기반 스킬로 고정 |
| 특정 인프라 점검 | 필요할 때마다 수동 확인 | 읽기전용 점검 + 조건부 복구 에이전트 분리 |
| 스크립트 실행 로그 | 사람이 읽는 자연어 로그만 | AI가 파싱 가능한 고정 마커 병행 |
| 성과 근거 자료 | 레드마인 티켓 참조 기대 | 실제로는 git 커밋 히스토리가 유일한 기록 |

"AI 에이전트로 업무를 자동화한다"는 이번 작업에서 진짜 흥미로웠던 지점은, 자동화 대상이 고객사 애플리케이션이 아니라 **내가 매번 반복하던 개발 프로세스 자체**였다는 점이다. 신규 앱을 자동화하는 절차를 AI가 따라갈 수 있는 스킬로 옮기고 나니, 다음에 새로운 앱이 들어와도 처음부터 판단 기준을 다시 세울 필요가 없어졌다. 반복 업무를 자동화하는 것과, 반복 업무를 자동화하는 그 과정 자체를 자동화하는 것은 완전히 다른 층위의 일이라는 걸 체감한 작업이었다.
